# Any Learn AI — 詳細設計書

**作成: 2026-08-09 / 状態: 実装から起こした版（dev で稼働中）**

## この文書について

⚠️ **実装が正である。**食い違いを見つけたらコードのほうを信じ、この文書を直すこと。

[基本設計書](基本設計書.md)が「なぜそう分けたか」を扱うのに対し、
本書は**データの形・状態遷移・処理の流れ・リソース一覧**を扱う。

命名規約: `resourceName.table(name, env)` → `any-learn-ai-{name}-{env}`、
`resourceName.lambda(name, env)` → `any-learn-ai-{env}-{name}`。
以下 `{env}` は `dev` / `stg` / `prod`。

| `explanationMode` | | `explanation \| re-explain`（直近の生成） |
| `reExplanations` | | 再解説の履歴 |
| `quizQuestion` | | いま出題中。解き直すたび上書き |
| `quizStatus` / `quizError` / `quizStartedAt` | | 出題の生成状態 |
| `quizAttempts` | | 挑戦の記録（出題ごとに1件） |
| `qaTurns` | | Q&A の記録。文脈供給にも使う |
| `pendingQuiz` | | 先読み済みの確認問題 |

```ts
QaTurn {
  question: string;
  answer: string;                                  // 生成中は空
  status?: 'generating' | 'ready' | 'failed';
  error?: string;
  purpose?: 'hint';                                // ヒント依頼を区別
  inputSource: 'suggested' | 'self_typed' | 'voice';
  askedAt: string;                                 // 猶予の判定に使う
}

QuizAttempt {
  question: QuizQuestion;                          // 模範解答・採点基準ごと残す
  answer: string;
  gradingStatus?: 'grading' | 'ready' | 'failed';
  gradingError?: string;
  isDontKnow: boolean;
  verdict: 'correct' | 'partial' | 'incorrect';
  score: number;                                   // 0〜1
  correctElements / incorrectElements: string[];
  feedbackMessage / misunderstoodConcept: string;
  hintsUsed: number;
  attemptCount: number;                            // 1 始まり
  answeredAt: string;                              // 猶予の判定に使う
}

PendingQuiz {
  question: QuizQuestion;
  attemptCount: number;   // ⚠️ 生成時点の不正解回数
  quizType: QuizType;     // ⚠️ 生成時点の問題タイプ
  generatedAt: string;
}
```

⚠️ **`quizAttempts` は問題ごと残す。**問題を上書きで持っていたころは、
解き直した時点で「何の問題にどう答えたのか」が分からなくなっていた。

⚠️ **`pendingQuiz` は前提が一致したときだけ使う**（`isPendingQuizUsable`）。
確認問題は不正解回数で難易度とヒント有無が変わるので、生成時と前提がずれて
いたら捨てる。使うと「3回間違えたのにヒントの無い難しい問題が出る」ことになる。

### 1.8 MicroCycleState（22値）

```
解説    GENERATING_EXPLANATION → DISPLAYING_EXPLANATION → EXPLANATION_COMPLETE
質問    OPEN_QA_PROMPT → WAITING_FOR_QA_CHOICE → QA_INPUT
        → GENERATING_QA_ANSWER → DISPLAYING_QA_ANSWER → QA_FOLLOWUP_PROMPT
確認    GENERATING_QUIZ → DISPLAYING_QUIZ → WAITING_FOR_ANSWER
        → ANSWER_RECORDING → SUBMITTING_ANSWER
結果    DISPLAYING_CORRECT / DISPLAYING_PARTIAL / DISPLAYING_INCORRECT
再解説  GENERATING_RE_EXPLANATION → DISPLAYING_RE_EXPLANATION
終端    MICRO_STEP_COMPLETE / SESSION_COMPLETE / ERROR
```

初期値は `MICRO_STEP_COMPLETE`。

### 1.9 ai-usage

**使用量レコード**（`llm` の `recordUsage` が書く）

| 属性 | 内容 |
|---|---|
| `scopeKey` | `${userId}#${scopeId}` |
| `usageId` | `${recordedAt}#${randomUUID()}` |
| `userId` / `scopeId` / `scopeKind` | `scopeKind` は `goal\|program\|assessment` |
| `purpose` / `model` | 用途（11値）と実際に使ったモデル |
| `inputTokens` / `outputTokens` / `cacheWriteTokens` / `cacheReadTokens` | |
| `durationMs` / `recordedAt` | |
| `rateInputUsd` / `rateOutputUsd` | **適用した単価**（USD / 100万トークン） |

⚠️ **単価を一緒に残すのが要点である。**

これが無いと読む側が自前の単価表を持つことになり、実際に登録簿と2か所へ
分かれて**2回ずれた**。単価は「その呼び出しに適用された事実」なので、
トークン数と同じ資格で記録に残す。残せば読む側は表を持たなくてよい。

副産物として、改定があっても過去の記録は当時の単価のまま残る。
「実際にいくら課金されたか」を答えるにはそのほうが正しい。

**所要時間の実績**（待ち画面の目安に使う）

| 属性 | 内容 |
|---|---|
| `scopeKey` | 固定値 `#duration-estimates`（`#` 始まりの userId は作られないので衝突しない） |
| `usageId` | `${purpose}#${model}` |
| `totalSeconds` / `samples` | 加算していく |

読み出しは **用途の前方一致**（`begins_with(usageId, '{purpose}#')`）で引き、
`updatedAt` が最新のものを使う。

⚠️ **モデル名で引かない。**待ち画面を出す側はモデルを知らない（決めるのは
LLM サービス）。知るために登録簿を読むと、待ち画面のためだけにプロバイダを
バンドルへ引き込むことになる。

実績が無いときのフォールバック（秒/個）: `explanation 9.8` /
`program-generation 2.4` / `assessment-generation 3.7` / `report 6.2` /
それ以外 30。

## 2. 状態遷移

### 2.1 冪等性の2方式

⚠️ **書き込みの形で使い分ける。**

| 書き込みの形 | 2回受けると | 方式 |
|---|---|---|
| 同じ値を**上書き** | 何も変わらない | 状態遷移を条件にする |
| 値を**積む**（`list_append` / `ADD`） | 二重に積まれる | 席を先に作って埋める |

#### 方式A: 状態遷移を条件にする

```
ConditionExpression: 'attribute_exists(programId) AND #generationStatus = :generating'
```

2回目は `ConditionalCheckFailedException` で弾かれる。
⚠️ **この例外は成功として扱う。**先に誰かが完了させた＝目的は達成されている。
例外にすると EventBridge が再試行し続け、最後は DLQ へ落ちる。

#### 方式B: 席を先に作って埋める

対話系は積む書き込みばかりで、二重に積まれると学習者に見える形で壊れる。

| 書き込み | 2回受けると |
|---|---|
| `appendQaTurn` | 同じ質問と回答が2回並ぶ |
| `appendQuizAttempt` | 挑戦記録が2件になる |
| `appendChatAndUpdate` | 同じ発言が2回会話に残る |
| `bumpProgress` | **不正解回数が2つ進む** → 再解説の切り口とヒントの有無がずれる |

```
受付（HTTP の同期処理）  appendQaTurn(...) → 添字を返す。context に載せる
結果ハンドラ            completeQaTurn(sessionId, microStepId, index, answer)
                        └ SET qaTurns[index].answer = :answer, ...
```

受付は再配信されないので積むのは1回きり、埋めるのは上書きなので何回でも同じ。
**方式A に還元される。**

⚠️ **数える処理も受付側へ置く。**数えるのは「質問したこと」自体に対してで、
生成が返ったかどうかではない。

⚠️ **処理済み ID の集合を持つ案は捨てた。**方式B にすれば防壁そのものが要らない。
次に同じ問題へ当たったら、**まず「積む操作を同期処理へ移せないか」を考えること。**

### 2.2 猶予による終端（`domain/stale.ts`）

非同期にすると「結果が返ってこない」経路が必ず生まれ、レコードは
`generating` のまま残る。これが2つを塞ぐ。

1. 画面が待ち続ける
2. 受付が「生成中だから待って」と返し、**作り直せなくなる**

⚠️ **書き換えずに、読むときに判断する。**

```
「生成中」= status が generating/grading かつ、開始から STALE_AFTER_MS 以内
猶予を過ぎたら → 読む側が failed として扱う
```

| 定数 | 値 |
|---|---|
| `STALE_AFTER_MS` | 5分 |
| `IN_PROGRESS` | `{'generating', 'grading'}` |
| `STALE_REASON` | 「時間内に結果が届きませんでした。もう一度お試しください。」 |

適用箇所: `resolveGenerationStatus` / `resolvePlanStatus`（goal）、
`getProgramStatus`（program）、`toPublicQaTurns` / `toPublicQuizAttempts`
（micro-step）、`toPublicQuestions`（assessment）、`get-explanation`、
`generate-explanation`（受付）。

⚠️ **掃除係を経路ごとに増やさなかった理由。**

対話系の「生成中」は配列の中（`qaTurns[i].status`）にあり索引を張れない。
掃除係で書き換えようとするとテーブル全件走査になり、学習者が増えるほど重くなる。
しかも取り残しがゼロのときも毎回走る。

⚠️ **開始時刻が読めないときは「待ってよい」に倒す。**読めないのは移設前の記録か
書き込みが壊れた場合で、「届かなかった」と決めつける根拠にならない。
待たせるほうが、出来ているものを作り直させるより害が小さい。

⚠️ **残る弱点: レコードは `generating` のまま残る。**生の `status` を直接見る
集計は誤る。状態は必ず `domain/stale.ts` を通して読むこと。

### 2.3 主要な遷移

#### goals

| 遷移 | 関数 | 条件 |
|---|---|---|
| 作成（`clarifying` + `generating`） | `putGoal` | — |
| 分析完了（`ready`） | `saveGoalAnalysis` | `attribute_exists(goalId) AND #generationStatus = :generating` |
| 分析失敗 | `saveGoalAnalysisFailure` | 同上 |
| 見積もり開始 | `markEstimating` | `attribute_exists(goalId)` |
| 見積もり完了 | `saveEstimate` | `attribute_exists(goalId) AND attribute_not_exists(totalSessions)` |
| 計画の算出開始 | `markPlanCalculating` | `attribute_exists(goalId)` |
| 計画の確定（`active` + `ready`） | `confirmPlan` | `attribute_exists(goalId)` |
| チャットの席を作る | `appendChatAndUpdate` | `attribute_exists(goalId)` / `ReturnValues: UPDATED_NEW` |
| チャットの返答を埋める | `completeChatReply` | `attribute_exists(goalId)` |

⚠️ `saveEstimate` の `attribute_not_exists(totalSessions)` は「すでに計画が確定
していたら見送る」という意味。先読みの結果が確定後に届くことがある。

#### programs

| 遷移 | 関数 | 条件 |
|---|---|---|
| 作成（`generating`・`phases: []`） | `putProgram` | — |
| 完了 | `completeProgramGeneration` | `attribute_exists(programId) AND #generationStatus = :generating` |
| 失敗 | `failProgramGeneration` | 同上 |

掃除係 `sweep-stuck-generations`（1時間ごと）: `Scan` +
`#generationStatus = :generating AND #updatedAt < :threshold`（30分）。

⚠️ **DLQ は自動で redrive しない。**入った理由が分からないまま戻すと、
同じ理由で落ちて往復するだけになる。鳴らして人が見る。

#### micro-steps

| 遷移 | 関数 | 条件 |
|---|---|---|
| 解説の生成開始 | `startExplanationGeneration` | `attribute_exists(microStepId)` |
| 先読みの生成権取得 | `claimExplanationGeneration` | `attribute_exists(microStepId) AND attribute_not_exists(explanationStatus)` |
| 解説の保存 | `saveExplanation` | `attribute_exists(microStepId)` |
| 出題の生成開始 | `startQuizGeneration` | `attribute_exists(microStepId)`（前の問題を REMOVE） |
| 先読みの消費 | `consumePendingQuiz` | `attribute_exists(pendingQuiz)`。失敗時はその場生成へ |
| Q&A の席を作る | `appendQaTurn` | `ReturnValues: UPDATED_NEW` |
| 採点の席を作る | `appendQuizAttempt` | 同上 |

⚠️ `startQuizGeneration` は前の問題を消す。残したまま `generating` にすると、
画面が「新しい問題を待っている」のか「前の問題に答えればよい」のか区別できない。

#### assessments

| 遷移 | 関数 | 条件 |
|---|---|---|
| 1問の回答を保存 | `saveAnswer` | `attribute_exists(assessmentId)` |
| 総合スコアの再計算 | `recomputeTotals` | `attribute_exists(assessmentId) AND (attribute_not_exists(#answeredCount) OR #answeredCount < :answeredCount)`。弾かれたら読み直して最大3回 |

⚠️ **集計は必ず読み直してから行う。**

移設前は受付が手元の設問一覧から計算していた。採点が同期だったのでそれは常に
最新だった。非同期になると、続けて2問答えると採点が2つ並走し、**古い
スナップショットで計算した総合スコアが新しいものを上書きしうる。**
1問ぶんの点が静かに消え、エラーは出ない。

⚠️ `completedAt` は `if_not_exists` で守る。二重配信で2回目の時刻に更新されると、
診断にかかった時間が狂う。

## 3. 非同期の配管

### 3.1 契約

```ts
// SQS メッセージの本文
interface LlmRequest {
  schemaVersion: number;     // 版違いは失敗として返す（キューに14日残るため必ず起きる）
  requestId: string;         // 同じ依頼を2回積んでも安全な形にすること
  purpose: Purpose;          // 11値
  system: string;
  userPrompt: string;
  schema: Record<string, unknown>;
  maxTokens?: number;
  usage?: UsageScope;        // { userId, scopeId, kind, units? }
  replyTo: string;           // 結果イベントの detail-type
  context: Record<string, unknown>;  // サービスは中身を一切見ない
}

// EventBridge イベントの detail
interface LlmResult {
  schemaVersion: number;
  requestId: string;
  purpose: Purpose;
  context: Record<string, unknown>;  // 依頼の context をそのまま返す
  status: 'succeeded' | 'failed';
  output?: unknown;          // 成功時。スキーマ検証を通った JSON
  error?: { kind: LlmErrorKind; message: string };
  model: string;             // 実際に使ったモデル
  durationMs: number;
  attempts: number;          // 1 または 2
  replyTo: string;           // 全宛先を購読する通知係が要る
}

type LlmErrorKind =
  | 'rate-limited'  // 待って積み直す価値がある
  | 'truncated'     // 上限で打ち切られた
  | 'refused'       // モデルが拒否。積み直しても無駄
  | 'schema'        // 2回試してもスキーマに合わなかった
  | 'provider'      // プロバイダが 4xx/5xx
  | 'unknown';
```

⚠️ **モデル名は依頼に入れない。**呼び出し元が指定できると、登録簿に無い名前が
入る経路ができ、単価表にも載らず原価が消える。

⚠️ **`context` を解釈しない。**サービスはそのまま echo する。これが無いと、
後処理が「どの生成の結果か」を別途引き当てることになる。

### 3.2 requestId の付け方

| 経路 | 鍵 |
|---|---|
| プログラム生成 | `{programId}` |
| 解説 | `explanation#{microStepId}` |
| Q&A（ステップ） | `qa#{sessionId}#{microStepId}#{index}` |
| Q&A（セッション） | `session-qa#{sessionId}#{index}` |
| 採点 | `grading#{sessionId}#{microStepId}#{index}` |
| 出題（その場） | `quiz-now#{microStepId}#{attemptCount}` |
| 先読み | `quiz#{microStepId}#{attemptCount}` |
| 目標チャット | `goal-chat#{goalId}#{index}` |
| 記述式の採点 | `answer-evaluation#{assessmentId}#{index}` |

⚠️ **出題と先読みで鍵を分けてある。**同じにすると、先読みの結果が出題の席へ、
あるいはその逆へ書き込まれる余地ができる。宛先（`replyTo`）も分けてある。

### 3.3 宛先（REPLY_TO）と後処理

⚠️ **CDK は必ずこの定数を import すること。**detail-type を手で書くと必ずずれ、
ずれても**通知だけ届かない**形で現れるので気づきにくい。

**core（11宛先）**

| detail-type | 後処理 |
|---|---|
| `program-generation.completed` | 検査して保存 |
| `goal-analysis.completed` | 目標の骨格を保存 |
| `plan-estimate.completed` | 見積もりを保存するだけ |
| `plan-calculation.completed` | 計画を確定し、プログラム生成まで進む |
| `explanation.completed` | 保存し、確認問題と次ステップを先読み |
| `re-explanation.completed` | 切り口と不正解回数は依頼時の値を使う |
| `quiz-prefetch.completed` | `pendingQuiz` へ置く。**失敗は握りつぶす** |
| `qa.completed` | 席へ回答を埋める（ステップ／セッション両方） |
| `quiz.completed` | `quizQuestion` へ置く。**失敗は必ず書く** |
| `grading.completed` | 席へ採点結果を埋め、画面の状態を進める |
| `goal-chat.completed` | 席へ返答を埋め、合意なら状態を進める |

**assessments（3宛先）**

| detail-type | 後処理 |
|---|---|
| `assessment-generation.completed` | ドメイン検査を通して保存 |

⚠️ **見積もりと算出、先読みと出題は宛先を分けてある。**同じ用途・同じプロンプト
だが、結果を受けたあとにやることが違う（片方は保存だけ、もう片方は次へ進む）。

### 3.4 キューとイベントバス

| リソース | 設定 |
|---|---|
| `any-learn-ai-llm-requests-{env}` | 可視性タイムアウト11分、保持4日、DLQ へ `maxReceiveCount: 3` |
| `any-learn-ai-llm-requests-dlq-{env}` | 保持14日 |
| `any-learn-ai-llm-results-{env}`（EventBus） | 結果の配信 |
| `any-learn-ai-llm-smoke-results-{env}` | 疎通確認専用。保持1時間 |

⚠️ **可視性タイムアウト（11分）> Lambda のタイムアウト（10分）**。
逆にすると、まだ動いている処理をもう1つ起動して二重に課金される。

消費側: `batchSize: 1` / `reportBatchItemFailures: true` /
`maxConcurrency` = prod 50 / stg 10 / dev 5。

⚠️ `reportBatchItemFailures` は**ハンドラと CDK の両方**で有効にすること。
片方だけだと、失敗した1件のせいでバッチ全体が再配信される。

### 3.5 疎通確認

デプロイのたびに1往復させる（`scripts/smoke-test.mjs`）。

キュー・消費側・鍵・イベントバス・ルールのどれが切れていても、症状は
「学習者の画面が `generating` のまま止まる」という同じ形で出る。

専用の detail-type（`smoke-test`）を使い、本番の経路へは流れ込まない。
通知係も `anything-but` でこれだけ除いている。

### 3.6 監視

| アラーム | 意味 |
|---|---|
| DLQ not-empty | 1件でも入ったら鳴る。**鳴らないと学習者は待ち続ける** |
| 依頼の滞留（10分超） | 消費が追いつかない |

## 4. LLM サービスの内部

### 4.1 処理の流れ

```
SQS → consumer
  ├ 版を確認（違えば失敗として返す）
  ├ SSM + 登録簿でモデルを解決
  ├ プロバイダ呼び出し
  ├ スキーマ検証（再帰）→ 通らなければ1回だけ作り直す
  ├ 使用量と所要時間を記録（単価も一緒に）
  └ EventBridge へ結果を出す（成功も失敗も）
```

⚠️ **失敗も成功と同じ経路で返す。**失敗の通知経路を別に作ると、
その経路自体の故障が次の穴になる。

⚠️ **例外を投げるのは「結果を届けられないとき」だけ。**生成の失敗は
`status: 'failed'` として正常に返す。投げるとキューが再試行し、
同じ生成をもう一度課金することになる。

### 4.2 モデル選択

```
SSM /any-learn-ai/{env}/model/{purpose}  →  無ければ PURPOSE_DEFAULTS
                                          →  登録簿に無ければ既定へ落とす
```

キャッシュ 60秒。⚠️ `GetParametersByPath` は**パス自身にも**権限が要る
（`/model` と `/model/*` の両方）。片方だけだと黙って既定へ落ち、
「SSM で差し替えたのに効かない」が見えない形で起きる。

### 4.3 登録簿と単価

⚠️ **単価は登録簿の各行に同居させてある。**

別表にすると、同じリポジトリに置いても片方だけ足す事故が起こる
（実際に2回起きた形）。同じ行に置けば、モデルを足すときに単価を書かないと
**コンパイルが通らない。**

| モデル | 単価（USD / 100万トークン） |
|---|---|
| `claude-sonnet-5` | 3 / 15 |
| `claude-haiku-4-5` | 1 / 5 |
| `claude-opus-5` | 5 / 25 |
| `qwen3.7-plus` | 0.32 / 1.28 |
| `qwen3.7-flash` | 0.03 / 0.13 |
| `gpt-5.6-luna` | 0.2 / 1.2 |

⚠️ **未登録のモデルは 0 を返さない。**0 だと「無料」として扱われ、
読む側が安いと誤解する。`undefined` を返し、見積もりとして扱わせる。

### 4.4 品質検査

**サービス側（スキーマ）**: `type / properties / required / items / minItems /
maxItems / enum / minLength` を再帰的に見る。

⚠️ **最上位の `required` だけでは足りない。**実験（18件）で発火率が 0/18 だった。
OpenAI 互換の口はスキーマを強制できないので、ここが唯一の防波堤になる。

**呼び出し元（ドメイン）**: 「学習として成立するか」を見る。作り直さない。

| 検査 | 何を見るか |
|---|---|
| `program-quality.ts`（core） | フェーズ・単元・セッションの構造、セッション総数 |
| `assessment-quality.ts`（assessments） | 件数・選択肢の整合・難易度の偏り |

⚠️ `assessment-quality.ts` は移設で**新設した**。assessments には品質検査が
ひとつも無かった（Sonnet 固定でスキーマ強制が効いていたため）。

## 5. WebSocket 通知

### 5.1 構成

| 何 | どこ | なぜそこか |
|---|---|---|
| WebSocket API・2テーブル・認可・チケット発行 | `shared-infra` | REST API と Cognito を持つのがここ |
| 通知を送る係 | `llm` | 購読するバスをこのサービスが持っている |

⚠️ **送る側を `shared-infra` に置けない。**あちらがバスを読むと
`shared-infra → llm → shared-infra` の循環になり、どちらも先にデプロイできない。

### 5.2 送る内容

```ts
interface Signal {
  kind: string;      // replyTo と同じ
  status: 'succeeded' | 'failed';
  ids: Record<string, string | number>;  // sessionId / microStepId / index など
}
```

⚠️ **生成物は送らない。**画面は合図を受けて GET で読み直す。
これで読む経路が1つに保たれ、ポーリングと WebSocket が同じコードへ収束する。

⚠️ **失敗の理由も送らない。**文言はドメインの後処理が決める。
ここで作ると2か所で持つことになる。

⚠️ **通知係は結果の中身を解釈しない。**`userId` と識別子だけを見る。
それ以上を知ると、LLM サービスが学習ドメインを知ることになる。

### 5.3 ルール

すべての宛先を1つのルールで拾う（`anything-but` で疎通確認だけ除く）。

⚠️ **宛先ごとに分けない。**中身を見ないので分けても同じ処理が並ぶだけで、
detail-type を列挙すると経路を足すたびに直すことになる。忘れると
**通知だけ届かない**——しかもポーリングで動くので気づけない。

再試行は**1回だけ**。届かない理由は変わらないので、何度も試すと同じ合図が
遅れて何度も飛ぶだけになる。

### 5.4 接続の掃除は3重

`$disconnect` は回線が切れた場合などに届かないことがある。

1. `$disconnect` で消す
2. TTL（2時間 = WebSocket の最大接続時間）で消す
3. 送信で **410 Gone** が返ったらその場で消す

⚠️ **410 以外では消さない。**一時的な障害で生きた接続を消すと、その学習者は
ポーリングだけになる（壊れはしないが速さが戻らない）。

⚠️ **410 は実環境で再現しにくい。**偽の接続 ID では「Invalid connectionId」が
返る。410 は「形式は正しいがもう切れている接続」だけなので、単体テストで固めてある。

動的ルートは `__shell` へリライトする。

### 7.2 待ち方

```ts
pollUntilDone(fetcher, {
  isDone, isFailed, failureMessage,
  intervalMs,            // 2〜5秒
  timeoutMs,
  maxConsecutiveFailures,  // 既定5回
  onTick,                  // ⚠️ 待ち帯の目安を受け取る
  signal,
  wakeUp,                  // ⚠️ WebSocket の合図で間隔を待たずに起きる
});
```

**投げうる例外は3つ。**⚠️ **1つに丸めないこと。**

| 例外 | 意味 | 学習者に勧めること |
|---|---|---|
| `PollFailedError` | サーバーが失敗を記録した | もう一度作る |
| `PollUnreachableError` | 状態を読めない（既定5回連続） | **作り直させない。**開き直す |
| `PollTimeoutError` | 読めているが終わらない | 待つ（続いている） |

⚠️ **以前は 2 が 3 として現れていた。**401 以外の例外を全部握りつぶして再試行
するので、GET が 500 でも「サーバー側で続いています」と出た。
状態を一度も読めていないのだから、そう言う根拠が無い。

⚠️ **`onTick` を忘れると待ち帯が出ない。**目安（`estimatedSeconds`）と開始時刻は
生成**中**の応答にしか入らない。最終値だけを見ていると、待っている間ずっと
目安が取れず、経過秒だけが増える。**成功経路のテストでは見つからない。**

### 7.3 通知の受け口

- 接続は**1本だけ**張って共有する（複数の待ちがあっても）
- 待ちが無くなったら閉じる（接続テーブルを無駄に埋めない）
- 5回張れなければ、その環境では張れないと判断して以降試さない
- **合図は識別子まで突き合わせる。**種別だけだと関係のない合図で読み直しが走る

⚠️ 宛先の名前は `lib-web/reply-kinds.ts` に1か所だけ持つ。サーバーの `REPLY_TO`
とずれると、合図が素通りして間隔ぶん待つ——エラーにならず
**「WebSocket を足したのに速くならない」**形で現れるので気づきにくい。

## 8. 運用

### 8.1 デプロイ順序

```
cicd → shared-infra → llm → core / assessments / media → frontend
```

⚠️ **SSM の依存があるので順序を守ること。**先に進めると
「パラメータが見つからない」で失敗する。

⚠️ 共有 API Gateway にリソースを追加しただけでは、そのリソースはステージに
反映されない（HTTP 403 になる）。**ステージの再デプロイが必須**で、しかも
結果整合性がある。

### 8.2 環境ごとの差

| 設定 | dev | stg | prod |
|---|---|---|---|
| ログ保持 | 7日 | 30日 | 90日 |
| 消費側の同時実行数 | 5 | 10 | 50 |
| PITR | 無し | 有り | 有り |
| removalPolicy | DESTROY | RETAIN | RETAIN |

### 8.3 モデルの差し替え

```
aws ssm put-parameter --name "/any-learn-ai/{env}/model/{purpose}" \
  --value "claude-sonnet-5" --type String --overwrite
```

反映は最大60秒（キャッシュ）。⚠️ 登録簿に無い名前を入れると黙って既定へ落ちる。
