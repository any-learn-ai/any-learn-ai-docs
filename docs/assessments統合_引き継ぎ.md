## 0. なぜ統合したのか（⚠️ 蒸し返さないこと）

利用者の言葉:

> なんでこんな複雑な実装なんですか？
> 理解度チェックの回答が終わったら、診断結果と学習プログラムの目次を
> 生成してそれを表示すればいいだけですよね。
>
> もう、core と assessment 統合したほうがいいですかね？

⚠️ **指摘は正しかった。**その日のうちに、複雑さが原因の不具合を2つ出している。

**(1) 診断結果が目標に載らず、プログラムが作られなかった**

⚠️ レポートは assessments、目標は core にあった。だから診断結果を
**画面に運ばせていた。**ところが運ぶ先に選んだ「見積もりの受付」は
⚠️ レポートより先に走る。その時点では診断結果がまだ無い。
⚠️ そして2回目以降は早期 return するので、保存の機会が二度と来ない。

**(2) 生成が一度も走らなかった**

`preview-program` を core に足したとき、⚠️ LLM キューへ積む権限と
環境変数を渡すループに入れ忘れた。⚠️ **型検査もテストも通っていた。**

⚠️ **(2) の落とし穴は、assessments の配線を調べたときに自分で発見して
報告していた。**それでも core で同じ関数を足すときに踏んだ。
⚠️ **間違えられる箇所が多すぎる、というのが統合の理由だった。**

## 3. ⚠️ 統合で踏みかけた罠（次に同じことをする人へ）

### (1) ⚠️ テーブル名がサービス名から作られていた

診断テーブルだけが `resourceName.table(SERVICE_NAME, ...)` で作られていた。
名前は同じ `assessments` になるので普段は気付かない。⚠️ **しかし core へ
持ち込むと `any-learn-ai-core-dev`（＝スタック名と同じ）に化ける。**

⚠️ **goals が MERGE-NOTES 第4段階で踏んだのと文字どおり同じコード**だった。
⚠️ **統合の前に、単独のコミットで潰した**（段2）。実テーブル名が変わらない
ことを合成結果で確認してからデプロイしている。

### (2) ⚠️ 同名の環境変数が、別のテーブルを指す

core も assessments も `USAGE_COUNTERS_TABLE_NAME` /
`DURATION_ESTIMATES_TABLE_NAME` を使うが、中身は別のテーブルである。

⚠️ **取り違えても型検査も cdk synth も通り、実行時にすら例外が出ない。**
症状は「上限の判定が別サービスの数を見る」という静かな壊れ方で、
⚠️ **配線漏れより見つけにくい。**番人を新設した。

### (3) 論理 ID の衝突

`SharedApi` / `LlmRequestQueue` / `LlmResultBus` / `UsageCountersTable` /
`DurationEstimatesTable` が両側に存在した。別 ID で参照して回避した。

⚠️ **AI に丸投げすると分量が制御不能になる。**

消せるのは「独立した LLM 呼び出しとしての段」だけで、
⚠️ **レポート生成に統合する**（どちらも同じ回答を読んでいる）。

⚠️ **順序を守ること:**

1. レポートのプロンプト／スキーマに「必要セッション数・目次・根拠・里程」を足す
   （⚠️ この時点では誰も読まない。無害）
2. レポートの結果ハンドラが、それらを保存する
3. プログラム生成をレポート完成から起動する
4. ⚠️ **そのあとで**見積もりを消す
5. 番人を移す

⚠️ **4 を先にやると、誰も学習を始められなくなる。**
