## 0. なぜ統合するのか（⚠️ 蒸し返さないこと）

利用者の言葉:

> なんでこんな複雑な実装なんですか？
> 理解度チェックの回答が終わったら、診断結果と学習プログラムの目次を
> 生成してそれを表示すればいいだけですよね。
>
> もう、core と assessment 統合したほうがいいですかね？

⚠️ **指摘は正しい。**その日のうちに、複雑さが原因の不具合を2つ出している。

### ⚠️ 実際に起きた不具合（どちらも「境界をまたぐ」ことが原因）

**(1) 診断結果が目標に載らず、プログラムが作られなかった**

⚠️ **レポートは assessments、目標は core にある。**だから診断結果を
**画面に運ばせていた。**ところが運ぶ先に選んだ「見積もりの受付」は
⚠️ **レポートより先に走る**（時間短縮のため）。その時点では診断結果が
まだ無い。⚠️ **そして2回目以降は早期 return するので、保存の機会が
二度と来ない。**

**(2) 生成が一度も走らなかった**

`preview-program` を core に足したとき、⚠️ **LLM キューへ積む権限と
環境変数を渡すループに入れ忘れた。**結果、DynamoDB のレコードだけ
作られ、⚠️ **画面は「作成しています…」のまま永久に待ち、その空の
プログラムが同時学習数の枠を食った。**

⚠️ **型検査もテストも通っていた。**

⚠️ **(2) の落とし穴は、assessments の配線を調べたときに自分で発見して
報告していた。**それでも core で同じ関数を足すときに踏んだ。
⚠️ **間違えられる箇所が多すぎる、というのが統合の理由である。**

## 4. ⚠️ 見積もりの段を、先に消さないこと

⚠️ **`docs/診断からプログラムまでの単純化_設計.md` を必ず読むこと。**

要点だけ再掲する。

⚠️ **「見積もりを消す」は不正確である。**`totalSessions` は
プログラム生成の**入力**で、「何回にするか」を決める仕事は消せない。
⚠️ **AI に丸投げすると分量が制御不能になり、原価も揺れる。**

消せるのは「独立した LLM 呼び出しとしての段」だけで、
⚠️ **レポート生成に統合する**（どちらも同じ回答を読んでいる）。

⚠️ **順序を守ること:**

1. レポートのプロンプト／スキーマに「必要セッション数・目次・根拠・里程」を足す
   （⚠️ この時点では誰も読まない。無害）
2. レポートの結果ハンドラが、それらを保存する
3. プログラム生成をレポート完成から起動する
4. ⚠️ **そのあとで**見積もりを消す
5. 番人を移す

⚠️ **4 を先にやると、誰も学習を始められなくなる。**

## 6. ⚠️ このプロジェクトで守ること（再掲）

- ⚠️ **「緑になった」は結果ではない。**守りを外して落ちることを実測する
- ⚠️ **推測で断定しない。**ログとデータで裏を取る
- ⚠️ **手元から `cdk deploy` しない。**必ず GitHub Actions 経由
- ⚠️ **状態を変える操作は、必ず先に確認を取る**
- ⚠️ **`main` への push は dev にだけ届く**（stg/prod は手動）

### ⚠️ 2026-08-23 の失敗（同じ轍を踏まないこと）

1. 文言を直して **jest を回さずに** push → CI で落ちた
2. **同着を区別せず 54.2%** と集計し、それを根拠に大きな設計変更を勧めた
   （正しくは期待正答率 30.8%、ランダム 25%）
3. 「カスタマイズできない」と言われて **どの画面か確認せず** 別の場所を直した
4. 診断結果の保存先を、**レポートより先に走る処理**に紐づけた
5. **自分で報告した配線の落とし穴を、自分で踏んだ**

⚠️ **すべて「先に確かめれば分かったこと」である。**

## 7. ⚠️ 隔離してある論点（統合と混ぜないこと）

- ⚠️ **確定時の生成が上限を見ていない**（`plan-finalize` は `checkLimit` を
  通らない）。プレビュー側だけ見ているので抜け道がある
- ⚠️ **画面が読む `limits` は契約時の焼き込み値**で、サーバーのクレーム
  （`plans.ts` から引き直し）と食い違う。⚠️ 項目が増える前に契約した
  Standard の人が影響を受ける
- 設問の質（`設問の質_実測メモ.md`）— 規範系テーマで消去法 13%
- 原価と収支（⚠️ **利用者が「あとで」と決めた**）
