## 1. システム概要

### 1.1 プロジェクト目的

本システムは、AIを活用した完全個別対応の学習支援プラットフォームである。ユーザーが自由に学習テーマを指定するだけで、AIが現在の理解度を診断し、最適な学習プログラムを自動生成する。先生アバターによるインタラクティブな指導を通じ、「本物の個別指導教室」に近い学習体験を提供することを目的とする。

### 1.2 主要ユーザーシナリオ

```
【ユーザー操作フロー全体像】

① 学習テーマ指定（フリーテキスト or 音声）
   例：「中学受験難関校レベルの確率をマスターしたい」
   例：「自動車免許の筆記試験対策をしたい」
         ↓
② 目標設定チャット（AI）
   ・到達レベルの確認
   ・扱う範囲の確認
   ・目標内容の合意
   ※ 期間・学習時間はここでは扱わない（現在地が不明なため判断できない）
         ↓
③ 測る深さを選んで理解度チェック実施
   ・軽め / 普通 / しっかり（既定・推奨）から選ぶ
   ・問題数は深さとテーマの広さで決まる（10〜30問）
   ・AI生成の診断問題
   ・タイピング or 音声で回答
   ・先生アバターが進行
         ↓
④ 診断レポート表示
   ・強化すべき点の可視化
   ・できている点の可視化
   ・分野別スコアチャート
         ↓
⑤ 学習ペースの選択（学習者）
   ・学習の深さ（軽め / 普通 / しっかり）→ セッション数が決まる
   ・学習期間（週）と学習する曜日
   ・1日あたりの所要時間は、選んだ内容から導いて目安として表示
         ↓
⑥ 学習プログラム生成・確認
   ・フェーズ・ユニット・セッション構成
   ・各セッションの実施予定日の表示
         ↓
⑥ 学習実施（繰り返し）
   ・先生アバター + 音声 + 吹き出しで指導
   ・テキスト・画像・アニメーションで解説
   ・いつでも自由質問可能
   ・進捗はいつでも確認可能
```

|--------|--------|------|

| F-003 | アセスメント | AI生成問題による理解度診断（問題数は深さとテーマで可変） |

### 2.1 システムアーキテクチャ

```
【AWS全体構成図】

ユーザー（ブラウザ）
    │
    ├─[HTTPS]─→ Amazon CloudFront
    │                   │
    │          ┌─────────┴──────────┐
    │          │                    │
    │      S3 (静的資産)      API Gateway (HTTP API)
    │      ・React SPA            │
    │      ・アバター画像          │
    │      ・Lottieアニメ    ┌─────┴──────────────────────┐
    │                       │   マイクロサービス（スタック）│
    │                       │  ・core                     │
    │                       │    目標・計画・プログラム    │
    │                       │    学習ループ（解説〜採点）  │
    │                       │  ・assessments              │
    │                       │    理解度チェック            │
    │                       │  ・media                    │
    │                       │    音声合成・アップロード    │
    │                       └─────┬──────────────────────┘
    │                             │
    │              ┌──────────────┼──────────────────┐
    │              │              │                  │
    │         DynamoDB        S3 (コンテンツ)   Secrets Manager
    │         ・学習目標      ・学習コンテンツ   ・Claude API Key
    │         ・プログラム    ・TTS音声キャッシュ ・代替 LLM API Key
    │         ・セッション    ・ユーザー音声
    │         ・マイクロステップ
    │         ・理解度チェック
    │         ・AI 使用量
    │
    ├─[STT]──→ Amazon Transcribe（音声→テキスト）
    └─[TTS]──← Amazon Polly（テキスト→音声）

                    ↕ Anthropic Claude API（外部）
                    ・claude-opus-4-8（高品質タスク）
                    ・claude-haiku-4-5（高速タスク）

【認証フロー】
ユーザー ──→ Amazon Cognito User Pool ──→ JWT発行
                                      ↓
                         API Gateway Lambda Authorizer
                                      ↓
                              Lambda関数（認可済み）
```

#### サービス分割の方針

リポジトリ＝サービス＝CDK スタックとし、デプロイの単位を分ける。

| サービス | 担当 | 主な API |
|---------|------|---------|
| shared-infra | 共有 API Gateway・Cognito・鍵・AI 使用量テーブル | （リソース提供のみ） |
| **core** | 学習目標・学習計画・学習プログラム・学習ループ | `/goals` `/programs` `/progress` `/sessions` `/micro-steps` |
| assessments | 理解度チェックと診断レポート | `/assessments` |
| media | 音声合成・ファイルアップロード | `/tts` `/uploads` |
| frontend | 画面（Next.js の静的書き出し）+ CloudFront | — |
| cicd | GitHub OIDC のデプロイロール払い出し | — |

**core は learning と goals を統合したもの**

当初は「学習ループ（learning）」と「目標・プログラム（goals）」を別サービスに
していたが、両者を1つに統合した。分けていたことによる不利益が、分けている
利益を上回ったため。

- 学習の進捗は「プログラム構造（goals 側）」と「完了セッション（learning 側）」の
  両方が揃わないと計算できない。サービスをまたぐ HTTP 呼び出しが必要で、
  往復のぶん遅く、認証ヘッダを引き回す必要があり、相手サービスの障害が
  そのまま自分の障害になっていた。統合により、この3つが同時に消えた
- プログラムを削除するとき、学習記録も一緒に消す必要がある。
  別サービスだと「片方だけ消えた」状態が起こりうる
- 目標・プログラム・セッションはすべて1人の学習者の1つの学習に属する。
  独立して変更される単位ではなかった

なお programs（学習プログラム）はさらに以前に goals へ統合済みで、
その結果が core に引き継がれている。

統合の副作用として、API Gateway 上のパスは変えていない。
`/programs` `/progress` はルート直下のままで、`/goals` 配下へは移していない。
移すと呼び出し側（フロントエンド）が全て壊れるため。

### 2.3 AIモデル利用戦略

Anthropic Claude APIを直接利用（AWS Bedrockは使用しない）。

#### モデル選定基準

```
【Claude Opus 4.8 を使用する処理】
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  用途: 高品質な推論・生成が必要なタスク
  特徴: 最高品質だが応答にやや時間がかかる
  ユーザー影響: バックグラウンドで実行（待ち時間許容）

  ① アセスメント問題生成（一括・問題数は可変）
     - 学習テーマの本質を理解した良問生成
     - 難易度バランスの制御
     - ひっかけ問題の作成

  ② 診断レポート生成
     - 全問の回答パターンから複合的分析
     - 強み・弱みの言語化
     - 個別化されたコメント生成

  ③ 学習プログラム生成
     - 長期学習計画の立案
     - フェーズ・ユニット・セッションの階層設計
     - ユーザー特性を反映したカスタマイズ

【Claude Haiku 4.5 を使用する処理】
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  用途: 低レイテンシ・高頻度な対話タスク
  特徴: 高速・低コスト、品質も十分
  ユーザー影響: リアルタイム応答（2秒以内）

  ① 学習セッション中の会話・フィードバック
     - 回答の正誤評価とコメント
     - ヒント提供
     - 次ステップへの誘導

  ② 自由質問への回答
     - 学習範囲内の質問への即時応答

  ③ 脱線検知（分類タスク）

  ④ 目標設定チャット
     - ユーザーとの自然な対話

  ⑤ アセスメント中の個別回答評価
```

#### コスト最適化施策

| 施策 | 内容 | 効果 |
|------|------|------|
| Prompt Caching | システムプロンプトに`cache_control`設定 | Opus使用コスト最大90%削減 |
| モデル使い分け | Opus/Haikuの適切な切り替え | 平均コストをOpus単独比で約70%削減見込み |
| TTS音声キャッシュ | S3へPolly出力をキャッシュ・再利用 | Pollyコスト削減、応答速度向上 |
| Batch API活用 | アセスメント問題生成に非同期Batch API検討 | Opus利用コスト最大50%削減 |
| 会話履歴の圧縮 | 長期セッション時に古い履歴を要約して圧縮 | 入力トークン数の抑制 |

### 2.4 音声処理設計

#### テキスト→音声（TTS）：Amazon Polly

```
【TTSフロー】

フロントエンド
    │ テキスト送信（POST /tts）
    ▼
Lambda (ttsHandler)
    │
    ├─ S3キャッシュ確認（テキストのSHA256ハッシュをキー）
    │       ヒット ─────────────────────────┐
    │       ミス                            │
    ▼                                      │
Amazon Polly (Neural TTS)                  │
    │ MP3音声生成                           │
    ▼                                      │
S3 (tts-cache バケット)に保存              │
    │                                      │
    ▼                                      │
Presigned URL生成 ←─────────────────────────┘
    │
    ▼
フロントエンド（Audio要素で再生）

【設定】
・エンジン: neural（高品質）
・音声ID: Kazuya（男性・標準）/ Tomoko（女性）※ユーザー選択可
・形式: MP3、サンプルレート: 22050Hz
・キャッシュTTL: 30日（頻出フレーズを長期キャッシュ）
```

#### 音声→テキスト（STT）：Amazon Transcribe

```
【STTフロー】

ユーザーがマイクボタン押下
    │
    ▼
MediaRecorder API（ブラウザ標準）
    │ 音声データ収集（WebM/Opus形式）
    ▼
Lambda (sttHandler) ※Presigned URL経由でS3アップロード
    │
    ▼
Amazon Transcribe StartTranscriptionJob
    │ 非同期処理（数秒〜十数秒）
    ▼
転写結果をWebSocket or ポーリングで取得
    │
    ▼
フロントエンド（テキスト入力欄に表示・確認）
    │ ユーザーが内容確認後に送信
    ▼
通常のテキスト入力と同様に処理

【設定】
・言語: ja-JP（日本語）
・メディア形式: webm
・最大発話時間: 60秒
・自動句読点: 有効
```

### 2.5 セキュリティ設計

#### 認証・認可フロー

```
1. ユーザーがメール/パスワードでCognito認証
2. CognitoがJWT（ID Token + Access Token）を発行
3. フロントエンドがTokenをSecure httpOnly Cookie or Memory Storeに保管
4. API呼び出し時にAuthorizationヘッダにBearer Tokenを付与
5. API GatewayのLambda AuthorizerがJWTを検証
6. 検証成功後、Lambda関数にuserIdを渡す
7. Lambda内でDynamoDBアクセス時にuserIdの所有権を確認
```

#### APIキー管理

- Claude API KeyはAWS Secrets Managerに保管
- Lambda実行ロールにSecretsManagerReadWrite権限を付与
- Lambda起動時にSecrets Managerから動的取得（キャッシュ有り）
- 定期的なローテーション設定（90日）

#### データ保護

| データ種別 | 保護方法 |
|-----------|----------|
| DynamoDBデータ | AWS管理キーによる保存時暗号化 |
| S3データ | SSE-S3による保存時暗号化 |
| 通信経路 | TLS 1.3 (HTTPS全通信) |
| ユーザー音声データ | 処理後S3から自動削除（7日） |
| Claude APIへの送信 | 最小限の個人情報（userId以外は匿名） |

### 2.6 データフロー設計

#### 学習セッション中のデータフロー（ストリーミング）

```
【セッション中のリアルタイム応答フロー】

フロントエンド
  ① POST /sessions/{id}/messages
     Body: { userMessage: "...", stepId: "..." }
         │
         ▼
  Lambda (sessionResponder)
  ② DynamoDBから会話履歴取得

  フロントエンド
  ⑥ SpeechBubbleコンポーネントがテキストをリアルタイム表示

  ⑩ アバター状態を「話し中」→「待機中」に遷移
```

## 3. 機能要件定義

### 3.1 学習テーマ入力（F-001）

#### 機能概要

ユーザーが最初に学習したい内容をフリーテキストまたは音声で指定する。

#### 入力仕様

| 入力方法 | 詳細 |
|----------|------|
| テキスト入力 | 最小10文字〜最大500文字。Placeholderで入力例を提示 |
| 音声入力 | マイクボタン押下で録音開始、最大60秒。Transcribeで文字変換後、確認欄に表示してから送信 |

#### 入力例（プレースホルダー表示用）

- 「中学受験難関校レベルの確率・統計をマスターしたい」
- 「自動車免許（普通車AT）の筆記試験に1ヶ月で合格したい」
- 「TOEIC 800点を目指したい（現在600点レベル）」
- 「Pythonで機械学習の基礎を学びたい」

#### 送信後のAI処理

Claudeが以下を解析してJSON形式で返却：

```json
{
  "subject": "確率・統計",
  "context": "中学受験",
  "targetLevel": "難関校合格レベル",
  "clarificationQuestions": ["どの学校を想定していますか", "扱う範囲はどこまでですか"]
}
```

⚠️ **この段階で学習期間や学習時間を推定してはいけない。**
学習者の現在の理解度がまだ分からないため、ここで所要期間を示すのは根拠がなく、
誤った期待を与える。確認質問でも期間や学習時間は尋ねない。
「何を」「どこまで」を明確にする質問だけにする。
期間・ペースは理解度チェックのあとに学習者自身が選ぶ。

### 3.2 目標設定チャット（F-002）

#### チャットフロー状態機械

```
状態: INITIAL
  → AIが入力内容を解析したサマリーを提示
  → 確認が必要な項目をリストアップ

状態: CONFIRMING_LEVEL
  → 到達目標レベルの詳細確認
  → 例：「難関校とは具体的にどの学校を想定していますか？」

状態: CONFIRMING_SCOPE
  → 扱う範囲の確認
  → 例：「和食だけですか、洋食も含めますか？」

  ⚠️ 学習期間・週当たり学習時間はここでは尋ねない。
     現在の理解度が分からない段階では判断できないため。
     学習者から尋ねられた場合は「まず理解度チェックで今の力を測ってから、
     具体的な計画を立てます」と伝える。
  ⚠️ 現在の理解度・経験の有無も尋ねない。このあとの理解度チェックで実測する。
     自己申告させても測り直すので意味がない。

状態: GOAL_SUMMARY
  → 合意した目標のサマリーを表示
  → 「この内容で進める」または「変更する」を選択

状態: AGREED
  → アセスメントフェーズへ遷移
```

#### 脱線防止機構（目標設定フェーズ）

Claude Haiku 4.5のシステムプロンプトに以下を設定：

```
あなたは優しい個別指導の先生です。
現在のタスクは「学習目標の設定」のみです。
ユーザーが学習と無関係な話題を持ち出した場合、
「それについては学習が始まってから話しましょう！
まずは目標を決めましょう」と優しく誘導してください。
```

### 3.3 アセスメント機能（F-003）

#### 問題生成仕様（Claude Opus 4.8）

| 項目 | 仕様 |
|------|------|
| 問題数 | 可変（後述）。AI がテーマの広さ・深さに応じて決める |
| 難易度分布 | 比率で指定（易 30% / 中 50% / 難 20%）。出題順は易 → 中 → 難 |
| 問題タイプ | 比率で指定（選択式 75% / 記述式 20% / 自由記述 1〜2問） |
| 生成タイミング | 学習者が深さを選んだ直後に一括生成（API 呼び出し1回） |
| 生成方式 | 非同期。starter が 202 を返し、ワーカーが生成する |
| 問題形式 | テキスト主体。画像が有効な場合はS3上のプリセット問題画像を参照 |

**問題数を固定しない理由**

狭いテーマに20問は冗長で、広いテーマには20問では足りない。
テーマの広さ・深さに見合う数を AI が決め、その理由を `countRationale` に
書かせて学習者に示す。

**測る深さ（学習者が選ぶ）**

理解度チェックを始める前に、どこまで細かく測るかを選べる。

⚠️ **学習の深さ（6.1 の goals テーブル参照）とは意味が違う。**
名前もラベル（軽め / 普通 / しっかり）も同じだが、指すものが別である。

| | 学習の深さ | 測る深さ |
|---|---|---|
| 何が変わるか | 学ぶセッション数 | 出題数 |
| 浅くすると | 学べる内容が減る | **診断の精度が落ち、後続すべての質が下がる** |
| 既定 | 普通 | **しっかり** |
| いつ選ぶか | 診断レポートを見たあと | 理解度チェックを始める前 |

測る深さを浅くすると、弱点分野とスコアの精度が落ちる。
これらは学習計画（必要セッション数の見積もり）と学習プログラムの生成の
両方が入力として使うため、影響が下流すべてに及ぶ。
学習の深さのように「選んだぶんだけ減る」で閉じない。

```
出題数の範囲 = 「しっかり測る場合」の範囲（10〜30問） × 深さの係数
```

| 深さ | 係数 | 出題数の範囲 |
|------|------|------------|
| しっかり（既定・推奨） | 1.0 | 10〜30問 |
| 普通 | 0.7 | 10〜21問 |
| 軽め | 0.5 | 10〜15問 |

- 係数はすべて 1.0 以下。上限は「しっかり測る場合」の値であり、
  深さはそこから削る方向にしか働かない（学習の深さと同じ考え方）
- ⚠️ **下限の10問は深さに関わらず維持する。** 半分にすると軽めが5問になるが、
  それでは分野別スコアが出せず、弱点の特定が当てずっぽうになる。
  診断として成立しない測り方は選ばせない
- ⚠️ **既定は「しっかり」。** 指定が無い場合も deep で扱う。
  浅く測ると診断の精度が落ち、その結果から作る学習計画と学習プログラムの
  質まで下がる。指定が無いのは「選ばなかった」ということなので、
  こちらの都合で精度を削る方向へ倒さない
- 画面では「しっかり」を推奨として示し、浅い方を選んだときだけ
  何を失うのか（弱点の特定が粗くなる）を出す

**⚠️ 深さの適用方法**

深さを反映した範囲そのものをプロンプトへ渡す。
「しっかりの数を決めてから半分にせよ」のような計算をモデルにさせない。
指示どおり割ってくれる保証が無いうえ、生成後に数を合わせようとすると、
出題順が易 → 難なので**後ろを削って難問だけが消え**、到達している上限が
測れなくなる。

範囲は1か所（`questionRangeFor`）で求め、プロンプトと生成後の件数検証の
両方で使う。別々に書くと「指示どおり作ったのに検証で落ちる」状態になる。

なお Structured Outputs は JSON Schema の `minItems` / `maxItems` を
サポートしないため、件数はスキーマで強制できない。プロンプトでの指示と
生成後の検証の2つで担保する。

#### 回答評価仕様（Claude Haiku 4.5）

- 選択式：正解/不正解の即時判定（DB照合）
- 記述式：Claude Haiku 4.5が模範解答と比較し部分点を算出
- 各問にかかる評価時間：1秒以内（Haiku使用）
- アセスメント中はユーザーに正誤をフィードバックしない（結果への偏りを防ぐ）

| 学習スタイル推定 | 回答パターンから「計算は得意だが概念理解が弱い」等を推定 |

### 3.5 学習プログラム生成（F-005）

#### プログラム構造（階層）

```
LearningProgram（学習プログラム全体）
  └─ Phase（フェーズ：大きな学習段階）
       ├─ Phase 1: 基礎固め（2週間）
       ├─ Phase 2: 応用力強化（3週間）
       └─ Phase 3: 実践・演習（2週間）
            └─ Unit（ユニット：テーマ単位の学習）
                 ├─ Unit 1-1: 確率の基礎概念（3セッション）
                 └─ Unit 1-2: 場合の数（4セッション）
                      └─ Session（セッション：1回の学習単位、20〜30分）
                           ├─ Step 1: 概念説明
                           ├─ Step 2: 例題解説
                           ├─ Step 3: 練習問題 × 3
                           └─ Step 4: まとめ・次回予告
```

#### 生成プロンプト設計方針

Claude Opus 4.8への入力：
- ユーザーの学習目標（合意済み）
- 診断レポート全文（強み・弱みの詳細）
- 学習期間（学習者が選んだ週数）
- **セッション総数（`totalSessions`）**
- 学習計画で出したセッションの題名一覧（`sessionOutline`・内容の下敷き）
- 出力フォーマット（JSON Schema）

⚠️ セッション総数は「目安」ではなく**仕様**として渡す。学習者が選んだ深さが
そのままこの数になっているため、モデルが自分の判断で増減してよいものではない。
生成結果が指定から 15% 以上外れたら作り直す。

以前はここを「目安」とし、しかも外れても非 critical（警告ログのみ）だったため、
実際のセッション数は事実上モデル任せだった。その状態では学習者が深さを選んでも
結果が変わらないことがありうる。

ただし作り直しても合わなかった場合は、そのまま使わせる。数が合わないことを
理由に学習者へプログラムを1つも渡さないのは行き過ぎであるため。

生成物：全フェーズ・ユニット・セッション構成のJSON（約5,000〜10,000トークン規模）

### 3.6 自由質問機能（F-007）

```typescript
      <Lottie
        ref={lottieRef}
```

### 5.3 SpeechBubble コンポーネント

#### 概要

AIが生成したメッセージをタイピングアニメーションで表示し、Claude APIのServer-Sent Eventsストリーミングに対応する。

#### Props定義

#### ストリーミング対応実装概要

```typescript
const SpeechBubble: React.FC<SpeechBubbleProps> = ({
  isStreaming, content, typingSpeed = 30, position = 'right', onReadingComplete
}) => {
  const [displayedText, setDisplayedText] = useState('')
  const [pendingTTS, setPendingTTS] = useState('')
  const prevContentRef = useRef('')

  useEffect(() => {
    if (isStreaming) {
      // ストリーミング: contentの差分を即時表示
      setDisplayedText(content)

      // 文末文字（。！？）を検出したらPendingTTSに追加
      const newPart = content.slice(prevContentRef.current.length)
      prevContentRef.current = content
      const sentences = newPart.match(/[^。！？]*[。！？]/g) || []
      if (sentences.length > 0) {
        setPendingTTS(prev => prev + sentences.join(''))
      }
    } else {
      // 非ストリーミング: タイピングアニメーション
      let i = 0
      const timer = setInterval(() => {
        setDisplayedText(content.slice(0, i + 1))
        i++
        if (i >= content.length) clearInterval(timer)
      }, typingSpeed)
      return () => clearInterval(timer)
    }
  }, [content, isStreaming])

  return (
    <div className={cn('speech-bubble', `speech-bubble--${position}`)}>
      <div className="speech-bubble__text">
        {displayedText}
        {isStreaming && <span className="speech-bubble__cursor">▌</span>}
      </div>
    </div>
  )
}
```

#### Amazon Transcribeとの連携フロー

```
1. ユーザーが録音ボタンを押す
2. navigator.mediaDevices.getUserMedia() でマイク権限取得
3. MediaRecorder APIで録音開始（MIME: audio/webm;codecs=opus）
4. 録音停止時にBlobデータを取得
5. Presigned URL取得API（GET /uploads/presigned-url）を呼び出し
6. S3にBlob直接アップロード（PUT）
7. Transcribe開始API（POST /transcribe）を呼び出し
8. ポーリングまたはWebSocketでジョブ完了を確認
9. 文字起こし結果をonTranscriptコールバックで返却
10. S3上の音声ファイルを削除（POST /uploads/cleanup）
```

| `any-learn-ai-micro-steps-{env}` | マイクロステップ（解説・Q&A・確認問題） | `sessionId` | `microStepId` | core |
| `any-learn-ai-micro-step-progress-{env}` | マイクロステップの進捗 | `userId` | `microStepId` | core |

`any-learn-ai-sessions-{env}` には GSI `userProgramId-startedAt-index`
（PK: `userProgramId`、SK: `startedAt`）がある。無いと、あるプログラムの
進捗を見るだけでそのユーザーの全セッションを読むことになる。
PK を `userId#programId` の合成にしているのは、`programId` 単独だと
ユーザー ID の条件を書き忘れた時点で他人のセッションが読めてしまうため。

**廃止したテーブル**

| 旧テーブル | 廃止理由 |
|-----------|---------|
| `users` | ユーザー属性は Cognito User Pool が持つ。DynamoDB に写しを作らない |
| `conversations` | 会話は学習セッションに紐づくため micro-steps 側へ移した（v1.1 追補） |
| `progress` | 進捗は保存せず、プログラム構造と完了セッションから毎回導出する（後述） |
| `deferred-questions` | 脱線した質問の持ち越しは micro-steps 側で扱う |

**進捗を保存しない理由**

同じ事実が2か所にあると、書き写しに失敗した時点で画面が嘘をつく。
実際に「学習を終えたのに達成率が 0% のまま」が起きた。
写しを持たなければ、ずれようがない。
達成率は「プログラム構造（core が持つ）× 完了セッション（core が持つ）」から
毎回計算する。

**学習量の決め方（重要）**

セッション数を決めるのは **深さだけ** である。

```
必要セッション数（AI が題材と診断結果から算出）
  × 深さの係数（軽め 0.5 / 普通 0.7 / しっかり 1.0）
  = totalSessions（実施するセッション数）
```

- 深さの係数はすべて 1.0 以下。AI が出すのは「しっかりやる場合に必要な一式」
  であり、それを超える増量は定義上ありえない。深さは「その一式からどこまで
  削るか」を選ぶもの。この前提は計画プロンプトと対になっており、AI に
  「必要最小限」を出させると普通・軽めが最小限を下回って目標に届かなくなる
- **`durationWeeks` は学習量に影響しない**。期間を短くしても学ぶ内容は減らず、
  1日あたりの負荷が上がるだけ。期間でも量が変わると、深さと期間のどちらが
  効いたのか説明できなくなる
- `sessionMinutes` は定数（20 分）。学習者の集中力の話であって題材の話ではない

**予定日は保存しない**

各セッションの実施予定日は `startDate` / `studyDays` / `durationWeeks` と
セッションの並びから毎回導出する（進捗を保存しないのと同じ方針）。
保存すると、学習プログラムを作り直したときに古い日付が残る。

⚠️ `weeklyStudyHours`（週当たり学習時間）は入力項目として**廃止済み**。
廃止前に作られたレコードにのみ存在し、その場合だけ `totalSessions` を
旧式（期間 × 週当たり時間 × 60 ÷ 1回の分数 × 0.8）で補う。
旧式には「何に対する8割か説明できない係数」と、1回の分数を週当たり時間から
逆算していたために「週 1.25〜2.5 時間では何時間と申告しても同じセッション数に
なる」という既知の問題がある。新しい計画でこの経路を通ってはいけない。


#### 進捗の扱い（テーブルを持たない）

- 学習プログラムの構造（`any-learn-ai-programs-{env}`）

返す内容は、完了セッション ID の一覧、現在地（フェーズ・単元・セッション）、
最終学習日時、総学習時間、フェーズごとの達成率。

⚠️ 「まだ終えていない最初のセッション」を現在地とする。
プログラムに存在しないセッション ID は数に入れない（分母と分子がずれるため）。

#### POST /goals/{goalId}/plan/estimate — 必要な学習回数の見積もり

学習者が深さ・期間・曜日を選ぶ**前**に、必要なセッション数を先に算出させる。

**なぜ確定前に走らせられるのか**

計画 AI の入力は学習テーマ・到達目標・診断結果だけで、学習者の選択に
依存しない。そのため選択の前に計算できる。

⚠️ この性質は意図して作ったもので、計画プロンプトに深さや期間を足すと
失われる。足すときは、この節と選択画面の作りを一緒に見直すこと。

**なぜ必要なのか**

選択画面で「1日あたり何分になるか」をその場で出すため。

```
1日あたりの目安 = 実施セッション数 × 1回の分数 ÷ 学習日数
```

- 1回の分数 … 定数（20分）
- 学習日数 … 学習期間 × 選んだ曜日数
  （N 週間の窓には、どの曜日もちょうど N 回現れるため厳密に求まる）
- 実施セッション数 … **これだけが AI 次第**

つまり見積もりさえ先に済ませれば、残りは選択に応じてその場で計算できる。

**呼び出しのタイミング**

診断レポートの生成（1〜2分）と**並行して**走らせる。

見積もりに要るのは総合スコアと弱点/習得済み分野で、これらは回答から
機械的に出るため、レポート生成中の `GET /assessments/{id}/report` でも
すでに返っている（`report` 本文だけが null）。待つ必要があるのは AI の
所見だけなので、それを諦めて並行させる。順に走らせると、レポートを
読み終えた学習者が選択画面で見積もり（約16秒）を待つことになる。

なお assessments から core を呼ぶ形にはしない。統合で消した越境呼び出しを
復活させることになるうえ、両サービスを呼んでいるのはフロントなので、
起動タイミングを早めるだけで足りる。

**リクエスト:**
```json
{
  "diagnosticSummary": "場合の数の数え上げで重複を見落とす傾向がある。",
  "totalScore": 62,
  "weakTopics": ["条件付き確率"],
  "strongTopics": ["約数・倍数"]
}
```

所見（`diagnosticSummary`）は省略できる。サーバー側は空でも見積もれる。

**レスポンス（202 Accepted）:**
```json
{ "goalId": "goal_abc123", "estimateStatus": "estimating" }
```

算出は非同期。クライアントは `GET /goals/{goalId}` の `estimateStatus` が
`ready` / `failed` になるまでポーリングする。同じ目標に対して算出中・
算出済みなら、Claude を呼ばずにそのまま 202 を返す。

**`GET /goals/{goalId}` が返す見積もり関連の項目:**

| 項目 | 説明 |
|------|------|
| `estimateStatus` | `estimating` / `ready` / `failed` |
| `necessarySessions` | しっかりやる場合に必要なセッション数 |
| `sessionsByDepth` | 深さごとの実施セッション数（`{light, standard, deep}`） |

⚠️ `sessionsByDepth` を返すのは、**深さの係数をクライアントに複製させない
ため**。複製すると、片方だけ直したときに「選択画面に出した数と確定後の数が
違う」という壊れ方をする。

⚠️ 確定（`POST /goals/{goalId}/plan`）は、保存済みの見積もりを必ず優先する。
引き直すと AI の出力が毎回変わるため、選択画面に出した数とずれる。
見積もりが無い場合だけ、その場で計算してから進む。

⚠️ 見積もりの完了前に学習者が確定することがある（見積もりは約16秒かかる）。
その場合、遅れて届いた見積もりは保存しない（`totalSessions` が既にあれば
書かない）。上書きすると、深さの係数と辻褄の合わないレコードが残る。

#### POST /goals/{goalId}/plan — 学習計画の確定

理解度チェックが終わってから呼ぶ。学習者が決めるのは深さ・期間・曜日の3つだけ。

**リクエスト:**
```json
{
  "assessmentId": "asmnt_abc123",
  "depth": "standard",
  "durationWeeks": 8,
  "studyDays": [1, 3, 5],
  "diagnosticSummary": "場合の数の数え上げで重複を見落とす傾向がある。",
  "totalScore": 62,
  "weakTopics": ["条件付き確率"],
  "strongTopics": ["約数・倍数"]
}
```

| 項目 | 制約 |
|------|------|
| `depth` | `light` / `standard` / `deep` のいずれか |
| `durationWeeks` | 1〜104 の整数 |
| `studyDays` | 0（日）〜6（土）を1つ以上。重複は除去される |

- `studyDays` が空だと学習日が 0 日になり、1日あたりの目安が計算できず予定も
  立たないため 400 で弾く
- 学習開始日はサーバーが決める（`startDate` = 確定した日）。端末の時計を
  信じると、タイムゾーンや時刻ずれで予定が1日ずれる
- ⚠️ `weeklyStudyHours` は受け取らない。送られても無視する。
  深さ・期間・曜日と矛盾したときに、どちらを優先するか決められなくなるため

**レスポンス（202 Accepted）:**
```json
{ "goalId": "goal_abc123", "planStatus": "calculating" }
```

算出は非同期（Sonnet で数秒）。クライアントは `GET /goals/{goalId}` を
`planStatus` が `ready` / `failed` になるまでポーリングする。
確定すると続けて学習プログラムの生成が自動で始まる。

**確定後に `GET /goals/{goalId}` が返す予定（すべて導出値・保存していない）:**

| 項目 | 説明 |
|------|------|
| `totalSessions` | 実施セッション数 |
| `startDate` / `endDate` | 学習の開始日・最終予定日 |
| `dailyLoadMinutes` | 1日あたりの目安（分） |

各セッションの実施予定日は `GET /programs/{programId}` の `sessionSchedule`
（セッション ID → `YYYY-MM-DD`）で返す。目標一覧に含めていないのは、
セッション単位の予定日を出すにはプログラム本体（数百ステップの巨大 JSON）の
読み込みが必要になり、一覧の表示コストが跳ね上がるため。

```typescript
// sessionResponder Lambda実装概要
import { streamifyResponse, ResponseStream } from 'lambda-stream'
import Anthropic from '@anthropic-ai/sdk'

export const handler = streamifyResponse(async (event, responseStream) => {
  const client = new Anthropic({ apiKey: await getApiKey() })

  // HTTPメタデータを先に送信
  const metadata = { statusCode: 200, headers: { 'Content-Type': 'text/event-stream' } }
  responseStream.setContentType('application/vnd.awslambda.http-integration-response')
  responseStream.write(JSON.stringify(metadata))

  // Claude APIストリーミング呼び出し
  const stream = await client.messages.stream({
    model: 'claude-haiku-4-5',
    max_tokens: 1024,
    system: buildSystemPrompt(sessionContext),
    messages: buildMessages(conversationHistory, userMessage)
  })

  // チャンクをSSE形式でフロントへ転送
  for await (const chunk of stream) {
    if (chunk.type === 'content_block_delta') {
      const sseData = `data: ${JSON.stringify({
        type: 'text_delta',
        delta: chunk.delta.text
      })}\n\n`
      responseStream.write(sseData)
    }
  }

  // 完了シグナル
  responseStream.write(`data: ${JSON.stringify({ type: 'message_stop' })}\n\n`)
  responseStream.end()

  // 非同期でDynamoDBに会話履歴を保存（レスポンス後）
  await saveConversationHistory(sessionId, messages)
})
```

## 9. インフラ設計

### 9.1 AWS CDK構成概要

単一スタックではなく、リポジトリ＝サービス＝CDK スタックの構成を採る。
デプロイの単位を分けることで、片方の変更が他方を止めないようにする。

```
any-learn-ai-shared-infra/   # 共有 API Gateway・Cognito・鍵・使用量テーブル
any-learn-ai-core/           # 学習の中核（目標・計画・プログラム・学習ループ）
any-learn-ai-assessments/    # 理解度チェック
any-learn-ai-media/          # 音声合成・アップロード
any-learn-ai-frontend/       # Next.js（静的書き出し）+ CloudFront
any-learn-ai-cicd/           # GitHub OIDC デプロイロール
```

各サービスのスタックは共通の形を取る。

```
any-learn-ai-core/
├── bin/any-learn-ai-core.ts        # スタックの入口（env は環境変数から注入）
├── lib/
│   ├── config.ts                   # リソース名・環境設定・SSM パス規約
│   ├── core-stack.ts               # スタック本体
│   └── goals-resources.ts          # 目標・プログラム側のリソース定義
├── src/
│   ├── handlers/                   # API Gateway から呼ばれる Lambda
│   ├── workers/                    # 非同期で走る Lambda（29 秒制限の外）
│   ├── domain/                     # ドメインロジック（AWS に依存しない）
│   └── shared/                     # LLM 呼び出し・HTTP・使用量記録
└── test/
```

**共有 API Gateway の扱い**

API Gateway 本体は shared-infra が作り、各サービスは SSM から ID を読んで
自分の担当パスだけを追加する（`AWS::ApiGateway::RestApi` を自分では作らない）。

⚠️ リソースを追加しただけではステージに反映されない。CDK デプロイのあとに
`create-deployment` でステージを作り直す必要がある。これを忘れると、
ステージは古いスナップショットを配信し続け、**認証を通ったリクエストだけが
500 になる**（未認証のリクエストはオーソライザ止まりで 401 のままなので、
疎通確認をすり抜ける）。

## 1. 設計方針

### 1.1 基本コンセプト

実際の優秀な家庭教師が行う指導スタイルを忠実に再現する。

```
【良い個別指導の特徴】
  ✓ 一度に大量の情報を与えない
  ✓ 小さな単位で区切り、都度理解を確認する
  ✓ 疑問はその場で即座に解消する
  ✓ 理解の確認は「質問するだけ」でなく「問いを解かせる」
  ✓ 間違えたら責めず、別のアプローチで再挑戦させる
  ✓ 正解したら具体的に何が良かったかを伝える
```

### 1.2 マイクロサイクルの定義

**1マイクロサイクル = 1概念の解説 → 質問受付 → 確認問題**

このサイクルを最小単位として繰り返し積み上げることで学習を進める。

| 概念の例（確率の場合） | 1マイクロサイクルの対象 |
|---------------------|----------------------|
| 「確率の定義」を理解する | ✅ 1サイクル |
| 「余事象の公式」を理解する | ✅ 1サイクル |
| 「加法定理」を理解する | ✅ 1サイクル |
| 「確率の全単元」を理解する | ❌ 大きすぎる（複数サイクルに分割必須） |

### 1.3 設計上の重要原則

| 原則 | 詳細 |
|------|------|
| **解説の原子性** | 1マイクロサイクルで扱う概念は必ず1つ。複数概念の混在禁止 |
| **質問ファースト** | 確認問題の前に必ず質問受付フェーズを挟む |
| **強制前進禁止** | ユーザーが「分かった」と言うまで次に進まない |
| **失敗の安全性** | 確認問題の不正解は責めず、必ず別アプローチで再解説 |
| **コンテキスト保持** | 同一サイクル内の会話は全て記憶し、再解説に活かす |
| **脱線の適切な管理** | Q&Aフェーズ中の脱線質問は「あとで聞くリスト」へ |

```
      🌧️ 例：天気の問題
       「明日雨が降る確率は30%」← これが普通の確率
       「今、空が曇っているとわかった上で、
        明日雨が降る確率は？」← これが条件付き確率！
      ─────────────────────────────────────

      曇り空という「条件」がつくことで、確率が変わるのがポイントです。
      式で書くと：P(A|B) = P(A∩B) / P(B)
      と表せます。」

━━ ② 質問受付フェーズ ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
先生: 「ここまでどうですか？
       疑問に思ったことや、もう少し詳しく聞きたいことはありますか？」

      [❓ 質問があります]  [✅ 分かりました！]

─── ユーザーが「質問があります」を選択した場合 ───────────────────
ユーザー: 「P(A∩B)って何ですか？」

先生: 「良い質問です！
       A∩B（AとBの積事象）は、
       『AとBが両方同時に起きる』という出来事のことです。

       天気の例で言うと、
       ・A = 明日雨が降る
       ・B = 今日が曇りである
       ・A∩B = 今日が曇りで、かつ明日も雨が降る

       [ベン図アニメーション：AとBの重なり部分を強調表示]

       この重なった部分がA∩Bです。わかりましたか？」

先生: 「他に質問はありますか？」

ユーザー: 「大丈夫です！」
      → 確認問題フェーズへ進む

━━ ③ 確認問題フェーズ ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
先生: 「では、理解できているか確認しましょう！

       ─────────────────────────────────────
       ❓ 確認問題
       
       袋の中に赤玉3個・白玉2個・青玉1個が入っています。
       「1個取り出したら白玉だった」とわかっています。
       
       このとき、「取り出した玉が白玉である確率」を
       P(A|B)の形で表すとき、P(B)は何の確率ですか？
       ─────────────────────────────────────」

ユーザー: 「白玉を取り出す確率です」

━━ ④ 評価フェーズ ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
━━ ⑤ 正解フィードバック ━━━━━━━━━━━━━━━━━━━━━━━━━━━━
先生（🎉アニメーション）:
      「正解！完璧です！
       P(B)は「条件となる出来事の確率」、
       つまり今回は「白玉を取り出す確率（2/6）」です。
       
       条件付き確率の分母が何を表すか、
       しっかり理解できていますね！」

━━ ⑦ 次のステップへ ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
先生: 「素晴らしい！では次は、
       この公式を使って実際に計算してみましょう！」
       → 次のマイクロステップへ
```

### 3.1 マイクロサイクル状態定義


### 3.3 不正解回数による分岐

```
確認問題 不正解回数ごとの処理:

1回目不正解:
  → 別の具体例を使った再解説（同じ解説アプローチは使わない）
  → 再度質問受付 → 確認問題（別問題）

2回目不正解:
  → 概念をさらに細かいサブステップに分割して再解説
  → 「一緒に順番に考えてみましょう」という誘導型再解説
  → 再度質問受付 → 確認問題（さらに易しい問題）

3回目不正解:
  → ヒントあり確認問題に切り替え
  → ユーザーに「一旦次に進んで後で戻る」オプション提示
  → 「苦手マーク」として記録（後の学習プログラム調整に反映）

```

## 4. コンテンツ粒度設計

### 4.1 マイクロステップの構造

セッション内のステップを「マイクロステップ」という単位に分解する。

```
【Unit 2-3: 条件付き確率の応用】（セッション例）

  Micro-step 1: 条件付き確率の定義を理解する
    - 解説: 「条件付き確率とは何か」（テキスト + 天気の例）
    - 確認問題: 定義の言葉を問う問題

  Micro-step 2: P(A|B)の式の意味を理解する
    - 解説: 「式の分子・分母が何を意味するか」（ベン図アニメーション）
    - 確認問題: 式の各記号が何を表すかを問う問題

  Micro-step 3: 具体的な数値で式を使う
    - 解説: 「計算手順を例題で追う」（ステップバイステップ）
    - 確認問題: 数値を代入して計算する問題

  Micro-step 4: 文章題を式に変換する
    - 解説: 「文章のどの部分がA・B・A∩Bか見極める方法」
    - 確認問題: 文章題の各要素をA・B・A∩Bに分類する問題

  Micro-step 5: 応用問題を解く
    - 解説: 「複合的な条件付き確率の問題の解き方」
    - 確認問題: 実際の応用問題を解く

合計: 5マイクロステップ × 1サイクル = 1セッション（推定20〜30分）
```

### 4.2 マイクロステップ生成のルール

Claude Opus 4.8 が学習プログラム生成時に各マイクロステップを定義する際のルール：

| ルール | 詳細 |
|--------|------|
| 1ステップ1概念 | 1つのマイクロステップで扱うメインの学習目標は必ず1つ |
| 解説時間60〜90秒 | テキスト量は200〜400文字以内（読み上げ基準） |
| 依存関係の明示 | 前のステップを完了しないと次に進めないステップを明示 |
| 具体例必須 | 必ず1つ以上の具体的な例を含む |
| 視覚化要素の指定 | テキストのみ / 図が必要 / アニメーションが有効 を明示 |
| 再解説アプローチ予約 | 不正解時に使う「別の説明アプローチ」を事前に生成 |

### 4.3 マイクロステップのデータ構造

```typescript
interface MicroStep {
  microStepId: string               // "ms_001"
  sessionId: string
  order: number                     // セッション内の順番
  concept: string                   // 「条件付き確率の定義」

  // ── 解説コンテンツ ────────────────────────────────────────
  explanation: {
    primary: ExplanationContent     // メイン解説（初回）
    alternativeA: ExplanationContent // 再解説案A（1回目不正解時）
    alternativeB: ExplanationContent // 再解説案B（2回目不正解時）
  }

  // ── 確認問題 ──────────────────────────────────────────────
  quizQuestion: {
    primary: QuizQuestion           // メイン確認問題
    easyFallback: QuizQuestion      // 易しいバージョン（3回目用）
  }

  // ── メタ情報 ──────────────────────────────────────────────
  estimatedMinutes: number          // 推定所要時間（分）
  visualizationType: 'text' | 'image' | 'animation' | 'math'
  prerequisiteMicroStepIds: string[] // 依存する前のステップ
  topicTags: string[]               // タグ（「定義」「計算」「応用」等）
}

interface ExplanationContent {
  approach: string                  // 「比喩を使った説明」「具体例中心」
  contentItems: LearningContent[]   // ContentRendererへ渡すコンテンツ配列
  ttsScript: string                 // Polly読み上げ用スクリプト
}

interface QuizQuestion {
  type: 'shortAnswer' | 'multipleChoice' | 'calculation' | 'explanation'
  questionText: string
  hintText?: string                 // 3回目不正解時に表示するヒント
  rubric: string                    // 採点基準（Claude Haikuへの採点指示）
  sampleAnswer: string              // 模範回答（採点・フィードバック用）
}
```

## 5. 確認問題設計

### 5.1 確認問題の種別

| 種別 | 説明 | 適用場面 | 例 |
|------|------|---------|-----|
| `shortAnswer` | 短文回答（1〜3文） | 定義・概念の確認 | 「条件付き確率とは何か説明してください」 |
| `multipleChoice` | 4択選択式 | 用語の識別・理解確認 | 「P(A\|B)の分母は何を表すか？ A〜D」 |
| `calculation` | 数値計算（記述） | 公式の適用確認 | 「P(A\|B)を計算しなさい（数値問題）」 |
| `explanation` | 理由・プロセス説明 | 深い理解の確認 | 「なぜ分母がP(B)になるのか説明してください」 |

### 5.2 確認問題の設計原則

```
【良い確認問題の条件】
  ✓ 今解説した概念だけで解ける（新しい知識は不要）
  ✓ 記憶の確認ではなく「理解の確認」になっている
  ✓ 「丸暗記した」だけでは答えられない
  ✓ 正解/不正解が採点者によらず一意に判断できる
  ✓ ヒントなしで解けるが、ヒントがあれば難易度が適切に下がる

【悪い確認問題の例（禁止）】
  ✗ 「条件付き確率の式は何ですか？」（丸暗記で答えられる）
  ✗ アセスメントで出た問題と同じ問題
  ✗ 2つ以上の新概念を同時に必要とする問題
  ✗ 計算が複雑すぎて「式の理解」が測れない問題
```

### 5.3 採点基準設計（Claude Haiku 4.5 への採点指示）

各確認問題に `rubric`（採点基準）を付与し、Haikuが一貫した採点ができるようにする。

```typescript
// 採点プロンプト骨格
const QUIZ_EVALUATION_PROMPT = `
あなたは採点者です。以下の基準に従って厳密に採点してください。

【学習した概念】
${microStep.concept}

【確認問題】
${quizQuestion.questionText}

【模範回答】
${quizQuestion.sampleAnswer}

【採点基準（Rubric）】
${quizQuestion.rubric}

【ユーザーの回答】
${userAnswer}

以下のJSONのみを返答してください：
{
  "verdict": "correct" | "partial" | "incorrect",
  "score": 0.0〜1.0,
  "correctElements": ["正しく理解できている部分の説明"],
  "incorrectElements": ["誤っている・不足している部分の説明"],
  "feedbackMessage": "ユーザーへの具体的なフィードバック（200文字以内）",
  "misunderstoodConcept": "つまずきポイントのタグ（再解説選択に使用）"
}
`
```

### 5.4 部分正解の処理

```
部分正解（partial）の場合:
  ・正しい部分を明確に褒める
  ・不足・誤りの部分を具体的に指摘する
  ・scoreが0.7以上 → 「ほぼ正解」として次のステップへ進む
  ・scoreが0.7未満 → 不正解と同様に再解説フェーズへ
```

## 6. Q&A処理設計

### 6.1 Q&A質問タイプの分類

Haikuが質問を受け取ったとき、まず質問タイプを分類する。

```typescript
type QAQuestionType =
  | 'CONCEPT_CLARIFICATION'   // 「〜とはどういう意味ですか？」
  | 'EXAMPLE_REQUEST'         // 「別の例を見せてください」
  | 'PROCESS_QUESTION'        // 「なぜ〜になるんですか？」
  | 'CALCULATION_HELP'        // 「この計算合ってますか？」
  | 'SCOPE_ADJACENT'          // 関連するが今のステップ外の質問
  | 'OUT_OF_SCOPE'            // 全く関係ない質問（脱線）

// 各タイプに応じたHaikuへの回答指示
const QA_TYPE_INSTRUCTIONS: Record<QAQuestionType, string> = {
  CONCEPT_CLARIFICATION: '定義を別の言葉で言い換え、最小限の例を1つ添えて答える',
  EXAMPLE_REQUEST: '今の説明とは異なる具体例を1〜2個出す',
  PROCESS_QUESTION: 'なぜそうなるかの論理的な説明を、ステップバイステップで答える',
  CALCULATION_HELP: 'ユーザーの計算を引用しながら、どこが正しく/間違っているかを指摘する',
  SCOPE_ADJACENT: '簡潔に答えた上で「詳しくは後で学ぶよ」と伝える',
  OUT_OF_SCOPE: 'メモして学習に戻るよう誘導する（回答は提供しない）'
}
```

### 6.2 Q&A回答の長さ制限

AIの回答が長すぎると理解の妨げになる。Haiku へのトークン制限を設定する。

| 質問タイプ | 最大出力トークン | 理由 |
|-----------|----------------|------|
| CONCEPT_CLARIFICATION | 300 | 簡潔な言い換えで十分 |
| EXAMPLE_REQUEST | 400 | 例は1〜2個に絞る |
| PROCESS_QUESTION | 500 | 論理展開が必要なため少し長め |
| CALCULATION_HELP | 400 | 計算ステップを明示 |
| SCOPE_ADJACENT | 200 | 簡潔に答えて誘導 |

### 6.3 脱線検知詳細設計

```
【脱線検知の判定フロー】

① 質問テキストを受信
② Claude Haiku 4.5 で関連度スコア（0.0〜1.0）を算出
   ・現在のマイクロステップのconcept
   ・現在のセッションのtopicTags
   ・ユーザーの質問テキスト
   を入力として関連度を判定

③ 判定結果に応じた処理:
   ・0.85以上: 完全に関連 → 通常Q&A回答
   ・0.70〜0.84: 関連するが周辺 → SCOPE_ADJACENTとして回答
   ・0.50〜0.69: やや脱線 → 「今の話に少し関係しているね。
                               簡単に答えるけど、今は○○に集中しよう！」
   ・0.50未満: 完全に脱線 → 「おもしろい質問だね！
                               今は○○の学習中だから、
                               後で一緒に考えよう。メモしておくね！」

④ 脱線として処理した質問は `pendingQuestions` に保存
   （セッション完了後または次のセッション開始時に確認）
```

### 6.4 Q&Aループの終了条件

```
Q&Aループは以下のいずれかで終了する:

  ① ユーザーが「分かりました」「大丈夫です」「次に進みたい」
     等の意思表示をした場合（Haikuが意図を検出）
  
  ② ユーザーが「✅ わかりました！次へ」ボタンを押した場合
  
  ③ Q&A回数が5回を超えた場合
     → 「たくさん質問してくれてありがとう！
         では確認問題で理解を確かめましょう！」と自動誘導

  ④ 同じ質問（または非常に近い質問）が2回繰り返された場合
     → 理解が進んでいない可能性を検知
     → 「もしかして、まだ腑に落ちていないところがある？
         確認問題の前に、もう少し別の例で説明しようか？」と提案
```

## 7. 再解説設計

### 7.1 再解説アプローチの種類

不正解時に使う再解説は、最初の解説とは必ず異なるアプローチを使う。

```typescript
type ReExplanationApproach =
  | 'DIFFERENT_EXAMPLE'      // 別の具体例（日常生活の別シーン）
  | 'SIMPLER_ANALOGY'        // より身近な比喩・アナロジー
  | 'STEP_BY_STEP_BREAKDOWN' // さらに細かいサブステップに分解
  | 'VISUAL_FIRST'           // 図やアニメーションを先に見せる
  | 'COUNTER_EXAMPLE'        // 「〜でないケース」から理解させる
  | 'NUMERIC_FIRST'          // まず数字で具体的に計算させてから概念化
```

### 7.2 再解説アプローチの選択ロジック

```
【再解説アプローチ選択】

入力:
  - misunderstoodConcept: どこでつまずいたか（採点結果から）
  - attemptCount: 何回目の不正解か
  - previousApproach: すでに使ったアプローチ
  - visualizationType: 元の解説タイプ

選択ロジック:
  if (attemptCount === 1) {
    // 1回目: 誤解ポイントに応じたアプローチ選択
    if (misunderstoodConcept === '式の意味理解') → VISUAL_FIRST
    if (misunderstoodConcept === '具体化できない') → DIFFERENT_EXAMPLE
    if (misunderstoodConcept === '論理の流れ') → STEP_BY_STEP_BREAKDOWN
    else → SIMPLER_ANALOGY
  }
  if (attemptCount === 2) {
    // 2回目: 前回と異なるアプローチ + サブステップ分割
    → STEP_BY_STEP_BREAKDOWN（必ずサブ分割）
  }
  if (attemptCount >= 3) {
    // 3回目: ヒントあり問題 + 段階的誘導
    → NUMERIC_FIRST（数字から入って概念に戻る）
    + hintEnabled: true
  }
```

### 7.3 再解説の会話例

```
【1回目不正解後の再解説例（DIFFERENT_EXAMPLE アプローチ）】

先生: 「惜しかったです！少し角度を変えて考えてみましょう。

      今度はカードゲームで例えますね。

      ─────────────────────────────────────────
      🃏 トランプの例
      
      52枚のトランプから1枚引きます。
      
      ・普通の確率: ハートを引く確率 = 13/52
      ・条件付き確率:「赤いカードだった」とわかっている。
        その上で、ハートである確率は？= 13/26
      ─────────────────────────────────────────

      「赤いカード」という条件がつくと、
      分母が52から26に減りましたね。

      これが条件付き確率のポイントです。
      条件がつくと「確率の空間が絞り込まれる」んです！」

【2回目不正解後の再解説例（STEP_BY_STEP_BREAKDOWN アプローチ）】

先生: 「大丈夫！一緒に1ステップずつ確認しましょう。

      まず、『確率の空間』ってわかりますか？

      [sub-micro-step A: 確率の空間とは]
       → 確認: 「全事象とは何か？」の確認問題
       → 正解後に続く

      [sub-micro-step B: 条件をつけると空間が変わる]
       → 確認: 「条件後の全事象の例」の確認問題
       → 正解後に続く

      [sub-micro-step C: 式の分母は絞られた空間]
       → 確認: 「なぜ分母がP(B)なのか」の確認問題

      3つ全部理解できたら、元の問題に戻ってみよう！」
```

### 10.1 解説コンテンツ生成（Claude Haiku 4.5）

```

  当セッションに含まれる全マイクロステップの解説本文を事前生成
  （待ち時間なしでスムーズに進むよう、一括でプリフェッチ）

・再解説時（Haiku）:
  不正解の都度、リアルタイムで別アプローチの再解説を生成
```

```
│  ┌─────────────────────────────┐  ┌──────────────────────────┐  │
│  │  ✏️  他に質問を入力する    │  │  ✅  わかりました！      │  │
│  └─────────────────────────────┘  └──────────────────────────┘  │
└──────────────────────────────────────────────────────────────────┘
```

### 1.2 操作の流れ

```
【サジェスト質問をタップした場合】
  タップ → そのまま Q&A回答フェーズへ（入力欄のステップをスキップ）
  先生の回答が表示 → 「他に質問はありますか？」へ

    ※ タップした質問は「吹き出し（ユーザー側）」として
      チャット履歴に表示する（自分で入力したかのように見える）

【「他に質問を入力する」をタップした場合】
  → 従来どおり QA_INPUT 状態へ（テキスト/音声入力）

【「わかりました！」をタップした場合】
  → 確認問題フェーズへ（従来どおり）
```

### 1.3 フォローアップ時（QA_FOLLOWUP_PROMPT）の表示

Q&A回答後の「他に質問はありますか？」でも同様にサジェストを表示する。  
ただし **1回答えた質問は除外** し、残りのサジェストから表示する。

```
【QA_FOLLOWUP_PROMPT での表示（1問答えた後）】

  他に質問はありますか？

  ┌────────────────────────────────────────────────────────────┐
  │ ❓ なぜ分母が P(B) になるのですか？                       →│
  └────────────────────────────────────────────────────────────┘
  ┌────────────────────────────────────────────────────────────┐
  │ ❓ 別の例で説明してもらえますか？                         →│
  └────────────────────────────────────────────────────────────┘

  ┌──────────────────────────────┐  ┌──────────────────────────┐
  │  ✏️  他の質問を入力する     │  │  ✅  もう大丈夫！        │
  └──────────────────────────────┘  └──────────────────────────┘
```

### 1.4 再解説後の質問受付でのサジェスト

再解説後は元の3問ではなく、**つまずきポイントに特化した新しい3問**を生成して表示する。

```
【再解説後のサジェスト例（つまずき: 「条件事象の特定」の場合）】

  ┌────────────────────────────────────────────────────────────┐
  │ ❓ 「条件」と「求めたい事象」はどう区別するの？          →│
  └────────────────────────────────────────────────────────────┘
  ┌────────────────────────────────────────────────────────────┐
  │ ❓ B に当たるものを問題文から見つけるコツは？             →│
  └────────────────────────────────────────────────────────────┘
  ┌────────────────────────────────────────────────────────────┐
  │ ❓ もう一度最初の例で確認したい                           →│
  └────────────────────────────────────────────────────────────┘
```

## 2. サジェスト質問の生成設計

### 2.1 生成タイミング

**解説コンテンツ生成と同一 API 呼び出しで一括生成する。**  
別リクエストにすると「解説完了 → サジェスト待ち」という空白が生じるため、  
解説本文と同時に生成してフロントエンドにキャッシュしておく。

```
【生成タイミング図】

  セッション開始 or 次ステップ遷移
         ↓
  POST /micro-steps/{microStepId}/explanation
         ↓
  Claude Haiku 4.5 が1回のAPIコールで生成:
    ① 解説コンテンツ（contentItems, ttsScript）
    ② サジェスト質問3件（suggestedQuestions）   ← NEW
    ③ 再解説用サジェスト質問3件も事前生成しておく ← NEW
         ↓
  フロントエンドにキャッシュ
         ↓
  解説表示完了 → サジェストを即座に表示（待ち時間ゼロ）
```

### 2.2 サジェスト質問の設計原則

```
【良いサジェスト質問の条件】

  ✓ この概念を初めて聞いた人が本当に思うことを反映している
  ✓ 3問が互いに異なる「疑問の種類」をカバーする
  ✓ 短く自然な口語表現（「〜って何ですか？」「なぜ〜なの？」等）
  ✓ タップして回答が返ってきたとき、理解が深まる内容

【3問が担当する疑問カテゴリ】

  Q1: 用語・定義の確認
      例）「P(A∩B) って何ですか？」
          「○○という言葉の意味は？」

  Q2: 理由・仕組みの確認
      例）「なぜ分母が P(B) になるのですか？」
          「どうして○○になるの？」

  Q3: 例示・具体化の要求
      例）「別の例で説明してもらえますか？」
          「日常生活での例を教えて」

【禁止パターン】
  ✗ 「全部わかりません」のような広すぎる質問
  ✗ 確認問題で問われる内容そのまま（先に答えを教えてしまう）
  ✗ 次のマイクロステップの内容に踏み込む質問
  ✗ 3問が似たような質問の重複
```

### 2.3 カテゴリと質問テンプレート

Haikuがゼロから生成するが、内部的に以下の型を守って生成させる。

```typescript
type SuggestedQuestionCategory =
  | 'TERM_DEFINITION'       // 用語・定義の確認
  | 'REASON_MECHANISM'      // 理由・仕組みの確認
  | 'EXAMPLE_REQUEST'       // 例示・具体化の要求

interface SuggestedQuestion {
  category: SuggestedQuestionCategory
  text: string              // 実際に表示・送信される質問文（30文字以内）
  internalNote: string      // Haiku が回答を生成するときに使う補足（UI非表示）
}
```

## 3. 状態機械への変更（v1.1 差分）

```typescript
const QA_ANSWER_PROMPT = `
```

### 7.1 QAChoicePanel コンポーネント（更新）

v1.1 の `QAChoicePanelProps` を拡張する。

```typescript
  mode: 'initial' | 'followup'
  onHasQuestion: () => void          // 既存（「他に質問を入力」ボタン用）

  // ── NEW（v1.2 追加）──────────────────────────────────────────

  // ─────────────────────────────────────────────────────────────

```

**表示ロジック:**

```typescript
// QAChoicePanel 内部のレンダリングロジック
const QAChoicePanel = ({ mode, suggestedQuestions, onSuggestedQuestionTap, ... }) => {

  // すでにタップ済みのサジェストは除外して残りを表示
  const [usedCategories, setUsedCategories] = useState<Set<string>>(new Set())
  const visibleSuggestions = suggestedQuestions.filter(
    q => !usedCategories.has(q.category)
  )

  const handleSuggestedTap = (q: SuggestedQuestion) => {
    setUsedCategories(prev => new Set([...prev, q.category]))
    onSuggestedQuestionTap(q)
  }

  return (
    <div className="qa-choice-panel">
      <p className="qa-choice-panel__prompt">
        {mode === 'initial'
          ? 'よく聞かれる質問：'
          : '他に質問はありますか？'
        }
      </p>

      {/* サジェスト質問カード（残っているものだけ表示） */}
      <div className="qa-choice-panel__suggestions">
        {visibleSuggestions.map(q => (
          <button
            key={q.category}
            className="qa-suggestion-card"
            onClick={() => handleSuggestedTap(q)}
          >
            <span className="qa-suggestion-card__icon">❓</span>
            <span className="qa-suggestion-card__text">{q.text}</span>
            <span className="qa-suggestion-card__arrow">→</span>
          </button>
        ))}
      </div>

      {/* 自由入力 & わかった ボタン */}
      <div className="qa-choice-panel__actions">
        <button onClick={onHasQuestion}>
          ✏️ {mode === 'initial' ? '他に質問を入力する' : '他の質問を入力する'}
        </button>
        <button onClick={onUnderstood} className="primary">
          ✅ {mode === 'initial' ? 'わかりました！' : 'もう大丈夫！'}
        </button>
      </div>
    </div>
  )
}
```

## 1. ビジュアルテーマ設計

### 1.1 テーマコンセプト：「KNOWLEDGE QUEST」

学習を「壮大なRPGの冒険」に見立てる。  
知識の習得 = 新しい力を手に入れること。  
先生 = 頼れるメンター。ユーザー = 成長する勇者。

```
【世界観の対応表】

  学習テーマ        →   "クエスト"（冒険の目的地）

  ユニット          →   "ダンジョン"（探索場所）
  マイクロステップ  →   "エンカウンター"（バトル/謎解き）
  確認問題          →   "チャレンジ"（試練）
  正解              →   "スターゲット"（星を獲得）
  習熟度            →   "マスタリーゲージ"（熟練度）
  先生アバター      →   "メンターキャラクター"（導き手）
  診断レポート      →   "冒険者ステータス"
  学習プログラム    →   "クエストマップ"
```

### 1.2 ビジュアルスタイル

```

  ・回答がストリーミング表示（タイピングカーソル点滅）
```

```typescript

  origin?: { x: number; y: number }  // 発生源（デフォルト: 画面中央）

```

**実装方針（Canvas 2D）:**

```typescript
// パーティクルシステムはCanvas 2Dで描画（React外）
// Framer Motionや純CSSでは大量パーティクルのパフォーマンスが不十分なため

class Particle {
  x: number; y: number
  vx: number; vy: number
  alpha: number; scale: number
  color: string; shape: '★' | '✦' | '●'
  gravity: number; friction: number
}

class ParticleSystem {
  canvas: HTMLCanvasElement
  ctx: CanvasRenderingContext2D
  particles: Particle[] = []

  emit(type: ParticleType, origin: Point) {
    const configs = PARTICLE_CONFIGS[type]
    for (let i = 0; i < configs.count; i++) {
      this.particles.push(new Particle({
        x: origin.x,
        y: origin.y,
        vx: (Math.random() - 0.5) * configs.speed,
        vy: -(Math.random() * configs.speed * 1.5),
        color: configs.colors[Math.floor(Math.random() * configs.colors.length)],
        gravity: configs.gravity,
        ...
      }))
    }
  }

  animate() { /* requestAnimationFrame loop */ }
}
```

### 8.2 アニメーション実装の使い分け方針

| アニメーション種別 | 採用技術 | 理由 |
|-----------------|---------|------|
| パーティクル爆発 | Canvas 2D | 大量オブジェクトのパフォーマンス |
| ページ遷移 | Framer Motion (AnimatePresence) | Reactのマウント/アンマウント連携 |
| ボタン hover/active | CSS transition | シンプルで軽量 |
| XPバー伸び | Framer Motion (motion.div width) | 簡潔に書ける |
| レベルアップ演出 | GSAP Timeline | 複雑な連続制御が必要 |
| アバター | Lottie Web | 既存設計通り |
| チャート | Recharts + CSS animation | 既存設計通り |
| 吹き出しテキスト | CSS + JS timer | シンプルが最適 |
| 背景流れ星 | Canvas 2D requestAnimationFrame | パフォーマンス |

### 8.3 Framer Motion の主要パターン

```typescript
// 1. ページ遷移（AnimatePresence）
<AnimatePresence mode="wait">
  <motion.div
    key={currentPage}
    initial={{ opacity: 0, scale: 0.95 }}
    animate={{ opacity: 1, scale: 1 }}
    exit={{ opacity: 0, scale: 1.02 }}
    transition={{ duration: 0.25, ease: [0.25, 0.46, 0.45, 0.94] }}
  />
</AnimatePresence>

// 2. 正解フィードバック出現
<motion.div
  initial={{ opacity: 0, scale: 0.3, y: 20 }}
  animate={{ opacity: 1, scale: 1, y: 0 }}
  transition={{ type: 'spring', stiffness: 400, damping: 15 }}
/>

// 3. サジェストカードの stagger 出現
<motion.div
  variants={{
    hidden: {},
    visible: { transition: { staggerChildren: 0.07 } }
  }}
  initial="hidden"
  animate="visible"
>
  {suggestions.map(q => (
    <motion.div
      key={q.category}
      variants={{
        hidden: { opacity: 0, x: -20 },
        visible: { opacity: 1, x: 0, transition: { ease: 'easeOut' } }
      }}
    />
  ))}
</motion.div>

// 4. XPバー（useMotionValue + useSpring）
const xpMotion = useMotionValue(previousXP)
const xpSpring = useSpring(xpMotion, { stiffness: 120, damping: 20 })
useEffect(() => { xpMotion.set(currentXP) }, [currentXP])
<motion.div style={{ width: useTransform(xpSpring, [0, maxXP], ['0%', '100%']) }} />
```

## 9. パフォーマンスバジェット

### 9.1 レンダリング目標

| 指標 | 目標値 | 計測方法 |
|------|--------|---------|
| アニメーション FPS | 60fps（モバイル: 最低30fps） | DevTools Performance |
| First Contentful Paint | 1.5秒以内 | Lighthouse |
| Largest Contentful Paint | 2.5秒以内 | Lighthouse |
| Cumulative Layout Shift | 0.05以下 | Lighthouse |
| JS Bundle Size（gzip） | 350KB以下 | webpack-bundle-analyzer |

### 9.2 パフォーマンス最適化方針

```
【アニメーション】
  ✓ transform / opacity のみ変更（Layout, Paint を避ける）
  ✓ will-change: transform を常時適用しない（使う直前にのみ設定）
  ✓ パーティクルは Canvas 2D（DOM操作を避ける）
  ✓ Lottie アニメーションは表示中のみ再生（非表示時に停止）

【アセット】
  ✓ Lottie JSON は遅延ロード（セッション開始前にプリフェッチ）
  ✓ フォントは使用するウェイトのみロード
  ✓ BGM は必要になる直前にロード（Howler の preload: false）
  ✓ SE はアプリ起動時に全プリロード（ファイルサイズが小さいため）

【端末別の品質設定】
  ハイエンド機:  パーティクル80個・フルBGM・全エフェクト有効
  ミドルレンジ:  パーティクル40個・BGM有効・エフェクト簡略化
  ローエンド機:  パーティクル無効・BGM無効・CSS transitionのみ
  prefers-reduced-motion: アニメーション完全無効化（アクセシビリティ）

  → navigator.hardwareConcurrency / devicePixelRatio で自動判定
  → ユーザーが設定画面から手動切り替えも可能
```
