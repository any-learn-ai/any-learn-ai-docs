## 1. システムの目的

学習テーマを言うだけで、AI が理解度を測り、その人だけの学習プログラムを作って
最後まで伴走する。

```
① 学習テーマを言う（テキスト／音声）
      ↓
② 目標設定チャット — 到達レベルと範囲を AI と決める
      ↓
③ 理解度診断 — 深さを選び、10〜30問に答える
      ↓
④ 診断レポート — 得意・不得意の可視化
      ↓
⑤ 学習計画の確定 — 期間・曜日・1回の長さを選ぶ
      ↓
⑥ 学習プログラム生成 — フェーズ／単元／セッション／ステップ
      ↓
⑦ 学習セッション — マイクロサイクルを繰り返す
      ↓
⑧ 進捗の可視化
```

⚠️ **②で期間と学習時間を扱わない。**現在地が分からない段階では判断できないため、
診断（③）を経てから⑤で決める。

### 1.1 マイクロサイクル

学習の最小単位。1つの概念について、これを繰り返す。

```
解説を読む → 質問する（任意）→ 確認問題 → 採点
                                    ↓
                          正解 → 次のステップへ
                          不正解 → 再解説 → もう一度
```

1セッションに15前後のステップがあり、1人あたりの LLM 呼び出しは
**解説75回・確認問題75回・採点75回・Q&A20回**が目安になる。

## 2. サービス境界

### 2.1 何を別サービスにしたか

```
                        ┌──────────────────────┐
                        │   shared-infra       │
                        │  Cognito / API GW    │
                        │  WebSocket / 共有DB  │
                        └──────┬───────────────┘
                               │ SSM で公開
          ┌────────────────────┼────────────────────┐
          │                    │                    │
    ┌─────▼──────┐      ┌──────▼──────┐      ┌──────▼──────┐
    │   core     │      │ assessments │      │    media    │
    │ 目標・計画  │      │  診断・      │      │ アップロード │
    │ プログラム  │      │  レポート    │      └─────────────┘
    │ 学習・進捗  │      └──────┬──────┘
    └─────┬──────┘             │
          │  ①依頼（SQS）       │
          └──────────┬──────────┘
                     ▼
              ┌─────────────┐
              │     llm     │  ← LLM の鍵を持つ唯一のサービス
              │  生成の実行  │
              └──────┬──────┘
                     │ ②結果（EventBridge）
          ┌──────────┴──────────┐
          ▼                     ▼
    各サービスの後処理      WebSocket 通知係
```

| サービス | 責務 | 実際にデプロイされているか |
|---|---|---|
| `shared-infra` | Cognito、API Gateway 本体、WebSocket、共有テーブル、Secrets の箱 | ✅ |
| `core` | 目標・学習計画・プログラム・セッション・マイクロサイクル・進捗 | ✅ |
| `assessments` | 理解度診断と診断レポート | ✅ |
| `llm` | **LLM 呼び出しの一切**。モデル選択・品質検査・原価記録 | ✅ |
| `media` | ファイルアップロード | ✅ |
| `frontend` | Next.js 静的エクスポート + S3 + CloudFront | ✅ |
| `cicd` | GitHub OIDC のデプロイロール | ✅ |
| ~~`goals` / `learning` / `programs`~~ | **core へ統合済み。**リポジトリは残るがデプロイされていない | ❌ |

⚠️ **`goals` / `learning` / `programs` のコードを読まないこと。**
2026-08-02 で更新が止まっており、動いているのは `core` である。

### 2.2 なぜ LLM を別サービスにしたか

**費用ではない。方式を1つに保つためである。**

移設前、LLM の呼び出し口は3つのサービスに散っていた。結果として:

| 起きたこと | なぜ |
|---|---|
| モデル登録簿と単価表が2回ずれた | 別リポジトリにあり、片方だけ足せてしまった |
| assessments だけ Sonnet 固定だった | Anthropic 専用の実装しか持っていなかった |
| 「モデルを差し替えたのに効かない」 | 環境変数の受け渡しが4件抜けていた |

いずれも**同じ知識を複数の場所に持ったこと**が原因である。
鍵・登録簿・単価・品質検査を1か所へ集め、呼び出し元には
「SQS へ JSON を1件積む」だけを残した。

### 2.3 同期の入口を作らなかった

⚠️ **LLM 呼び出しは例外なくキューを通る。**同期版の口は無い。

理由:

- **契約が1つになる。**入口が2つあると、冪等性・再試行・エラー経路・流量制御を
  2通り作ることになり、片方だけ直す事故が必ず起きる
- **呼び出し元が待たなくなる。**同期だと、呼び出し元は応答を返す義務がある間ずっと
  動き続ける。実測ベースで100人あたり111円がその待ち時間ぶんの課金だった
- **流量制御が全経路に効く。**回数が多いのは対話系（全体の6割）で、
  ここが対象外だと背圧をかける意味が薄い

## 3. 非同期の骨格

### 3.1 3つの役

```
  受付 Lambda              llm consumer            後処理 Lambda
  512MB / 15秒             512MB / 10分            512MB / 30秒
  ┌──────────┐   SQS      ┌──────────┐  Event    ┌──────────┐
  │ 検証する  ├──────────►│ 生成する  ├─────────►│ 検査する  │
  │ 席を作る  │  (+DLQ)    │ 検証する  │  Bridge   │ 保存する  │
  │ 依頼を積む│            │ 記録する  │           └──────────┘
  └──────────┘            └──────────┘
```

⚠️ **待つのは consumer だけである。**

「非同期にしたから待ちが消えた」のではない。**待ちが6か所から1か所へ寄った。**
誰かがソケットを握る必要はあり、それを1つに集めて適切な大きさ（512MB）にした。

| | 移設前 | いま |
|---|---|---|
| LLM を待つ Lambda | 6個（1024〜3008MB） | **1個（512MB）** |
| 鍵を持つ Lambda | 6個 | **1個** |
| 対話系の受付 | 1024MB・60秒 | 512MB・15秒 |

### 3.2 待たなくてよいものは待たせない

⚠️ **全経路を非同期にしたが、全呼び出しを非同期にしたわけではない。**

| 場面 | どうするか | なぜ |
|---|---|---|
| 選択式の確認問題で正解 | **その場で 200** | 選択肢との一致で決まる |
| 「分からない」を選んだ | **その場で 200** | 0点で決まる |
| 確認問題の先読みが間に合った | **その場で 200** | すでに出来ている |
| それ以外 | 202 を返し、画面が待つ | 実際に生成が要る |

答えが決まっているものをキュー越しに待たせる理由が無い。

### 3.3 画面はどう待つか

**ポーリングと WebSocket を並べて使う。**

```
画面 ──GET──► サーバー        （3秒ごと。これだけでも動く）
  ▲
  └──「変わった」の合図──── WebSocket  （届けば即座に読み直す）
```

⚠️ **WebSocket が運ぶのは合図だけで、生成物は含まない。**

中身を送れば往復が1回減るが、同じデータに2つの経路ができる。届いた場合と
届かない場合で通る道が変わり、片方だけで再現する不具合になる。
実際に危ないのは、**ドメインの検査を通っていない値が WebSocket 経由で画面へ
入ること**である。

合図だけにすれば、画面が読むのは常に GET の1経路になる。

⚠️ **WebSocket が張れなくても学習は成立する。**企業プロキシなどで通らない環境が
あるので、接続に失敗したら黙って諦めてポーリングだけで待つ。

## 4. 貫いている設計判断

移設を通して繰り返し現れた判断を、ここにまとめる。
**個別の実装より、この考え方のほうが寿命が長い。**

### 4.1 持たせない

| 何を持たせなかったか | 代わりに | どこ |
|---|---|---|
| 呼び出し元に LLM のライブラリ | 依頼の形（小さくて安定した契約）だけ | 全サービス |
| 結果ハンドラに「積む」操作 | 受付が席を作り、結果は埋めるだけ | 対話系 |
| 通知に生成物 | 「変わった」という合図だけ | WebSocket |
| 読む側に単価表 | 単価を記録に残す | 原価計算 |
| 経路ごとの掃除係 | 読むときに猶予を見る | 状態の終端 |

⚠️ **同期を取る仕組みを作るより、同期を取る必要を無くすほうが強い。**

登録簿と単価表を「テストで一致を縛る」案は捨てた。
**ずれられる構造を残したまま見張るのは、解いたことにならない。**

### 4.2 状態は必ず終端させる

非同期にすると「結果が返ってこない」経路が必ず生まれる。

- LLM サービスが DLQ へ落ちた
- 結果イベントは出たが後処理が失敗した
- EventBridge のルールが壊れていた

どれも学習者から見ると同じで、**画面が「生成中」のまま止まる。**

| 手段 | 何を守るか |
|---|---|
| 失敗も成功と同じ経路で返す | 失敗の通知経路を別に作らない（作るとそこが次の穴） |
| DLQ + アラーム | 人を呼ぶ |
| 猶予（5分）を読むときに見る | 画面を必ず終端させる |
| 掃除係（プログラム生成のみ・30分） | レコード自体も終端させる |

### 4.3 検査は2段構え

| 誰が | 何を見るか |
|---|---|
| LLM サービス | **スキーマに合っているか。**合わなければ1回だけ作り直す |
| 呼び出し元の後処理 | **ドメインとして成立するか。**作り直さない |

⚠️ **ドメインの検査で作り直さない。**

実験（6題材×3回）で確かめた結果、**作り直しが走るのは作り直しても直らない場合
だけ**だった。作り直す価値のある不備は1件も出なかったので、ループを外した。

⚠️ **ドメインの検査は必須である。**既定モデルは OpenAI 互換の口を使っており、
スキーマを強制できない。選択肢が空の確認問題などが実際に返りうる。

### 4.4 学習者に見せる言葉を分ける

失敗の種類ではなく、**次に何をすればよいか**で分ける。

| 状況 | 学習者に勧めること |
|---|---|
| サーバーが失敗を記録した | もう一度作る |
| 状態を読めない | **作り直させない。**開き直す |
| 期限まで終わらない | 待つ（続いている） |

⚠️ これを1つに丸めると、**出来上がっているものを作り直させる**ことになる。
実際にその事故が起きた。

## 5. 技術スタック

| 層 | 採用 | 補足 |
|---|---|---|
| フロント | Next.js（静的エクスポート）+ S3 + CloudFront | サーバーサイドの中継点が無い |
| API | API Gateway REST + Lambda | **統合タイムアウト29秒は引き上げられない** |
| 通知 | API Gateway WebSocket | Cognito Authorizer 非対応（6章） |
| 認証 | Cognito ユーザープール（+ Google） | パスワード8文字以上・英大小数字 |
| データ | DynamoDB（オンデマンド） | 9テーブル |
| 非同期 | SQS（依頼）+ EventBridge（結果） | 順序不要・複数購読 |
| 実行環境 | Node.js 24 / ARM64 | 全 Lambda 共通 |
| IaC | AWS CDK（TypeScript） | リポジトリごとにスタック |

### 5.1 モデル

登録簿は6モデル。**用途ごとの既定は全11用途とも `gpt-5.6-luna`。**

| モデル | 用途 |
|---|---|
| `gpt-5.6-luna` | 全用途の既定 |
| `claude-sonnet-5` / `claude-haiku-4-5` / `claude-opus-5` | 登録済み。差し替え候補 |
| `qwen3.7-plus` / `qwen3.7-flash` | 同上 |

⚠️ **モデルを決めるのは LLM サービスだけ。**呼び出し元は用途しか渡さない。
指定できると登録簿に無い名前が入る経路ができ、単価表にも載らず原価が消える。

差し替えは SSM（`/any-learn-ai/{env}/model/{purpose}`）で行う。

## 6. 制約とその回避

実装で踏んだ、**設計に影響した制約**だけを挙げる。

| 制約 | 回避 |
|---|---|
| API Gateway REST の統合タイムアウトは29秒、引き上げ不可 | 全経路を非同期にした |
| WebSocket API は Cognito Authorizer 非対応 | 短命チケット + REQUEST Authorizer（下記） |
| WebSocket の認可は `$connect` でしか掛からない | 「誰の接続か」を接続時に確定し、接続テーブルで持ち回る |
| OpenAI 互換の口はスキーマを強制できない | 再帰的なスキーマ検証 + ドメイン検査 |
| DynamoDB の TTL は最大48時間遅れる | 期限の判定を TTL に任せず、消費側でも時刻を見る |
| 配列の中の状態は索引を張れない | 掃除係を作らず、読むときに猶予を見る |
| 静的エクスポートにサーバーサイドの中継点が無い | ブラウザから API Gateway へ直接つなぐ |

### 6.1 WebSocket の認証

⚠️ **ID トークンをクエリ文字列に載せる方式は採らない。**

クエリ文字列はアクセスログ・CloudWatch・ブラウザ履歴に残る。Cognito の
ID トークンは有効期限まで何度でも使えるので、漏れたときの影響が大きい。

```
① POST /ws-ticket（Cognito Authorizer 配下）で使い捨てチケットを取る
② wss://.../?ticket=... で接続
③ $connect の Authorizer がチケットを消費（条件付き削除）して userId を確定
④ 接続テーブルへ connectionId → userId を保存
```

- ログに残るのは**60秒で失効する1回きり**の文字列
- トークンの検証を自前で書かない（既存の Cognito Authorizer が守る）
- 再接続のたびに取り直す＝トークンの更新が自然に反映される

⚠️ **チケットは「消費」する。**読むだけだと、クエリ文字列に残った券を拾った誰かが
失効までの60秒のあいだ何度でも接続できる。

## 7. 非機能

| 項目 | 方針 | 実測・設定 |
|---|---|---|
| 応答（受付） | 学習者を待たせない | 受付は15秒以内、実際は数十ms |
| 応答（生成） | 待ち画面で実測から目安を出す | Q&A 5秒 / プログラム生成10秒 / 設問生成15秒 |
| 流量制御 | 消費側の同時実行数で絞る | prod 50 / stg 10 / dev 5（暫定） |
| 可用性 | 失敗しても学習を止めない | 通知・先読み・原価記録は失敗しても本体を止めない |
| 監視 | 溜まったら鳴らす | DLQ not-empty / 依頼の滞留（10分超） |
| コスト | 用途ごとにモデルを選べる | 単価は呼び出しの記録に残す |
| セキュリティ | 鍵を1か所に集める | LLM の鍵を持つのは llm のみ |

### 7.1 テスト

|---|---|
| core | 412 |
| frontend | 153 |
| llm | 75 |
| assessments | 74 |
| shared-infra | 37 |

⚠️ **テストの多くは「構造を縛る」ためにある。**
