## 1. ⚠️ 最初に決めること（あとで変えられない）

Cognito のユーザープールは、**作った後にスキーマを変更できない。**

```
Existing schema attributes cannot be modified or deleted
```

`update-user-pool` にスキーマを変える口が無く、⚠️ **追加はできるが、
変更と削除はできない。**間違えたら**プールごと作り直す**しかなく、
そのとき全員の `sub` が変わる。

### ⚠️ 作る前に必ず決める5つ

| # | 決めること | ⚠️ 間違えたときの代償 |
|---|---|---|
| 1 | `email` を **必須にしない**（`required: false`） | ⚠️ **外部 IdP の属性マッピングから email を外せなくなる**（3章）。プール作り直し |
| 2 | すべての標準属性を `mutable: true` にする | ⚠️ 外部 IdP の同期が失敗し、**認証ごと落ちる。**プール作り直し |
| 3 | `keepOriginal: { email: true }` を入れる | ⚠️ **打ち間違えた人がその場で締め出される**（2章） |
| 4 | 外部 IdP の email を **カスタム属性へ逃がす** | ⚠️ **利用者のアドレス変更が黙って巻き戻る**（3章） |
| 5 | 論理 ID に**版番号を付ける**（`UserPoolV1`） | ⚠️ 作り直すとき、論理 ID を変えないと**変更が黙って無視される** |

⚠️ **プールの設定と、クライアントの設定を混同しないこと。**
上の5つは**プール**の設定で、間違えると作り直しになる。
`preventUserExistenceErrors` などの**クライアント**の設定は、
`update-user-pool-client` でいつでも変えられる。

⚠️ **1 と 4 は対になっている。**`email` が必須だとマッピングを外せないので、
4 が実行できない。⚠️ **1 を忘れると 4 も失われる。**

### 実測（2026-08-19・使い捨てプール4つ）

| プール | ログイン方式 | `email` | マッピングを外せるか |
|---|---|---|---|
| A | `UsernameAttributes` | **必須** | ❌ |
| B | `AliasAttributes` | 任意 | ✅ |
| C | `UsernameAttributes` | 任意 | ✅ |
| D | `AliasAttributes` | **必須** | ❌ |

⚠️ **効いているのは `Required` だけ。**ログイン方式は関係ない。

⚠️ **私は最初これを「マッピングは外せない」と一般化して報告した。**
1つのプールで試しただけだった。⚠️ **使い捨てプールは数分で作れる。
一般化する前に、変数を分けて4つ作ること。**

## 2. ⚠️ メールアドレスの変更

### 決めること

```ts
keepOriginal: { email: true }   // ⚠️ 既定は false
```

これは `AttributesRequireVerificationBeforeUpdate: ['email']` になる。

### ⚠️ 無いとどうなるか

`signInAliases: { email: true }` のプールでは、**メールアドレスが
ログインの識別子そのもの**である。この設定が無いと、

1. 利用者が新しいアドレスを申請する
2. ⚠️ **その瞬間に識別子が新しいほうへ移る**
3. 確認コードは新しいアドレスへ飛ぶ
4. ⚠️ **打ち間違えていたら、古いアドレスでも入れず、コードも届かない**

⚠️ **取り返しがつかない。**

### 画面に必ず書くこと

- 「**コードを確認するまで、ログインは今までのアドレスのままです**」
- 「打ち間違えても、これまでどおりログインできます」
- 「このまま閉じれば、変更は行われません」

⚠️ **順番に注意。**アドレス変更の画面を作るより先に、この設定を入れること。
逆にすると、⚠️ **「入れなくなる」を防ぐために作った機能で、入れなくなる人を作る。**

### ⚠️ トークンは最大5分キャッシュされる

属性を変えた直後に表示を取り直すと、**古い値が出る。**

```ts
await fetchAuthSession({ forceRefresh: true });
```

⚠️ **これを忘れると「変えたのに反映されない」という問い合わせになり、
こちらで再現しない。**（実際にそうなった）

## 3. ⚠️ 外部 IdP の属性マッピング（最も高くついた場所）

### 結論

```ts
attributeMapping: {
  custom: {
    'custom:googleEmail': cognito.ProviderAttribute.GOOGLE_EMAIL,
    email_verified: cognito.ProviderAttribute.other('email_verified'),
  },
}
```

⚠️ **`email` にも `nickname` にもマッピングしない。**

### ⚠️ なぜか

外部 IdP でサインインする**たびに**、Cognito はマッピングした属性を
ユーザーへ同期する。⚠️ **利用者が変えたアドレスや表示名を、
IdP 側の値で上書きする。**

⚠️ **エラーは出ない。ログインも成功する。**
利用者からは「変えたはずなのに戻っている」としか見えない。

⚠️ **そして `PreSignUp` トリガーでは止められない。**
連携済みのアカウントのサインインでは、⚠️ **PreSignUp はそもそも呼ばれない**
（ログで確認済み）。

### 逃がした先は誰が読むのか

`custom:googleEmail` は `PreSignUp` が読む（新規登録時の紐づけ判断）。
⚠️ **消すと、外部 IdP の新規登録がすべて「新しいアカウント」になる。**
既にアカウントを持っている人に2つ目ができ、⚠️ **落ちないので気づけない。**

### 実測で確認した PreSignUp の中身

```json
{
  "triggerSource": "PreSignUp_ExternalProvider",
  "userName": "Google_117837252700134746143",
  "userAttributes": {
    "email_verified": "true",
    "custom:googleEmail": "（Google のアドレス）"
  }
}
```

⚠️ **`email` は入らない。**紐づけに必要な情報は失われない。

## 4. ⚠️ 「外部 IdP を後から追加する」の設計（本題）

### ⚠️ ここで一度、完全に間違えた

「Google と連携する」ボタンを、**ログイン用の Google サインイン**にしていた。

```
利用者がログイン中に押す
  → Cognito ホスト UI へ飛ぶ
  → PreSignUp が「メールアドレスの一致」で紐づけ先を探す
  → ⚠️ アドレスが違えば、別アカウントができる
```

⚠️ **押した人のアカウントには、何も起きない。**
⚠️ **それでも私は「Google 連携の追加・削除は完了」と報告していた。**
同一アドレスの場合しか成立しない機能を、完了と呼んでいた。

### 標準とする形：**明示的な連携**

```
① 画面が IdP と直接やり取りし、ID トークンだけを受け取る
② ログイン中の本人として、自前の API へ送る
③ サーバーが ID トークンを検証する
④ ⚠️ アクセストークンの持ち主へ紐づける
```

⚠️ **連携先は「送ってきた人」で決まる。**メールアドレスは見ない。
だから ⚠️ **IdP 側のアドレスが違っても、意図したアカウントに足される。**

### ⚠️ 乗っ取りの経路は2方向ある。両方を別々に塞ぐ

| 方向 | 何が起きるか | 塞ぐもの |
|---|---|---|
| (a) **他人の IdP を自分のアカウントへ** | 相手のデータは取れない。⚠️ **だが相手が次にログインすると、こちらのアカウントに入る** | ⚠️ **`aud` の検証** |
| (b) **自分の IdP を他人のアカウントへ** | ⚠️ **即座に乗っ取り** | ⚠️ **宛先をアクセストークンからしか取らない** |

⚠️ **(b) を開けるのは簡単である。**「管理画面から直したい」などの理由で
**本文から宛先を読む改修**が入りやすい。⚠️ **どんな理由でも入れないこと。**

### ⚠️ 実装で必ず守る4つ

1. ⚠️ **宛先はオーソライザの claim からしか取らない。**本文の `userId` は無視する
2. ⚠️ **紐づけキーは IdP の `sub`。**メールアドレスは使わない
   （アドレスは変わりうる。変わった瞬間に別人になる）
3. ⚠️ **既に別の IdP が付いていたら、黙って差し替えない。**
   差し替えると前の IdP で入っていた人が締め出され、⚠️ **本人に自覚が無い**
4. ⚠️ **その IdP が他人に使われていたら、相手に手を出さない。**
   相手にはデータがある。⚠️ **どちらを残すかは本人が決める**

### ⚠️ 事前チェックは「案内」であって「保証」ではない

`ListUsers` で先に調べても、⚠️ **調べてから紐づけるまでに状況は変わる。**
⚠️ **最後の砦は IdP 側（Cognito）が返すエラーである。**

⚠️ **握りつぶして成功を返さないこと。**繋がっていないのに
「連携しました」と表示することになる。

## 5. ⚠️ ID トークンの検証（ここだけは手で書かない）

### 必ず検証するもの

| # | 何を | ⚠️ 抜けたときに起きること |
|---|---|---|
| ① | 署名（IdP の JWKS） | 誰でも好きな中身のトークンを作れる |
| ② | `alg` | ⚠️ `alg: none` / 公開鍵を鍵にした HS256 が通る |
| ③ | `iss` | 別の発行者を名乗れる |
| ④ | **`aud`** | ⚠️ **他のどのサイトの IdP ログインで得たトークンでも通る** |
| ⑤ | `exp` | 期限切れが通る |
| ⑥ | `email_verified` | 確認していないアドレスで紐づけられる |

⚠️ **④ が最も重い。**署名は本物なので、①②③⑤ は全部成功する。
⚠️ **`aud` を見て初めて「このアプリの画面で、この人が押した」と言える。**

### ⚠️ 自前で JWT を検証しないこと

`alg` の取り違えは古典的な穴で、手で書くと必ず踏む。
**検証はライブラリに任せる**（本プロジェクトは `aws-jwt-verify`）。

⚠️ **ただし「任せた」と「正しく渡した」は別である。**
`audience` を渡し忘れても、⚠️ **署名検証は成功する。成功するので気づかない。**

### ⚠️ `iss` は複数許可すること

Google は2通り発行する。

```
https://accounts.google.com   … いま Identity Services が出すのはこちら
accounts.google.com           … 歴史的な形
```

⚠️ **片方だけ許すと、相手の実装が変わった日に全員の連携が黙って失敗する。**

### `email_verified` は真偽値でも文字列でも来る

```ts
payload.email_verified === true || payload.email_verified === 'true'
```

⚠️ 緩めているのではなく、**形の差である。**

## 6. ⚠️⚠️ テストの書き方（この章がいちばん重要）

### ⚠️ 「拒まれた」を見るテストは、それだけでは何も保証しない

⚠️ **実際に起きたこと。**

ID トークン検証のテストを書き、⚠️ **「拒むべきもの」が全部緑になった。**
`aud` 偽装も `alg: none` も HS256 も、すべて拒まれていた。

⚠️ **JWKS のモックが効いていなかった。**本物の IdP へ通信しており、
本物の鍵にテスト用の `kid` が無いので、⚠️ **何を渡しても同じ理由で
落ちていただけ**だった。

⚠️ **検証を1つも確かめていないのに、確かめた気になっていた。**

気づけたのは「**通すべきもの**」だけが落ちて理由を追ったからで、
⚠️ **もし最初から全部緑だったら、そのまま出していた。**

### ⚠️ だから、この2つを必ず入れる

**① 「テストが何かを測っているか」を測る検査**

```ts
const mockJwksFetches = { count: 0 };
// …モックの中で count を増やす…

it('⚠️ 差し替えた JWKS を取りに来ている（本物ではない）', async () => {
  mockJwksFetches.count = 0;
  await verifyIdToken(validToken());
  expect(mockJwksFetches.count).toBeGreaterThan(0);
});
```

⚠️ **これが 0 なら、そのファイルは何も測っていない。**

**② 検証を1つずつ外して、落ちることを実測する**

⚠️ **通ったことではなく、壊したときに落ちることを見る。**
本プロジェクトでは以下を1つずつ外して確認した。

| 外したもの | 落ちたテスト |
|---|---|
| `aud` の検証 | 「aud が別のアプリのもの」 |
| `email_verified` の検査 | 2本 |
| `iss` の片方 | 「https 無しでも通る」 |
| 宛先をアクセストークンから取る | 「本文に userId を入れても繋がない」 |
| 検証失敗の握りつぶし | 「検証が落ちたら Cognito を呼ばない」 |

⚠️ **これをやらずに「テストがあります」と言わないこと。**

### ⚠️ モジュールのモックは「本物を残す」だけでは足りないことがある

```ts
// ⚠️ これは効かない場合がある
jest.mock('lib/http', () => ({
  ...jest.requireActual('lib/http'),
  fetch: myFetch,
}));
```

⚠️ `requireActual` が返す**本物のクラス**は、**本物の関数を掴んだまま**である。
被せた側には誰も来ない。⚠️ **呼び出し側のクラスごと差し替えること。**

### 番人テストは「数」ではなく「性質」で書く

⚠️ **失敗例:**

```ts
expect(policies).toHaveLength(1);   // ⚠️ 権限を1つ足すと落ちる
```

落ちること自体は正しいが、⚠️ **直すときに数字を書き換えるだけになる。**
番人が意味を失う。

⚠️ **こう書く:**

```ts
expect(policies.length).toBeGreaterThan(0);  // ⚠️ 0 は「消えた」であって「安全」ではない
for (const p of policies) {
  expect(resourceOf(p)).not.toBe('"*"');
  expect(resourceOf(p)).toContain('UserPool');
}
```

## 7. 設定値をどこから配るか

### ⚠️ 経路を増やさない

環境ごとに違う値は **GitHub Secrets / Variables が唯一の起点**である。
⚠️ **コードにも SSM にも書かない。`switch (env)` も同じ違反。**

そのうえで、⚠️ **画面へ配る経路は極力増やさない。**

```
⚠️ 避けたい: GitHub Secrets → SSM → ワークフロー → NEXT_PUBLIC_… → 画面
```

⚠️ **どこか1段が抜けてもビルドは通り、押した人だけが失敗する。**
（同じ形で一度やられた: Lambda に書き込み権限が無く、synth も型検査も
テストも通り、**押した人だけが AccessDenied** になった）

### 標準とする形

**秘密でない値（IdP の client ID など）は、認証済みの API から配る。**

```
GET /account/providers/{provider}  →  { clientId }
```

⚠️ **秘密ではない**（OAuth のリダイレクト URL に平文で載る）。
⚠️ **秘密のほう（client secret）は Lambda の外へ出さない。**

⚠️ **GET にも認証を掛ける。**掛けても誰も困らず、
「なぜここだけ素通しなのか」を次に読む人が考えずに済む。

## 8. ⚠️ 「死んだ判定」を残さない

### 実例

```ts
passwordless: /^google_/i.test(username)
```

外部 IdP 経由で作られたユーザー名が `Google_<sub>` だった頃の判定。
⚠️ **自前でアカウントを作る方式に変えた時点で、常に false になった。**

これに依存していたもの：

| 場所 | 何が起きていたか |
|---|---|
| 画面「ログイン方法」 | ⚠️ **パスワードを持たない人に「パスワード ／ Google」と表示** |
| 画面「解除できません」 | ⚠️ **誰にも出ていなかった** |
| サーバーの 409 | ⚠️ **誰も守っていなかった** |

⚠️ **働かない検査を残すと、「守られている」と読める。**

⚠️ **そして最悪なのは、私が「もう発生しない形」というコメントを
このフィールドに書き足しながら、それに依存する表示のほうを直さなかったこと。**

### 標準

1. ⚠️ **判定が死んだら、依存している場所を全部たどる**（画面・API・テスト）
2. ⚠️ **働かない検査は消す。**コメントで「もう効かない」と書いて残さない
3. ⚠️ **番人テストは「使っていないこと」ではなく「定義ごと消えたこと」を見る**

### ⚠️ 「戻ったときに気づくために残す」は成立しない

⚠️ **この文書を書いた時点で、私はまだ消していなかった。**
`passwordless` というフィールドを残し、こうコメントしていた。

> ⚠️ それでも判定を残すのは、**戻ったときに気づくため**である。

⚠️ **気づけない。**その値は表示にも使わず、記録にも出さず、
テストもしていなかった。⚠️ **誰も読まない値は、何にも気づかない。**

⚠️ **そして残っているかぎり、また誰かが表示に使う。**実際そうなった。

⚠️ **本当に検知したいなら、検知する仕組みを作ること。**
作らないなら消すこと。⚠️ **中間は無い。**

（この食い違いは、文書を書いたあとにコードと突き合わせて見つかった。
⚠️ **文書とコードは、書いた直後に必ず突き合わせること。**）

## 9. ⚠️ 分からないことを画面に書かない

Cognito は「**パスワードを持っているか**」をトークンに載せない。
⚠️ **サーバーに聞いても分からない**（`UserStatus` でも判別できない）。

⚠️ **だから推測して書かない。**

| 分かること | 書いてよい |
|---|---|
| 外部 IdP 連携の有無（`identities`） | ✅ |
| パスワードの有無 | ⚠️ **❌ 分からない** |
| 連携が無い＝パスワードがある | ✅ 論理的に確定する |

書き方の例：

- 連携あり → 「Google」＋「**パスワードを設定していれば**、そちらでも」
- 連携なし → 「メールアドレスとパスワード」

⚠️ **「どちらでもログインできます」と言い切らない。**

---

## 10. ⚠️ 締め出しの経路を必ず1本残す

⚠️ **どの機能を作るときも、最後にこれを確認する。**

> ⚠️ **この操作の後、利用者が入れなくなる道はあるか。**
> **あるなら、そこから戻る道はあるか。**

### 実例1: パスワード再設定の入口が無かった

Cognito 側の受け口は最初からあったのに、⚠️ **画面にリンクが無かった。**
⚠️ **忘れた人は永久に入れなかった。**

### 実例2: 連携解除

パスワードを持たない人が外部 IdP の連携を解除できてしまう。
⚠️ **止めるべきか？**

⚠️ **止めない。**メールアドレスが検証済みなら「パスワードをお忘れですか」
から設定できる。⚠️ **止めると、IdP 側のアカウントを失った人が
解除すらできなくなる。**

⚠️ **代わりに、画面にその道筋を書く。**

> パスワードをまだ設定していない場合は、解除後に
> ログイン画面の「パスワードをお忘れですか」から設定してください。

⚠️ **これを成立させるために、自前で作るアカウントは
`email_verified: true` で作ること。**false だと再設定が使えず、
本人がパスワードを持つ手段が無くなる。

## 11. ⚠️ 登録経路のトリガーは、絶対に例外を投げない

`PreSignUp` は登録そのものである。

⚠️ **どんな失敗の仕方をしても、例外を外へ出さないこと。**
補助的な処理（紐づけ・契約レコードの作成）が失敗しても、
⚠️ **登録できないほうが比べものにならないほど悪い。**

```ts
try { await 補助的な処理(); } catch (e) { console.warn(...); }
```

⚠️ **番人テストで「どこが失敗しても resolve すること」を見ること。**
（実際、素の `await` を1つ書いてしまい、番人が捕まえた）

## 12. デプロイ時の落とし穴

| 落とし穴 | ⚠️ 内容 |
|---|---|
| `cdk diff` の `[~]` | ⚠️ **「置き換えでない」と「取り消せる」は別。**属性の追加は不可逆で、同時に入れた変更が失敗すると**戻せないものだけが残る**（実際にスタックを `UPDATE_ROLLBACK_FAILED` にした） |
| 不可逆な変更 | ⚠️ **単独でデプロイする** |
| ドメイン接頭辞 | ⚠️ CloudFormation は**作成が削除より先。**dev でも衝突する |
| 手元からの `cdk deploy` | ⚠️ **禁止。**CI が渡す文脈が無く、IdP・メール・決済の配線が「不要」と判断されて消える |
| Authorizer の変更 | ⚠️ 追随しないスタックは**全 API が 401** |
| 静的書き出しの画面 | ⚠️ 再デプロイではなく**再ビルド**が要る |

## 13. ⚠️ 外部サービス側の手作業を、必ず洗い出す

コードだけでは完成しない。⚠️ **そして抜けても静かに失敗する。**

| 設定 | ⚠️ 抜けたときの症状 |
|---|---|
| 承認済みリダイレクト URI | IdP ログインが丸ごと失敗 |
| ⚠️ **承認済みの JavaScript 生成元** | ⚠️ **ボタンが黙って出ない。**リダイレクト URI とは**別の欄** |
| メール送信の本番承認 | サンドボックスのまま、⚠️ **未検証アドレスへ届かない** |

⚠️ **「コードを読んで動くはず」と判断しないこと。**
⚠️ **押して確かめるまで「完了」と報告しない。**

## 14. ⚠️ 実装前のチェックリスト

新しいサービスで認証を組むとき、⚠️ **上から順に潰す。**

### プールを作る前（あとで変えられない）

- [ ] `email` を `required: false` にした
- [ ] すべての標準属性が `mutable: true`
- [ ] `keepOriginal: { email: true }` を入れた
- [ ] 外部 IdP の email を受けるカスタム属性を作った
- [ ] 論理 ID に版番号を付けた

⚠️ **`preventUserExistenceErrors` はここではない。**
プールではなく**クライアント**の設定で、`update-user-pool-client` で
いつでも変えられる。⚠️ **不可逆の欄に混ぜると、次に読む人が
「これも間違えたら作り直し」と読む。**下の「実装中」に置いてある。

### 実装中

- [ ] `preventUserExistenceErrors: true`（⚠️ **クライアント側**の設定）
- [ ] ⚠️ 画面がログインの成否で**登録の有無を漏らしていない**
      （サーバーで伏せても、画面で「そのアドレスは未登録です」と
      出したら台無しになる）

- [ ] 外部 IdP のマッピングに `email` / `nickname` が**入っていない**
- [ ] 連携の宛先を**アクセストークンからしか取っていない**
- [ ] 紐づけキーが IdP の `sub`（メールアドレスではない）
- [ ] ID トークンの検証6項目（署名 / alg / iss / **aud** / exp / email_verified）
- [ ] `iss` を複数許可した
- [ ] 登録経路のトリガーが例外を投げない
- [ ] 自前で作るアカウントが `email_verified: true`
- [ ] 属性変更の直後に `forceRefresh` している

### テスト

- [ ] ⚠️ **モックへ到達したことを数で確認する検査がある**
- [ ] ⚠️ **検証を1つずつ外して、落ちることを実測した**

- [ ] やめられることを書いている
- [ ] ⚠️ **締め出される道と、そこから戻る道を確認した**

## 15. ⚠️ この設計に至るまでに間違えたこと

⚠️ **同じ道を通らないために残す。**すべて 2026-08-19 の1日で起きた。

| # | 間違い | ⚠️ 根本 |
|---|---|---|
| 1 | 「マッピングは外せない」と一般化 | ⚠️ 1つのプールで試して結論した。**使い捨てプールは数分で作れる** |
| 2 | `cdk diff` の `[~]` を「安全」と読んだ | ⚠️ **置き換えでない ≠ 取り消せる。**スタックを壊した |
| 3 | 「Google と連携する」が一度も動いていなかった | ⚠️ **押さずに「完了」と報告した。**同じ対処が `login()` には書いてあった |
| 4 | 「別のアカウントが作られます」を推論で断定 | ⚠️ 合っていたが**運**。指摘されて初めて実測した |
| 5 | 死んだ判定にコメントを足し、依存先を直さなかった | ⚠️ **数時間前の自分の書き込みの帰結を見落とした** |
| 6 | 効かない設定に「効く」と注釈した | ⚠️ 「効かない対策を増やすな」と書いた直後にやった |
| 7 | ⚠️ **緑なのに何も測っていないテスト** | ⚠️ **通ったことを結果と読んだ**（6章） |
| 8 | ⚠️ **他人のアカウントに無断でパスワードを設定** | ⚠️ 「dev だから」「失敗すれば状態は変わらない」で実行した。**失敗する前提で他人のものを触ったこと自体が誤り** |
| 9 | ⚠️ **この文書に、実装と矛盾することを書いた** | ⚠️ 「働かない検査は消す」と標準に書きながら、**そのフィールドを消していなかった。**突き合わせて発見 |

⚠️ **状態を変える操作は、必ず先に確認を取ること。**
