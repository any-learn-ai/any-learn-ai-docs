## 0. 検討メモからの訂正

メモは 2026-08-07 の検討時点で書かれたもので、当時の理解として自然なものが多い。
ここは「メモが雑だった」という話ではなく、**設計の根拠として使う前に確認した結果**である。

正確だったもの（確認済み）: 用途ごとの所要時間・呼び出し回数（1人262回）・単価・LLM を呼ぶ12ファイル・フロントの同期前提5か所（行番号を含め全て一致）。

### 訂正1の詳細 — 費用

dev の CloudWatch Logs（直近30日・全 LLM Lambda の `REPORT` 行）で、**実使用メモリは 115〜157MB**、割り当ては 1024〜3008MB だった。

| Lambda | 割り当て | 実使用（最大） |
|---|---|---|
| generate-program | 3008 MB | 143 MB |
| generate-assessment | 1769 MB | 154 MB |
| generate-report | 1769 MB | 153 MB |
| explanation-worker | 1536 MB | 150 MB |
| submit-answer | 1024 MB | 157 MB |

メモの「1〜3GB の Lambda がネットワーク待ちにフル課金」は正しい。
しかし**その待ち役を軽くするのに非同期化は要らない**。割り当てを下げれば済む。

同じ式で3構成を並べた（`any-learn-ai-core/tools/cost-model.ts` で再現できる。100人 × 1プログラム）。

| 構成 | Lambda | ポーリング | WebSocket | 合計 |
|---|---|---|---|---|
| **A** 現在 | 648円 | 50円 | — | **698円** |
| **B** メモリだけ 512MB へ | 241円 | 50円 | — | **291円** |
| **C** 非同期サービス化（B に配管を足す） | 261円 | 0円 | 8円 | **269円** |

- A の 698円はメモの 705円とほぼ一致する（＝モデルは妥当）
- **A → B: −407円（58%）。アーキテクチャ変更なし**
- **B → C: −22円（7%）。これが非同期化そのものの効果**

C が B より Lambda 費用で高いのは、非同期化しても**待ち時間が消えないから**である。
待つ主体が呼び出し元から LLM サービスへ移るだけで、秒数もメモリも同じ。
増えるのは振り分け・後処理・SQS・EventBridge の分だけになる。

### 訂正1の続き — では本当の金額はどこにあるか

メモ自身が「AI 呼び出しの原価は約 3,000〜4,000円」と書いている。Lambda の 698円はその2割弱にすぎない。

dev の `ai-usage` テーブルに記録された**実トークン数**で、assessments が Luna を呼べないことの影響を計算した。

| 用途 | 記録数 | 現在（Sonnet / Haiku） | Luna なら | 差（100人） |
|---|---|---|---|---|
| 設問生成 | 14 | 18.00円 | 1.44円 | **1,656円** |
| 診断レポート | 8 | 3.57円 | 0.27円 | 330円 |
| 採点（assessments） | 28 | 3.55円 | 0.76円 | 280円 |
| **合計（1人あたり）** | | **25.12円** | **2.46円** | **2,266円** |

**assessments を Luna へ移すだけで 100人あたり 2,266円下がる。Lambda 適正化（407円）の 5.6 倍、非同期化（22円）の 100 倍である。**

そしてこれは、メモが挙げた「きっかけ」そのもの
（`assessments/src/shared/claude.ts` が Anthropic 専用で OpenAI 互換プロバイダを持たない）だった。

### この設計書の立場

以上から、費用を根拠に非同期化を正当化することはできない。
**非同期化は費用ではなく、耐障害性・流量制御・鍵の隔離で正当化する**（1章）。
そのうえで、着手順序は金額の大きい順に組み替えることを推奨する（9章）。

なお、費用が小さいことは「やらない理由」にはならない。
月あたりの金額が小さくても、後から入れるほど作り直しが増える種類の変更である。

## 1. 何を解くのか

検討メモが挙げた4つの問題を、実測で重みづけし直す。

| 問題 | 実害（確認済み） | 金額 | 非同期化が要るか |
|---|---|---|---|
| LLM 層が core と assessments に重複 | assessments は Anthropic 専用のまま。Luna へ移せない | **2,266円/100人** | **不要**（共有ライブラリで解ける） |
| 登録簿と単価表が別ファイル | 2回ずれた（原価18倍表示、Opus 単価表示） | 誤った値付けの risk | 不要 |
| API キーの読み取り権が過剰 | core の5関数が LLM を呼ばないのに Secrets 読み取り権を持つ | 0円（セキュリティ） | 不要（CDK 既定値の1行） |
| 大きな Lambda がネットワーク待ちにフル課金 | 実使用 157MB に対し最大 3008MB | 407円/100人 | 不要（割り当て変更） |
| **失敗が黙って消える** | SQS も DLQ も無い。ワーカーは fire-and-forget | 復旧不能な学習体験 | **要る** |
| **流量制御ができない** | 1人262回。同時利用が増えるとプロバイダのレート制限に当たる | 障害 | **要る** |

**非同期サービス化でしか解けないのは下2つ**である。上4つはより安い手段がある。

### 非同期化が実際に効く2点

**(a) 失敗が黙って消える。**
現在、ワーカーは `InvocationType: 'Event'` の Lambda 呼び出しで起動される
（`core/src/shared/worker.ts:55-68`）。DLQ は3リポジトリのどこにも構成されていない
（`AWS::SQS::*` が synth 済みテンプレートで 0 件）。
`explanation-worker` だけ `retryAttempts: 0`（`core-stack.ts:356`）で、
**残りのワーカーは既定の2回リトライが効いている**。
つまり `generate-program` が例外で落ちると、Lambda が黙って2回作り直し、
Luna の課金が3回分発生する。ハンドラが失敗を握り潰す作り
（`generate-program.ts:150-166`）のおかげで通常は起きないが、
`failProgramGeneration` 自体が失敗すると起きる。

**(b) 流量制御ができない。**
1人あたり262回、100人同時なら瞬間的に数百の並列呼び出しが出る。
現在これを絞る手段はない（Lambda の予約済み同時実行数も設定していない）。
キューがあれば消費側の同時実行数で背圧をかけられる。

## 2. サービス境界

### 2.1 何をサービスにするか

**`any-learn-ai-llm` を「LLM 呼び出しサービス」にする。** 責務は次の4つだけ。

1. モデル登録簿（provider / tuning / dialect / 単価）を1か所で持つ
2. ベンダー方言の吸収（Anthropic / OpenAI 互換）
3. **スキーマ検証**（JSON として妥当か・スキーマに従っているか）と、そこだけの再試行
4. 使用量（トークン・所要時間）の記録

**持たせないもの**: ドメインの品質基準（締め文句・簡体字・セッション数・ステップ数）。
理由は3章で実測とともに示す。

### 2.2 ライブラリかサービスか

`any-learn-ai-llm` には既に**共有ライブラリ（npm パッケージ）としての実装が未コミットで存在する**。
`package.json` は `@any-learn-ai/llm` / GitHub Packages 公開の形になっている。

内容は core の `src/shared/llm/` を写したもので、**core より古い**。

| | 未コミットのライブラリ | core の現行 |
|---|---|---|
| モデル選択 | **SSM から取得**（デプロイ不要で変更可） | 環境変数（デプロイが要る） |
| Markdown / LaTeX | LaTeX の囲みを落とす（旧仕様） | 落とさない（KaTeX 導入後の現行） |
| `registeredModels()` | 無し | 有り（単価表との突き合わせに使用） |

**扱い**: SSM によるモデル選択という1点だけが core より進んでいる。
この差分だけを取り込み、**残りは core の現行版を正とする**。
古い `stripMarkdown` を復活させると、KaTeX で描画できるようになった数式を壊し続ける。

**結論**: 最終形はサービスだが、**中身は同じコードで、まずライブラリとして共有する段階を挟む**。
ライブラリ化は非同期化の前提であって競合ではない。同じ登録簿・同じ検査を
2つのリポジトリが別々に持ったまま非同期化すると、ずれる場所が増えるだけになる。

### 2.3 構成図（段階4b 完了時点）

```
  呼び出し元                   any-learn-ai-llm（サービス）
 （core / assessments）
   ┌──────────────┐            ┌──────────────────────────────┐
   │ 受付 Lambda   │  ①依頼    │  consumer Lambda 512MB       │
   │ 512MB / 15秒  ├──────────►│   ・SSM と登録簿でモデルを解決  │
   │  ・検証        │   SQS     │   ・プロバイダ呼び出し          │
   │  ・席を作る    │  (+DLQ)   │   ・スキーマ検証 + 1回だけ再生成 │
   │  ・依頼を積む  │            │   ・使用量と所要時間を記録      │
   └──────────────┘            └───────────┬──────────────────┘
                                            │ ②結果（成功も失敗も）
                                 EventBridge │
                    ┌───────────────────────┴───────────┐
                    │                                   │
   ┌────────────────▼─────────────┐      ┌──────────────▼──────────────┐
   │ 後処理 Lambda 512MB / 30秒     │      │ 通知係 Lambda 256MB / 15秒   │
   │ （呼び出し元が宛先ごとに持つ）  │      │ （llm が持つ）                │
   │  ・ドメイン検査                │      │  ・userId で接続を引く         │
   │  ・保存（4.2 の2方式）         │      │  ・「変わった」だけ送る         │
   └────────────────┬─────────────┘      └──────────────┬──────────────┘
                    │                                    │ WebSocket
                    │ DynamoDB                           ▼
                    ▼                              ┌───────────┐
              （画面が GET で読む）  ◄──────────────│  ブラウザ   │
                                     ポーリング／合図 └───────────┘
```

依頼は **SQS**（順序不要・耐久性あり・背圧をかけられる）、
結果は **EventBridge**（1つの結果を複数の購読者へ配れる）で返す。

⚠️ **検討時の図から変わった点。**

| 検討時 | いま | なぜ |
|---|---|---|
| 後処理が「不備なら再投入」 | **しない** | 論点1の実験で再生成ループを廃止（3.5） |
| 後処理が「WebSocket へ通知」 | **通知係が別にいる** | 全宛先を1つで拾う。宛先ごとに書くと足すたび直すことになる |
| 呼び出し元の Lambda を描いていない | 受付 512MB / 15秒 | 待つ役が居なくなったので小さくなった |

⚠️ **WebSocket が運ぶのは「変わった」という合図だけで、生成物は含まない。**
画面が読むのは常に GET の1経路になり、ポーリングと WebSocket が同じコードへ
収束する（段階4b）。

## 3. 論点1: 品質検査の再生成ループをどこに置くか

検討メモが「最大の争点」とし、**机上で決めずに1経路で実地に確かめること**と指定した論点。
プログラム生成の経路で実験した。

### 3.1 問いの立て直し

メモは「`generateStructured` の再生成ループが非同期境界をまたぐ」と書いている。
コードを読むと、**ループは2層あり、しかも検査している対象が重なっていない**。

| | 汎用層 `shared/llm/quality.ts` | ドメイン層 `domain/program-quality.ts` |
|---|---|---|
| 呼ばれる場所 | `generateStructured` の中 | `generate-program` ワーカーの中 |
| 検査の深さ | **スキーマ最上位の `required` のみ**（`title` / `totalWeeks` / `phases` の3つ） | 全階層（フェーズ数・単元・セッション数・ステップ数・`contentPrompt` の空） |
| その他の検査 | 簡体字、締め文句、Q&A の締め | セッション総数の許容幅（±15%） |
| 再生成 | 不備が1件でもあれば1回 | `critical` か `worthRetry` があれば1回 |

`inspect()` は `schema.required` を**再帰せずに**読む（`quality.ts:180-183`）。
`PROGRAM_SCHEMA` は各階層に `required` を持つ（`goal-prompts.ts:383, 388, 398, 409, 420`）が、
汎用層が見るのは最上位の3つだけ。**実質的な構造検査は全てドメイン層が担っている。**

2層が入れ子なので、最悪 **2 × 2 = 4 回** LLM を呼ぶ。これは誰も測っていなかった。

したがって問いは「ループをどこへ置くか」ではなく、次の3つになる。

- **(a)** 各層の検査は実際どのくらい発火するのか
- **(b)** 作り直すと本当に直るのか（直らないならループ自体が要らない）
- **(c)** 不備はスキーマから導けるものか、ドメイン知識か

### 3.2 実験の方法

`any-learn-ai-llm/tools/inspect-loop-probe.ts`（再現可能）。

- 本番と**同一**のシステムプロンプト・ユーザープロンプト・スキーマ・`maxTokens`・モデル（`gpt-5.6-luna`）・調整値（`effort: medium`）
- 6題材 × 3回 = 18回。セッション指定数を 4 / 6 / 12 / 18 / 24 / 30 と散らした
  （ドメイン層で唯一 `worthRetry` になるのがセッション総数のズレで、指定数に依存するため）
- **条件付きの再試行をしない。** 本番は1回目に不備があったときだけ2回目を回すので、
  失敗した生成の2回目しか観測できず (b) に答えられない。無条件に3回ずつ独立に生成し、
  「題材で決まっているのか／毎回の揺らぎなのか」を分ける
- 汎用層とドメイン層の判定を**別々に**記録する

18回・合計原価 21.73円・所要時間は中央値 34.5秒（最小 15.7 / 最大 48.1）。

### 3.3 結果

**(a) 発火率**

| | 発火 | 割合 |
|---|---|---|
| 汎用検査で不備あり | **0/18** | **0%** |
| ドメイン検査で不備あり | 4/18 | 22% |
| うち作り直しが走る | 3/18 | 17% |
| 学習者に出せない（致命） | 3/18 | 17% |

**汎用検査は一度も発火しなかった。** これは偶然ではなく構造的で、
汎用層が見るのは最上位の3項目（`title` / `totalWeeks` / `phases`）だけだからである。
この3つが欠けることは、JSON が返ってきている限りまず起きない。

**(b) 作り直しは効くのか**

| 題材 | 指定 | 生成されたセッション数（3回） | 作り直し判定 |
|---|---|---|---|
| 発酵food科学の基礎 | 12 | 12, 12, 12 | － － － |
| 会計の読み方（財務三表） | 24 | 24, 24, 24 | － － － |
| 古代ローマの都市と水道 | 6 | 6, 6, 6 | － － － |
| 統計的因果推論 | 30 | 30, 30, 30 | － － － |
| **能楽の見方** | **4** | 5, 4, 4 | **要 要 要** |
| 免疫学入門 | 18 | 18, 18, 18 | － － － |

不備は2種類にはっきり分かれた。

**① 揺らぎ（非致命）** — 会計の1回目だけ「ステップ数が指定（2〜5）から外れる」が24件出た。
2回目・3回目は0件。これは毎回の揺らぎだが、**`critical` でも `worthRetry` でもないので作り直しは走らない**。

**② 題材で決まっている（致命）** — 能楽は3回とも**同一の壊れ方**をした。

```
2回  フェーズN-単元N: sessions が空          [critical=true]
1回  フェーズN: durationWeeks が無い          [critical=false]
```

したがって **(b) の答えは「効かない」**。
`program-quality.ts` のコメントにある「作り直しても同じ確率で同じ違反が出る」は、
この経路では**そのとおり**だった。

さらに悪いことに、両者の関係は逆になっている。

> **作り直しが走るのは、作り直しても直らない場合だけだった。**
> 直る見込みのある揺らぎ（会計）は非致命なので作り直しが走らず、
> 作り直しが走る致命的な不備（能楽）は題材で決まっているので直らない。

現状のループは、能楽のような入力に対して **35秒と1回分の原価を捨ててから失敗する**。

**(c) 不備はスキーマから導けるか**

| | 割合 |
|---|---|
| スキーマ由来（`required` 欠落・JSON 不正） | **0/18（0%）** |
| ドメイン知識（ステップ数・セッション数・空の配列） | 4/18（22%） |

**実際に起きる不備は全てドメイン知識側だった。**

### 3.4 実験で見つかった不具合（設計とは別に要修正）

能楽の失敗は、モデルの品質ではなく**指示の矛盾**である。

- プロンプトとドメイン検査は**フェーズ3〜6個**を要求する（`program-quality.ts` の `PHASE_RANGE`）
- 同時に**セッション総数を4回**にせよと指定している
- 3〜6個のフェーズに単元をぶら下げ、そこへ4回を配ると、**必ず空の単元ができる**

そして `totalSessionsFor` の下限は **1** である（`study-schedule.ts:87`、
`Math.max(1, round(necessarySessions × 深さの係数))`）。
つまり**短い目標 × 軽めの深さで、この状態は実際に起こる**。
学習者から見ると「プログラムの作成に失敗しました」で終わる。

**フェーズ数の下限をセッション総数から導く**必要がある
（例: `min(3, ceil(totalSessions / 2))`）。これは非同期化とは独立に直せる。
段階0へ入れる。

### 3.5 決定

**汎用検査はサービスが持ち、ドメイン検査は呼び出し元が持つ。
そして呼び出し元に再生成ループは置かない。**

選択肢でいえば「2（検査は呼び出し側）」だが、
**メモが懸念した「往復が2倍・レイテンシ増」は発生しない。往復しないからである。**

| | どこ | 何を見るか | 不備のとき |
|---|---|---|---|
| **サービス** | `any-learn-ai-llm` | JSON として妥当か / 打ち切り / 拒否 / **スキーマに従っているか（再帰的に）** | **1回だけ再試行**。それでも駄目なら `status: 'failed'`, `kind: 'schema'` |
| **呼び出し元** | 後処理 Lambda | ドメイン規約（セッション数・ステップ数・空の配列・締め文句・簡体字） | **再生成しない。** 非致命は記録して通す。致命は即 `failed` |

根拠:

1. **サービス側の検査は「スキーマ」だけにできる。** 依頼には既にスキーマが入っている（8.1）。
   ドメイン知識を渡す必要がないので、汎用性を捨てずに済む（選択肢1・3の欠点が消える）
2. **ただし現状の汎用検査は弱すぎる。** 最上位の `required` しか見ておらず、発火率0%はそのため。
   OpenAI 互換プロバイダは `schemaEnforced: false`（`openai-provider.ts`）で
   スキーマを強制できないのに、検査も最上位止まりでは何も守っていない。
   **サービスへ移すのと同時に、再帰的なスキーマ検証へ強化する**。
   能楽の「`sessions` が空」は、`minItems` をスキーマに書けばここで拾える
3. **再生成ループは廃止する。** 実験が「作り直しが走るのは直らない場合だけ」を示した。
   35秒と原価を捨てる価値がない。**直す先はプロンプトと制約であって、ループではない**（3.4）
4. **汎用層にあるドメイン知識は呼び出し元へ移す。**
   `quality.ts` の `CLOSING_PHRASE`（「このポイントが大事です」）・
   `QA_CLOSING`（「これで分かりましたか？」）・簡体字の一覧・`RICH_TEXT_FIELDS` は、
   汎用の LLM サービスが持つべきものではない。解説と Q&A の後処理へ移す

### 3.6 この決定が他の経路へ与える影響

プログラム生成で測った結果なので、他経路へ広げる前に**同じ道具で測る**こと
（`inspect-loop-probe.ts` の `CASES` を差し替えれば使える）。

特に注意が要るのは次の2つ。

- **設問生成**（assessments）: `questions[]` に `choices` が入れ子になっており、
  core の登録簿コメントが名指しで危険視している形。しかも assessments には
  ドメイン検査が**現在ひとつも無い**。段階1で新設する（9章）
- **解説**（75回/人）: 唯一 `RICH_TEXT_FIELDS` と締め文句の検査が実際に効く経路。
  ここのドメイン知識を汎用層から剥がすときに、画面表示と対で確認すること

## 4. 論点2: 冪等性

### 4.1 現状の穴

SQS は at-least-once なので、後処理が2回走りうる。
現在の書き込みは**存在確認しかしていない**。

| 関数 | 場所 | 条件 |
|---|---|---|
| `completeProgramGeneration` | `core/src/domain/program.ts:183-219` | **条件なし** |
| `failProgramGeneration` | `core/src/domain/program.ts:225-250` | **条件なし** |
| `saveExplanation` | `core/src/domain/micro-step.ts:405-425` | `attribute_exists(microStepId)` |
| `saveGeneratedQuestions` | `assessments/src/domain/assessment.ts:568-594` | `attribute_exists(assessmentId)` |
| `saveEstimate` | `core/src/domain/goal.ts:538-547` | `attribute_exists(goalId)` |

`attribute_exists` は「レコードがあるか」しか見ない。**同じ後処理が2回走れば2回とも成功する。**

プログラム生成では実害が具体的である。`normalizePhases` が
進捗管理のキーになる ID を採番し直す（`generate-program.ts:143`）ため、
2回目の書き込みは**学習者が既に進めている進捗レコードの参照先を壊す**。

メモが参考として挙げた `saveEstimate` も
`ConditionExpression: 'attribute_exists(goalId) AND attribute_not_exists(totalSessions)'`
という形ではなく、実際は `attribute_exists(goalId)` だけだった（訂正）。
つまり**参考にできる既存実装は無い**。

### 4.2 方式は2つある（書き込みの形で決まる）

⚠️ **検討時は「条件付き書き込み」1つで済むと考えていた。段階4a で
足りないことが分かり、もう1つ足した。**

書き込みには2種類あり、危なさが違う。

| 書き込みの形 | 2回受けると | 使う方式 |
|---|---|---|
| 同じ値を**上書き**する | 何も変わらない | 状態遷移を条件にする（4.2.1） |
| 値を**積む**（list_append / ADD） | 二重に積まれる | 席を先に作って埋める（4.2.2） |

#### 4.2.1 上書きする書き込み: 状態遷移を条件にする

「まだ生成中であること」を条件に入れる。

```
ConditionExpression: 'attribute_exists(programId) AND #generationStatus = :generating'
ExpressionAttributeValues: { ':generating': 'generating' }
```

2回目は `ConditionalCheckFailedException` で弾かれる。
後処理はこの例外を**成功として扱う**（先に誰かが完了させた＝目的は達成
されている）。例外として扱うと EventBridge が再試行し続け、最後は DLQ へ落ちる。

これを選ぶ理由:

- 追加のテーブルが要らない（処理済み ID の記録簿を別に持たない）
- 「終端状態は一度だけ」というドメインの規則がそのまま条件式になる
- 失敗（`failed`）も同じ条件で守れる。成功のあとに遅れて届いた失敗通知で
  `failed` に落ちるのを防げる

実装: `any-learn-ai-core/src/domain/program.ts` の `completeProgramGeneration` /
`failProgramGeneration`。

#### 4.2.2 積む書き込み: 席を先に作り、結果は添字で埋める

⚠️ **段階4a で必要になった。対話系は積む書き込みばかりである。**

| 書き込み | 形 | 2回受けると |
|---|---|---|
| `appendQaTurn` | `list_append` | 同じ質問と回答が2回並ぶ |
| `appendQuizAttempt` | `list_append` | 挑戦記録が2件になる |
| `appendChatAndUpdate` | `list_append` | 同じ発言が2回会話に残る |
| `bumpProgress` | `ADD` | 不正解回数が2つ進む |

不正解回数が2つ進むと、再解説の切り口と次のヒントの有無がずれる。
学習者から見ると「1回しか間違えていないのにヒントが出た」になる。

**積む操作を受付（HTTP の同期処理）の中だけに置き、結果ハンドラは
添字を指定して埋める。**

```
受付   appendQaTurn(...) → 添字を返す。依頼の context に載せる
結果   completeQaTurn(sessionId, microStepId, index, answer)
       └ SET qaTurns[index].answer = :answer, qaTurns[index].#status = :ready
```

受付は再配信されないので積むのは1回きり、埋めるのは同じ値の上書きなので
何回でも同じ結果になる。**4.2.1 の形に還元される。**

⚠️ 数える処理（`bumpProgress` / `incrementQaCount`）も受付側へ移した。
数えるのは「質問したこと」「回答したこと」自体に対してで、
生成が返ったかどうかではない。

実装: `any-learn-ai-core/src/domain/micro-step.ts`（`appendQaTurn` / `completeQaTurn` /
`failQaTurn`、`appendQuizAttempt` / `completeQuizAttempt` / `failQuizAttempt`）、
`any-learn-ai-core/src/domain/session.ts`、`any-learn-ai-core/src/domain/goal.ts`（`completeChatReply`）。

#### 4.2.3 検討して捨てた案: 処理済み ID の集合

はじめは処理済みの `requestId` を DynamoDB の文字列集合で持ち、

```
ConditionExpression: 'NOT contains(processedRequests, :requestId)'
UpdateExpression:    'ADD processedRequests :processed'
```

で弾く形を書きかけた。条件と記録が1回の更新に収まるので隙間が無く、
A → B → A の順で届いても正しく動く。

**捨てた。**4.2.2 の形にすれば防壁そのものが要らない。
用意しかけた `core/src/domain/once.ts` は破棄した。

⚠️ 次に同じ問題へ当たったときのために書き残す。**まず「積む操作を
同期処理へ移せないか」を考えること。**移せるなら専用の仕組みは要らない。

#### 4.2.4 集計は読み直してから（assessments）

⚠️ **移設で新しく生まれた危険。**

診断の総合スコアは、移設前は受付が手元の設問一覧から計算して回答と
一緒に書いていた。採点が同期だったので、その一覧は常に最新だった。

非同期になると崩れる。学習者が続けて2問答えると採点が2つ並走し、
古いスナップショットで計算した総合スコアが新しいものを上書きしうる。
**1問ぶんの点が静かに消える。エラーは出ない。**

書き込みを2段に分けた。

- `saveAnswer` … 1問ぶんだけ書く（添字指定なので競合しない）
- `recomputeTotals` … 読み直して集計する。回答済みの数を条件に入れ、
  変わっていたら読み直す（3回まで）

回答自体は別の書き込みで確定しているので、やり直しても失われない。

実装: `any-learn-ai-assessments/src/domain/assessment.ts`。

### 4.3 使用量の記録は冪等にしない

記録は呼び出し1回につき1行を積む（`randomUUID` を鍵にする）。
**再試行のたびに新しい行が増える。**

これは**そのままでよい**。原価は「実際に課金された回数」を記録すべきで、
作り直した2回目も本当に課金されている。ここを冪等にすると帳簿が
実際より安くなる。

⚠️ **書くのは LLM サービスだけである。**

段階4 で core / assessments から LLM を呼ぶコードが消えたので、
書く側が居なくなった。呼び出し元は集計と待ち画面の見積もりのために
**読むだけ**になり、CDK も読み取り権限しか渡していない。
読む側が書けると、原価を後から書き換えられる。

`any-learn-ai-core/src/shared/ai-usage.ts` に残っているのは、読む側が要る鍵の作り方と
型だけである（`recordAiUsage` は削除した）。

### 4.4 依頼側の冪等性

同じ依頼が二重にキューへ入らないよう、依頼に `requestId`（呼び出し元が
採番）を持たせる。SQS の `MessageDeduplicationId` は FIFO キューでしか
使えず、FIFO は同時実行数の制約が強い（グループあたり直列）ので**使わない**。

重複はサービス側では防がず、**後処理側で吸収する**（4.2）。

⚠️ `requestId` は「同じ依頼を2回積んでも安全な形」にすること。

| 経路 | 鍵 |
|---|---|
| プログラム生成 | `programId` |
| 解説 | `explanation#${microStepId}` |
| Q&A | `qa#${sessionId}#${microStepId}#${index}` |
| 採点 | `grading#${sessionId}#${microStepId}#${index}` |
| 出題（その場） | `quiz-now#${microStepId}#${attemptCount}` |
| 先読み | `quiz#${microStepId}#${attemptCount}` |

⚠️ **出題と先読みで鍵を分けてある。**同じにすると、先読みの結果が
出題の席へ、あるいはその逆へ書き込まれる余地ができる。宛先も分けてある。


## 5. 論点3: 対話系を非同期にするか

⚠️ **検討時は「対話系4つ」と数えていたが、実際は5経路あった。**
assessments の記述式採点（29秒問題の当事者）が数え漏れていた。

| 経路 | 移設前の実測 | どこ |
|---|---|---|
| 確認問題の出題 | 6.8秒 | core |
| 採点 | 3.6秒 | core |
| Q&A（ステップ／セッション） | 3.3秒 | core（2ハンドラ） |
| 目標チャット | 3.2秒 | core |
| 記述式の採点 | — | assessments |

いずれも画面が同期で待っていた。**すべて移設済み**（段階4a）。

### 5.1 判断: **やる。全経路を非同期に統一する**（2026-08-08 決定）

⚠️ この節は当初「当面やらない」としていた。費用の観点では割に合わないためである。
**方針が変わった。判断の基準を費用ではなく、方式の統一とスケーラビリティに置く。**

決定: **同期の経路を残さない。LLM 呼び出しは例外なくキューを通す。**

理由:

- **契約が1つになる。** サービスに同期と非同期の2つの入口があると、
  冪等性・再試行・エラー経路・流量制御をそれぞれ2通り作ることになる。
  片方だけ直す事故が必ず起きる（登録簿と単価表で2回起きたのと同じ構図）
- **同期を残すと二重課金が残る。** 呼び出し元が API Gateway へ応答を返す
  義務を負う限り、サービスの返事を待つ間ずっと動く。実測ベースの試算で
  同期ぶんは 100人あたり 111円で、これがそのまま上乗せになる。
  非同期なら呼び出し元は約100msで終わるので発生しない
- **流量制御が全経路に効く。** 1人262回の呼び出しのうち、回数が多いのは
  むしろ対話系（確認問題75・採点75・Q&A20）である。ここがキューを
  通らないと、背圧をかけたい経路の大半が対象外になる

**費用はこの決定の理由ではない。** 結果として安くはなるが、
根拠は「方式を1つに保つこと」である。

### 5.2 これに伴う前提の変更

- **WebSocket が必須になる**（6章）。「レート制限に当たってから」ではなく、
  対話系を移す時点で要る

  ⚠️ **着手時にこの前提を見直した。**必須なのは「体感を戻すため」であって、
  経路を移すこと自体には要らない。ポーリングを fallback として残す方針
  （6.3）なので、先にポーリングで通してから WebSocket を足せる。
  実際に 4a（キュー経由）と 4b（WebSocket）へ分けて実施した。
- `any-learn-ai-assessments/src/handlers/submit-answer.ts` の 29 秒問題は、
  個別の対処ではなく**この統一の中で解ける**
- フロントの改修規模は大きい。`app/learn/[sessionId]/page.tsx` は
  2,345 行・`useState` 34 個で、8 値のステートマシン（`type Phase`）を軸に
  全描画が分岐している。既存の `pollUntilDone` / `useWaitProgress` /
  `WaitProgressBar` の3点セットは流用できる

### 5.3 着手順序は変えない（そのとおりに実施した）

**対話系とフロントの WebSocket は最後にする。**
先に非同期のまま移せる経路（プログラム生成・解説・設問生成・診断レポート・
目標分析・計画見積もり）で配管を固め、そこが安定してから対話系へ進む。
最初から一番難しいところを触ると、配管の問題と画面の問題が混ざって切り分けられない。

## 6. 論点4: WebSocket の認証

> **実施済み（段階4b）。**この章の方式はそのまま実装した。
> 実装は shared-infra の `setupWebSocket` / `src/ws-*.ts`、
> llm の `src/handlers/notifier.ts`、frontend の `lib-web/notify.ts`。

### 6.1 制約（確認済み）

- **API Gateway の WebSocket API は Cognito ユーザープール Authorizer に対応していない。**
  使えるのは IAM 認可か Lambda REQUEST Authorizer で、しかも **`$connect` ルートでのみ**動く
- フロントは静的エクスポート（`next.config.ts` の `output: 'export'`）で CloudFront 配信。
  **サーバーサイドの中継点が無い**ので、ブラウザから API Gateway へ直接つなぐ
- ID トークンは Amplify v6 が localStorage に保持する。`getIdToken()`（`lib-web/auth.ts:183-192`）で取れる

### 6.2 方式: 短命チケット + Lambda REQUEST Authorizer

素直な実装は「ID トークンをクエリ文字列に載せる」だが、**採らない**。
クエリ文字列は API Gateway のアクセスログ・CloudWatch・ブラウザ履歴に残り、
Cognito の ID トークンは有効期限まで再利用できてしまう。

代わりに:

1. 既存の REST API に `POST /ws-ticket` を足す（Cognito Authorizer 配下＝既存の仕組みのまま）
2. 60秒で失効する一度きりのチケットを発行し、DynamoDB に `userId` とともに TTL 付きで保存
3. ブラウザは `wss://.../?ticket=...` で接続
4. `$connect` の Lambda REQUEST Authorizer がチケットを**消費**（条件付き削除）して `userId` を確定し、
   `principalId` として返す
5. 接続テーブルに `connectionId → userId` を TTL 付きで保存する

利点:

- ログに残るのは使い捨てのチケットで、漏れても60秒かつ1回きり
- トークンの検証ロジックを自前で書かない（`POST /ws-ticket` は既存の Cognito Authorizer が守る）
- 再接続のたびにチケットを取り直す＝トークンの更新が自然に反映される

### 6.3 接続の寿命と再接続

- 接続テーブルの TTL は **2 時間**（API Gateway WebSocket のアイドル
  タイムアウト10分・最大接続時間2時間に合わせる）
- チケットの TTL は **60秒**。発行してすぐ繋ぐだけで、持ち歩くものではない
- クライアントは切断時に**チケット取得からやり直す**。
  指数バックオフ（1秒から倍々、上限30秒）で**最大5回**。
  5回張れなければ、その環境では張れないと判断して以降試さない
- **ポーリングを消さない。** WebSocket が張れない環境（企業プロキシなど）
  向けに `pollUntilDone` を fallback として残す

#### 6.4 実装で決まったこと（設計時に書いていなかった）

⚠️ **接続の掃除は3重にする。**

`$disconnect` は回線が切れた場合などに届かないことがある。

1. `$disconnect` で消す
2. TTL（2時間）で消す
3. 送信で 410 が返ったらその場で消す（通知係の担当）

どれか1つに頼らない。

⚠️ **期限の判定を TTL に任せない。**

DynamoDB の TTL は最大48時間の遅れがある。期限切れのチケットが残っている
間に使われうるので、消費側（`ws-authorizer.ts`）でも時刻を見ている。
TTL は掃除のためだけのものと考える。

⚠️ **チケットは「消費」する。読むだけにしない。**

条件付き削除（`ConditionExpression: 'attribute_exists(ticket)'` +
`ReturnValues: 'ALL_OLD'`）で1回きりにする。読むだけだと、クエリ文字列に
残ったチケットを拾った誰かが失効までの60秒のあいだ何度でも接続できる。
削除が成功した呼び出しだけを通せば、同じチケットで2本目は張れない。

dev で実測して確認した:

```
チケット発行            HTTP 201 / 43文字
1回目の消費             Allow  / principalId = 発行した userId
2回目の消費（同じ券）   Deny   / principalId = anonymous
```

⚠️ **認可は `$connect` でしか掛からない。**

API Gateway の WebSocket API はこの1か所でのみ認可を行う。接続が確立した
あとのメッセージには認可が掛からないので、「誰の接続か」は接続時に確定
させて持ち回るしかない。それが接続テーブルの役目である。

これを忘れて `$default` に認可を付けたつもりになると、実際には誰でも
送れる状態になる。テストで `$connect` だけが `CUSTOM` であることを縛った。

⚠️ **失敗は Deny で返す（例外を投げない）。**

例外を投げると API Gateway は 500 を返す。チケットが無効なのは
「サーバーの障害」ではないので Deny（403）を返す。クライアントは 403 を
見てチケットの取り直しから始められる。

## 7. 論点5: エラーの経路

### 7.1 移設前の状態（何が問題だったか）

DLQ が無かった。失敗は**ワーカー自身が DynamoDB に `failed` を書く**ことで
のみ画面に届いていた（`failProgramGeneration` など）。ワーカーがその書き込み
ごと失敗すると、画面は `generating` のままポーリングし続け、クライアント側の
タイムアウトでしか終わらない。

つまり**失敗が黙って消える経路があった。**

### 7.2 方式

**失敗も成功と同じ経路で返す。** LLM サービスは例外を投げずに、
結果イベントへ `status: 'failed'` と理由を載せて EventBridge へ出す。
後処理 Lambda が受け取り、条件付き書き込みで `failed` を記録する。

理由: 失敗の通知経路を別に作ると、その経路自体の failure が次の穴になる。
成功と同じ配管を通せば、配管が壊れれば両方止まる＝気づける。

**3段構え**にする。

| 段 | 何が起きたか | 誰が拾うか |
|---|---|---|
| 1 | LLM 呼び出しが失敗（レート制限・タイムアウト・スキーマ違反） | LLM サービスが `status: 'failed'` を返す。後処理が `failed` を書く |
| 2 | LLM サービス自体が落ちた（バグ・OOM） | SQS の `maxReceiveCount: 3` で DLQ へ。**DLQ に CloudWatch アラームを張る** |
| 3 | 後処理が落ちた（DynamoDB 障害など） | 結果イベント用の SQS にも DLQ を置く。ここが溜まる＝`generating` のまま残る学習者がいる |

#### 実装した形

| 何 | どこ | 設定 |
|---|---|---|
| 依頼キューの DLQ | `llm-stack.ts` | `maxReceiveCount: 3`。**自動で戻さない** |
| DLQ が空でないアラーム | 同上 | 1件でも入ったら鳴る |
| 依頼の滞留アラーム | 同上 | 消費が追いつかない状態を拾う |
| 生成中のまま残った記録の掃除 | `any-learn-ai-core/src/handlers/sweep-stuck-generations.ts` | 定期実行で `failed` へ終端させる |

⚠️ **DLQ を自動で redrive しない。**入った理由が分からないまま戻すと、
同じ理由で落ちて往復するだけになる。鳴らして人が見る。

⚠️ **アラームが鳴らないと、学習者は `generating` のまま待ち続ける。**
移設前は DLQ 自体が無く、失敗が黙って消えていた。

### 7.3 画面側: 「作成できませんでした」に丸めない（2026-08-08 実施）

⚠️ **この節は実際に踏んだ不具合から書いている。**

dev で「学習プログラムを作成できませんでした／サーバーエラーが発生しました」
が出た。だがプログラムは出来ていた。落ちていたのは生成ではなく、
そのあとの `GET /progress`（環境変数の配線漏れ）だった。

学習者から見ると作成に失敗したようにしか読めない。勧められる操作も
「もう一度試す」だけで、押せば**出来上がっているプログラムをもう一度作る**。

#### 原因は `pollUntilDone` にあった

401 以外の例外をすべて握りつぶして再試行し続けていた。
GET が 500 を返し続けても期限まで回り、最後に

> 生成に想定以上の時間がかかっています（サーバー側で続いています）

と出る。**状態を一度も読めていないのだから、そう言う根拠が無い。**

#### 待っている間に起こりうることは3つある

| 例外 | 何が起きたか | 学習者に勧めること |
|---|---|---|
| `PollFailedError` | サーバーが `failed` を記録した | もう一度作る |
| `PollUnreachableError` | 状態を読めない | **作らせない。**開き直す |
| `PollTimeoutError` | 読めているが終わらない | 待つ（続いていると言ってよい） |

以前は3つとも素の `Error` で、画面は文字列1本しか受け取れなかった。

読めない状態が続いたら諦める（既定5回・3秒間隔で約15秒）ようにして、
一度でも読めればカウンタを戻す。デプロイ中の瞬断は乗り越え、
壊れている状態は15秒で表に出る。

#### 分ける基準は「次に何をすればよいか」

`describeWaitFailure` が `retry` / `reload` / `signIn` を返す。
原因の分類ではなく次の行動で分けた。学習者にとって意味があるのは
「何が起きたか」ではなく「どうすればよいか」である。

なお `fetch` 自体の失敗（ネットワーク断・CORS）は `ApiError` にならず
`TypeError` のまま上がる。以前は `"Failed to fetch"` がそのまま
画面に出うる状態だったので、これも受け止めるようにした。

**DLQ を誰が拾うか**（メモの問い）への答え:
**自動で拾わない。** DLQ に入るのはコードの不具合か AWS の障害で、
自動再投入は同じ失敗を繰り返すか、二重課金になる。
アラームで人を呼び、原因を直してから手で戻す。

ただし **`generating` のまま取り残された学習者を見つける仕組みは要る。**
`updatedAt` が一定時間より古く `generationStatus = 'generating'` のレコードを
1時間ごとに拾って `failed` へ落とす掃除係（EventBridge Scheduler + Lambda）を置く。
これは DLQ とは別の、**画面を必ず終端させるための保険**である。

## 8. イベントとインタフェースの定義

⚠️ **ここは実装（`any-learn-ai-llm/src/contract.ts`）が正である。**
食い違いを見つけたらコードのほうを信じること。

### 8.1 依頼（SQS メッセージ）

```ts
export interface LlmRequest {
  /**
   * 契約の版。
   *
   * ⚠️ 検討時には無かった。キューには最大14日ぶん残るので、
   * デプロイの順序で「古い形の依頼」が必ず届く。読めないまま黙って
   * 捨てると呼び出し元が待ち続けるので、版を見て失敗として返す。
   */
  readonly schemaVersion: number;
  /**
   * 呼び出し元が採番する。結果の突き合わせと、後処理の冪等性の鍵になる。
   * 同じ依頼を2回積んでも安全な形（例: `${programId}#1`）にすること。
   */
  readonly requestId: string;
  readonly purpose: Purpose;
  readonly system: string;
  readonly userPrompt: string;
  /** 期待する出力の形。サービスはこれで検証し、通らなければ1回だけ作り直す */
  readonly schema: Record<string, unknown>;
  readonly maxTokens?: number;
  readonly usage?: UsageScope;
  /** 結果イベントの detail-type。呼び出し元はこれで自分宛てを拾う */
  readonly replyTo: string;
  /** 呼び出し元が自由に持ち回れる値。**サービスは中身を一切見ない** */
  readonly context: Record<string, unknown>;
}

export interface UsageScope {
  readonly userId: string;
  readonly scopeId: string;
  readonly kind: 'goal' | 'program' | 'assessment';
  /**
   * この呼び出しで作る個数。所要時間の見積もりに使う。
   * 所要時間は作る個数でほぼ決まるので「秒 / 個」で実績を貯める。
   */
  readonly units?: number;
}
```

⚠️ **検討時にあった `attempt` は実装しなかった。**

「ドメイン検査による再投入の上限管理」のために置くつもりだったが、
論点1の実験で再生成ループそのものを廃止した（3.5）ので、数える対象が
無くなった。スキーマ違反での作り直しはサービス内部で1回だけ行い、
呼び出し元からは見えない。

`context` を置くのが要点である。サービスはこれを**解釈せずに結果へ
そのまま echo する**。これが無いと、後処理が「どの生成の結果か」を
別途引き当てることになる。

⚠️ **モデル名は依頼に入れない。**呼び出し元が指定できると、登録簿に
無い名前が入る経路ができ、単価表にも載らないので原価が消える。
用途だけ渡し、モデルはサービスが登録簿と SSM から決める。

### 8.2 結果（EventBridge イベント）

```ts
export interface LlmResult {
  readonly schemaVersion: number;
  readonly requestId: string;
  readonly purpose: Purpose;
  /** 依頼の context をそのまま返す */
  readonly context: Record<string, unknown>;
  readonly status: 'succeeded' | 'failed';
  /** status === 'succeeded' のとき。スキーマ検証を通った JSON */
  readonly output?: unknown;
  readonly error?: LlmError;
  /** 実際に使ったモデル。呼び出し元は指定しないので、結果で知らせる */
  readonly model: string;
  /** 生成に掛かった時間。作り直した場合は合計 */
  readonly durationMs: number;
  /** 何回生成したか（1 または 2）。検査の発火率を後から数えるため */
  readonly attempts: number;
  /**
   * 依頼の replyTo をそのまま返す（= この結果の detail-type）。
   *
   * ⚠️ 段階4b で足した。
   *
   * 宛先ごとの後処理は、ルールが detail-type で振り分けるので自分が何を
   * 受けたか分かっている。だが**すべての宛先をまとめて購読する購読者**
   * （WebSocket の通知係）は、detail の中から知る必要がある。
   */
  readonly replyTo: string;
}

export type LlmErrorKind =
  | 'rate-limited'  // 待って積み直す価値がある
  | 'truncated'     // 上限で打ち切られた。maxTokens を上げるか依頼を分ける
  | 'refused'       // モデルが拒否した。積み直しても無駄
  | 'schema'        // 2回試してもスキーマに合わなかった
  | 'provider'      // プロバイダが 4xx/5xx を返した
  | 'unknown';
```

検討時との差:

| 項目 | 検討時 | 実装 |
|---|---|---|
| `schemaVersion` | 無し | **追加**（依頼と対） |
| `attempt`（依頼の回数） | 有り | **削除**（再生成ループ廃止に伴い） |
| `attempts`（生成した回数） | 無し | **追加**。検査の発火率を後から数えるため |
| `replyTo` | 無し | **追加**（段階4b。全宛先を購読する通知係が要る） |
| `error.kind` | 6値をインラインで定義 | `LlmErrorKind` として型に切り出し。値は同じ |

`error.kind` を型で持つのは、**後処理が学習者へ見せる文言を選べるように
するため**である。検討時は「再投入すべきかの判断」と書いたが、再生成ループを
廃止したので、実際の使い道は文言の出し分けになった
（`rate-limited` → 「混み合っています」、`refused` → 「AI が控えました」）。

### 8.3 呼び出し元から見た形

呼び出し元は SQS を直接触らない。薄いクライアントが口を提供する。

パッケージにしないのは、private リポジトリ間の npm 配布に CI とローカル

## 9. 移行計画

検討メモの「5. 推奨する進め方」を、0章の訂正に合わせて組み替えたもの。
**順序の基準は金額と危険度**にした。

### 段階0: 独立した片付け（**2026-08-08 実施済み**）

どの設計を選んでも無駄にならない。**以下はすべて完了している**（結果は 9.1 節）。

1. **`usesLlm` の既定値を `false` にする**（`core-stack.ts:247`）。
   影響は5関数（`start-session` / `get-session` / `list-micro-steps` / `next-micro-step` / `complete-micro-step`）。
   `get-program-cost` で実施済みの `readsAiUsage` と同じ形。回帰テストは `test/core-stack.test.ts` の既存2件に倣う
2. **Lambda のメモリを 512MB へ**。ただし**まず1関数で測る**（下記）
3. `.github/workflows/deploy.yml` が `MODEL_*` を4件しか渡していない
   （`MODEL_PROGRAM_GENERATION` / `MODEL_GOAL_ANALYSIS` / `MODEL_GOAL_CHAT` / `MODEL_PLAN` が欠落）。
   CDK 側は8件を導出済みなので、ワークフロー側だけ直す
4. **フェーズ数の下限をセッション総数から導く**（3.4）。
   短い目標 × 軽めの深さでプログラム生成が必ず失敗する。実験で3回とも再現した。
   非同期化とは独立しており、**いま学習者に届いている不具合**なので最優先
5. **再生成ループを外す**（3.5）。実験の結果、直らない場合にだけ走っていた。
   `generate-program.ts` の `shouldRegenerate` による2回目の生成を止める。
   4 と併せて入れること（4 を直さずにこれだけ外すと、失敗が早くなるだけになる）

**メモリ変更は測ってから広げる。** Lambda は割り当てメモリに比例して CPU が付く。
待ち時間が支配的でも、初期化と JSON 解析は CPU を使う。
`generate-program` を 3008 → 1024 → 512 と落として `Init Duration` と `Duration` を比較し、
劣化が無いことを確認してから他へ広げること。実使用 143MB に対し 512MB は3.5倍の余裕がある。

#### 9.1 段階0 の結果（2026-08-08）

**(1) 短いプログラムが作れなかった不具合 — 直った**

`structureFor(totalSessions, totalWeeks)` を新設し、プロンプトと検査の**両方**が
これを使うようにした（片方だけ直すと必ずまたずれる）。
システムプロンプトからは固定値を外し、範囲はユーザープロンプトで毎回渡す。

同じ道具で測り直した結果（セッション4回・2週の題材、3回とも独立生成）:

| | 修正前 | 修正後 |
|---|---|---|
| 学習者に渡せたか | **0/3** | **3/3** |
| セッション数 | 5, 4, 4 | **4, 4, 4** |
| 致命的な不備 | 毎回2件（`sessions` が空） | **0件** |

フェーズ数の上限を週数でも縛るようにしたので、
「`durationWeeks` が無い」も併せて消えた。

**(2) 再生成ループ — 外した**

`generate-program` の2回目の生成と、`shouldRegenerate` / `ProgramDefect.worthRetry`
を削除した。LLM 呼び出しは**常に1回**になる（従来は最悪4回）。

**(3) `usesLlm` の既定値 — `false` にした**

合成後のテンプレートで、鍵を持つのは**LLM を呼ぶ10関数のみ**になった。
外れたのは `start-session` / `get-session` / `list-micro-steps` /
`next-micro-step` / `complete-micro-step` の5つ。

既定を反転させたことで「足し忘れると LLM を呼ぶ関数が実行時に落ちる」という
逆向きの間違いが起こりうるので、鍵が**要る**側の検知テストも対に入れた。

**(4) メモリ — 実測して 512MB へ**

`generate-program` で 3008 / 1024 / 512 を測った（`tools/memory-probe.sh`）。

| 割当 | 初期化 | 所要（コールド／ウォーム） | 実使用 |
|---|---|---|---|
| 3008MB | 283ms | 26.0秒 / 21.6秒 | 147MB |
| 1024MB | 308ms | 29.4秒 / 17.5秒 | 144MB |
| **512MB** | **391ms** | 20.7秒 / 25.2秒 | 145MB |

- 実使用は割り当てに関係なく 145MB 前後。**512MB でも 3.5 倍の余裕**
- 所要時間は割り当てと相関しない（LLM の待ちが支配的なので当然）
- 差が出たのは初期化だけで **+108ms**。20〜30秒の処理に対して 0.4%

このとき非同期ワーカー5つ（`generate-program` / `explanation-worker` /
`analyze-goal` / `estimate-sessions` / `calculate-plan`）を 512MB にした。

⚠️ **その後、この5つのうち4つは消えた。**段階2・3 で LLM サービスへ
移り、残るのは `calculate-plan` だけ（しかも 600秒 → 30秒）。

片方だけ足す事故は起こる（実際に2回起きたのはその形）。

だから換算する側が単価を持つ必要がある。

画面へ「推定」と伝える。安く見えて値付けを誤るより、高く見えるほうがよい。

#### 段階4a: 対話系をキュー経由にする（実施済み・2026-08-08）

移した経路（core 5 + assessments 1 = **6ハンドラ**）:

| 経路 | ハンドラ | 特徴 |
|---|---|---|
| 確認問題の出題 | `generate-quiz` | 先読みが間に合えば同期のまま 200 |
| 採点 | `evaluate-answer` | 選択式で正解・「分からない」は同期のまま 200 |
| ステップ Q&A | `micro-step-qa` | 席を作って 202 |
| セッション Q&A | `session-question` | 同上（宛先は Q&A と共通） |
| 目標チャット | `goal-chat` | 発言と空の返答席を同時に積んで 202 |
| 記述式の採点 | `submit-answer`（assessments） | 29秒問題がここで解けた |

⚠️ 5章では「対話系」を**種類**で5つと数えている（Q&A をひとまとめ）。
ここは**ハンドラ**の数なので6になる。同じものを違う粒度で数えている。

**⚠️ 待たなくてよいものは待たせない。** 選択式で正解したときの採点や、
先読みが間に合った出題は、答えが決まっている。キューを通すと
待つ必要のないものを待たせるだけになるので、同期のまま残した。
非同期にしたのは「実際に生成が要る場合」だけである。

##### 冪等性: 席を先に作り、結果が埋める

**これが段階4でいちばん重要な設計判断だった。**

段階2・3で移した経路は、いずれも「同じ値を上書きする」書き込みだった。
2回書いても結果が変わらないので、二重配信を気にせずに済んだ。

対話系は積む書き込みばかりである。

| 書き込み | 形 | 2回受けると |
|---|---|---|
| `appendQaTurn` | `list_append` | 同じ質問と回答が2回並ぶ |
| `appendQuizAttempt` | `list_append` | 挑戦記録が2件になる |
| `appendChatAndUpdate` | `list_append` | 同じ発言が2回会話に残る |
| `bumpProgress` | `ADD` | 不正解回数が2つ進む |

不正解回数が2つ進むと、再解説の切り口と次のヒントの有無がずれる。
学習者から見ると「1回しか間違えていないのにヒントが出た」になる。

はじめは処理済みの `requestId` を文字列集合で持ち、条件式
（`NOT contains(processedRequests, :requestId)`）で弾く形を検討した。
実装しかけて、もっと簡単な形があることに気づいた。

**積む操作を受付（HTTP の同期処理）の中だけに置き、結果ハンドラは
添字を指定して埋める。** 受付は再配信されないので積むのは1回きり、
埋めるのは同じ値の上書きなので何回でも同じ結果になる。

専用の防壁が要らなくなった。用意しかけた `domain/once.ts` は破棄した。

##### 総合スコアの競合（assessments）

⚠️ **移設で新しく生まれた危険。** 移設前は、受付が手元に持っている
設問一覧から `totalScore` を計算して回答と一緒に書いていた。
採点が同期だったので、その一覧は常に最新だった。

非同期になると崩れる。学習者が続けて2問答えると採点が2つ並走し、
古いスナップショットで計算した総合スコアが新しいものを上書きしうる。
1問ぶんの点が静かに消える形で、エラーは出ない。

書き込みを2段に分けた。

- `saveAnswer` … 1問ぶんだけ書く（添字指定なので競合しない）
- `recomputeTotals` … 読み直して集計する。回答済みの数を条件に入れ、
  変わっていたら読み直す（3回まで）

回答自体は別の書き込みで確定しているので、やり直しても失われない。

##### 状態を返し忘れると、待ち続けになる

⚠️ **段階4a の最後に見つけた。踏む前に気づいたが、危うかった。**

出題も同じで、`get-explanation` が `quizStatus` を返していなかった。

**成功したときは偶然動く。** 判定（`verdict`）が入るので、画面は
「入ったら終わり」と読める。

壊れるのは失敗したときである。`verdict` が空のまま止まるので、
画面は「失敗」と「まだ終わっていない」を区別できず、期限まで待つ。
学習者から見ると「採点が終わらない」になる。

**非同期化では、状態を返し忘れることが待ち続けに直結する。**
成功経路のテストでは見つからない。項目の存在自体を縛るテストを置いた
（失敗した挑戦を渡して `gradingStatus` が返ることを見る）。

あわせて、模範解答と採点基準が混ざらないことも縛った。この形は解説と
一緒に返る＝確認問題に答える前にも届くので、混ぜると答えが先に見える。

dev で実測して確認した:

```
quizStatus    : failed / quizError: 確認問題を作成できませんでした。
gradingStatus : failed / gradingError: 採点できませんでした。
答えの漏れ    : 無し
```

サーバーが状態を返し、画面はそれを読むだけにした。
推測は成功経路でしか合わない。

##### ポーリングは Lambda の待ちを作らない（実測・2026-08-08）

「ポーリングを fallback に残すと、Lambda の待ちが戻るのではないか」
という問いに答えておく。**戻らない。** ただし理由を正確に押さえておく
必要がある。

⚠️ **「待ち」を2つに分けて考えること。**

| | 移設前の待ち | ポーリング1回 |
|---|---|---|
| していること | LLM の応答を**ソケットを握って**待つ | DynamoDB を読んで**即返す** |
| 1回の長さ | 3.6〜6.8秒（対話系の実測） | **13〜45ms**（dev 実測） |
| メモリ | 1024MB | 512MB |
| 課金 | 待っている全時間 | 実行した数十ms |

前者は「何もしていないのに課金される時間」、後者は「実際に仕事をした
時間」で、性質が違う。dev の `get-explanation` を生成中の状態で5回
連続で呼んで測った（初回 325ms はコールドスタート、以降 13〜45ms）。

##### 待ちは消えたのではなく、1か所に集まった

⚠️ **LLM サービスの消費側 Lambda は、いまも待っている。**

これは避けられない。誰かがソケットを握る必要がある。
この一連の作業でやったのは、その待ちを**6か所（1024〜3008MB）から
1か所（512MB）へ寄せた**ことである。ポーリングはこの構図を変えない。

##### ポーリングのコストは「回数」

待ちではなく呼び出し回数である。

15秒の生成を2秒間隔で待つと 7〜8回の GET。1回 40ms・512MB として
約 320ms・512MB。移設前の対話系1回（6.8秒・1024MB）の**約 1/40**。

ただし回数は同時学習者数 × 頻度で増える。1人 262回の呼び出しのうち
非同期になったものすべてにポーリングが付くので、API Gateway と
DynamoDB の読み取り回数は確実に増える。ここが段階4b で効く。

##### ⚠️ やってはいけないこと: サーバー側で待つ long-polling

**「Lambda の中で結果が来るまで待つ」形にすると、待ちが復活する。**

呼び出し回数を減らしたくなると、この案が魅力的に見える。
GET を受けた Lambda が数十秒かけて結果を待ち、来たら返す——
呼び出しは1回で済み、体感も即時になる。

だがこれは移設前と同じものである。API Gateway の 29 秒制限に戻り、
1024MB の実行環境がネットワークを待つ状態も戻る。**わざわざ剥がした
ものを、別の名前で戻すことになる。**

回数を減らしたいなら WebSocket（下）を使う。サーバー側で待つ実装は
入れないこと。現在サーバー側に `sleep` も待機ループも無いことを
確認してある。

#### 段階4b: WebSocket を足して体感を戻す（実施済み・2026-08-08）

方式は6章のまま（短命チケット + Lambda REQUEST Authorizer）。
ポーリングは fallback として残す。

⚠️ **4b は「待ちを消す」作業ではない。**待ちはすでに1か所へ寄っている。
4b が削るのは**呼び出し回数と体感の遅れ**である。

| | ポーリング | WebSocket |
|---|---|---|
| Lambda の待ち | 無い | 無い |
| 呼び出し回数 | 生成時間 ÷ 2秒 | 1回（接続時） |
| 体感 | 最大2秒の遅れ | 即時 |

##### 送るのは合図だけ。生成物は送らない

⚠️ **これが 4b でいちばん重要な判断である。**

合図と一緒に生成物を送れば往復が1回減る。だがそうすると
**同じデータに2つの経路ができる。**

    WebSocket が届いた場合 … イベントの中身を使う
    届かなかった場合       … GET で読み直す

この2つがずれると、片方だけで再現する不具合になる。
実際に危ないのは、**ドメインの検査を通っていない値が WebSocket 経由で
画面へ入ること**である。選択肢が壊れた確認問題は、後処理の検査で弾かれて
`failed` になるはずが、合図と一緒に流すと画面へ出てしまう。

合図だけにすれば、画面が読むのは常に GET の1経路になる。
ポーリングと WebSocket が同じコードへ収束する。
「生成物を触っていないこと」をテストで縛った。

完了の判断も必ず GET の結果で行う。合図を完了と読むと、
失敗した場合まで成功として扱うことになる。

##### 置き場所は依存の向きで決まった

⚠️ **通知を送る側を shared-infra に置けない。**

| 何 | どこ | なぜ |
|---|---|---|
| WebSocket API・2つのテーブル・認可・チケット発行 | shared-infra | REST API と Cognito を持つのがここ。共有の入口は1か所に集める |
| 通知を送る係 | any-learn-ai-llm | 購読するバスをこのサービスが持っている |

送る側は結果イベント（EventBridge）を購読する必要があり、そのバスは
llm が持っている。shared-infra がそれを読むと

    shared-infra → llm → shared-infra

の循環になり、どちらも先にデプロイできない。土台だけを shared-infra が
作って SSM へ公開し、送る側が読む形にした。

⚠️ 通知係は結果の**中身を解釈しない**。`userId` と識別子だけを見る。
それ以上を知ると、LLM サービスが学習ドメインを知ることになる。

##### すべての宛先を1つのルールで拾う

宛先ごとにルールを分けない。中身を見ないので分けても同じ処理が並ぶだけで、
detail-type を列挙する形にすると経路を足すたびにここも直すことになる。
忘れると**通知だけ届かない**——しかもポーリングで動くので気づけない。

代わりに `anything-but` で疎通確認だけを除いた。
学習者の接続へ検証用の合図が飛ぶのは正しくない。

##### 接続の掃除は3重

`$disconnect` は回線が切れた場合などに届かないことがある。

1. `$disconnect` で消す
2. TTL（2時間 = WebSocket の最大接続時間）で消す
3. 送信で 410 が返ったらその場で消す

どれか1つに頼らない。

##### dev で実測したこと

```
チケット発行            HTTP 201 / 43文字
1回目の消費             Allow  / principalId = 発行した userId
2回目の消費（同じ券）   Deny   / principalId = anonymous
```

使い捨てが実環境で効いている。読むだけの実装だと、クエリ文字列に
残った券を拾った誰かが失効までの60秒のあいだ何度でも接続できる。

##### ⚠️ 実環境で確かめられなかった分岐

偽の接続 ID で通知係を呼んだところ、返ってきたのは 410 ではなく
**「Invalid connectionId」**だった。接続 ID には形式があるので、
存在しない値を渡しても Gone にはならない。

410 が返るのは「形式は正しいが、もう切れている接続」だけで、
それを実環境で作るには本当に接続して切る必要がある。
掃除の分岐は単体テストで固めた（410 なら消す・それ以外では消さない）。

**一時的な障害で生きた接続を消してはいけない。**消すとその学習者は
ポーリングだけになる（壊れはしないが、速さが戻らない）。

##### 張れなくても何も壊れない

企業プロキシなどで WebSocket が通らない環境はある。接続に失敗したら
黙って諦め、ポーリングだけで待つ。「接続できません」と学習者へ出さない
——学習には影響しないので、出すと不安にさせるだけになる。

5回張れなければ、その環境では張れないと判断して以降試さない。
CI も `ws-endpoint` が取れなくてもビルドを止めない。通知が使えない
だけの状態でデプロイが丸ごと止まるのは割に合わない。

##### 宛先の名前はサーバーと突き合わせる

画面側は `lib-web/reply-kinds.ts` に1か所だけ持つ。サーバーの
`REPLY_TO` とずれると、合図が素通りして間隔ぶん待つ——エラーにならず
**「WebSocket を足したのに速くならない」**形で現れるので気づきにくい。

### 10.1 決着 #8: 単価は記録に残す

⚠️ **この移設でいちばん直したかった構造。段階4 の後に解いた。**

#### 何が問題だったか

登録簿（LLM サービス）と単価表（core の `RATES`）で単価を別々に
持っていた。モデルを足すのは前者、原価を表示するのは後者なので、
片方だけ直す事故が起きる。**実際に2回起きた。**

qwen3.7-plus では解説1回が 0.19 円なのに **3.60 円**と表示された（18倍）。

段階1 で「単価表をサービスへ移す」としたが、移せなかった。
原価の**表示**が core の機能で、円換算する側が単価を要るからである。

#### 解き方: 単価はトークン数と同じ「事実」である

⚠️ **単価は「その呼び出しに適用された事実」**であって、
あとから引く参照表ではない。

事実なら、トークン数と同じ資格で記録に残せばよい。LLM サービスは
呼び出しの記録へ `rateInputUsd` / `rateOutputUsd` を一緒に書く。
**読む側は表を持たなくてよくなり、持たなければずれようがない。**

```
記録: { model, inputTokens, outputTokens, rateInputUsd, rateOutputUsd, ... }
                              └─ 事実 ─┘  └────── これも事実 ──────┘
```

#### 副産物: 過去の記録が正しくなった

単価は改定される。今の単価で引き直すと、**一度も請求されたことのない
金額**が出る。記録に残せば、過去は当時の単価のまま残る。
「実際にいくら課金されたか」を答えるにはそのほうが正しい。

4.3 で「金額を焼き込むと単価が変わった瞬間に食い違う」と書いたが、
焼き込むのは**金額ではなく単価**である。トークン数と単価の両方が
あれば、当時の実額も、今の単価での試算も、どちらも出せる。

#### core の表は凍結した（消していない）

この仕組みを入れる**前に**記録されたぶんを読むために残す。

⚠️ **「ここへモデルを足さないこと」と明記した。**足せる状態のまま
「足し忘れないように」と注意書きするのは、ずれられる構造を残したまま
見張るやり方でしかない。新しいモデルの記録には必ず単価が載るので、
足す必要が生じない。

### 10.2 決着 #9: 掃除係を増やさず、読むときに判断する

#### 掃除係を増やす案は採らなかった

段階3・4 で非同期の経路が8つに増えた。同じ形で掃除係を増やすと8つになる。

⚠️ **さらに、対話系の「生成中」は配列の中にある。**

```
qaTurns[3].status = 'generating'
quizAttempts[2].gradingStatus = 'grading'
chatHistory[5].status = 'generating'
questions[3].gradingStatus = 'grading'   （assessments）
```

索引を張れない。掃除係はテーブルを全件走査して配列を1つずつ歩くことに
なり、学習者が増えるほど重くなる。しかも**取り残しがゼロのときも毎回走る。**

#### 掃除係が守っていたのは2つだけだった

| 守っていること | どこで効く |
|---|---|
| 画面が待ち続けない | GET が状態を返すとき |
| 再試行が塞がれない | 受付が「生成中なら積み直さない」と判断するとき |

**どちらも読むときの判断である。**書き込んで状態を変える必要が無い。

```
「生成中」= status が generating かつ、開始から猶予内
猶予を過ぎたら → 読む側が「届かなかった」として扱う
```

開始時刻は段階4a で席を作るときに必ず入れてあるので、追加のデータは
要らない。**経路を足しても自動で効き、走査も定期実行も要らない。**

実装は `any-learn-ai-core/src/domain/stale.ts`（assessments に同じ写し）。

#### 猶予は5分

プログラム生成の掃除係は30分だが、あれは「最長がプログラム生成
（20〜60秒）」という前提の値である。Q&A は実測5秒、採点は3.6秒で、
30分待たせるのは長すぎる。

実測で最も遅い診断レポート（123秒）＋キューの順番待ちを見て5分。

⚠️ **短すぎるほうが危ない。**正常に生成中のものを終端させると、
学習者が作り直しに走って二重に生成することになる。

用途ごとに刻む案（`#duration-estimates` の実績 × 10 など）もあるが、
仕組みが増えるので、まず一律で入れて実測を見てから決める。

#### 開始時刻が読めないときは「待ってよい」に倒す

⚠️ **ここを逆に倒さないこと。**

読めないのは移設前の記録か、書き込みが壊れた場合である。どちらも
「届かなかった」と決めつける根拠にならない。待たせるほうが、
出来ているものを作り直させるより害が小さい。

#### 既存の掃除係は残した

こちらは**書き換える**。読むときの判断だけだと、レコードは
`generating` のまま残り、DB を直接見た人や集計が誤る。

プログラム生成は1レコード1件で索引も張れる（走査が安い）ので、
書き換えられるならそのほうがよい。**対話系にできないことを、
できるところだけやっている。**

#### ⚠️ 残る弱点

レコードは `generating` のまま残る。

**状態は必ず `domain/stale.ts` を通して読むこと。**
生の `status` を直接見る集計や分析は誤る。
規約は構造ほど強くないので、ここは弱点として残る。

### 10.3 段階1〜4で「作らずに済んだ」もの

⚠️ **移設を通して「決めずに済んだ」ことを記録しておく。**
次に同じ規模の切り出しをするとき、どこに判断が要らなかったかが分かる。

- **呼び出し元にライブラリを配らない**（8.3）。全経路が非同期なら、
  呼び出し元が持つのは「SQS へ JSON を1件積む」だけになる
- **専用の冪等性の仕組みを作らない**（段階4a）。積む操作を受付の中だけに
  置けば、結果ハンドラの書き込みは全部上書きになる
- **通知に生成物を載せない**（段階4b）。載せないほうが経路が1つに保たれる
- **登録簿と単価表の一致をテストで縛らない**（段階1・10.1）。
  サービス側は単価を登録簿の行へ埋め込み、呼び出し元側は単価を
  記録に残す形にした。**縛る対象そのものが無くなった。**
  ⚠️ **ずれられる構造を残したまま見張るのは、解いたことにならない。**

いずれも「作らなかった」ことが答えだった。作りかけて捨てたものは
`domain/once.ts` の1つだけである。

⚠️ **共通しているのは「持たせない」判断である。**

| 何を持たせなかったか | 代わりに |
|---|---|
| 呼び出し元にライブラリ | 依頼の形（小さくて安定した契約）だけ |
| 結果ハンドラに積む操作 | 受付が席を作り、結果は埋めるだけ |
| 通知に生成物 | 「変わった」という合図だけ |
| 読む側に単価表 | 単価を記録に残す |
| 経路ごとの掃除係 | 読むときに猶予を見る |

**持たせなければ、ずれようがない。**同期を取る仕組みを作るより、
同期を取る必要を無くすほうが強い。
