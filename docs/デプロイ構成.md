## 使用モデル

設計書 v1.0 では重量級処理に Opus を指定していましたが、
実装では **`claude-sonnet-5`** を使っています。

| 用途 | モデル |
|------|-------|
| 目標分析・学習計画算出・アセスメント生成・診断レポート・プログラム生成・解説生成 | `claude-sonnet-5` |
| 対話・回答評価・Q&A・脱線検知・確認問題生成 | `claude-haiku-4-5` |

Opus ではなく Sonnet を選んだ理由:

- 単価が約 6 割（$3/$15 対 $5/$25 per Mtok）
- 生成が速く、非同期ジョブの待ち時間が短くなる
- この用途（構造化された学習コンテンツの生成）では品質差が小さい

⚠️ Sonnet 5 は `temperature` / `top_p` / `top_k` を受け付けません（400 になる）。
本実装では元々設定していないため影響はありませんが、
将来これらを足すときは注意してください。

### コスト最適化

- **Prompt Caching**: システムプロンプトに `cache_control: ephemeral` を付与。
  日時・ユーザー ID 等の可変値をシステムプロンプトに含めないことで
  キャッシュヒット率を最大化しています。
- **Structured Outputs**: `output_config.format` の JSON Schema で出力を制約し、
  パース失敗によるリトライを排除。
- **ローカル採点**: アセスメントの4択問題（全体の約75%）は API を呼ばず
  ローカルで判定します。

## 実装で判明した重要な落とし穴

### 1. shared-infra を手元から流すときは `--context googleOAuth=true`

⚠️ **付け忘れると Google ログインが落ちます。**

`cdk.json` に既定値が無く、CI（`deploy.yml`）だけが渡しています。
手元から `cdk deploy` すると context が未設定になり、CDK は
「Google を使わない構成」を組み立てます。

```
[~] AWS::Cognito::UserPoolClient SpaClient
 ├─ SupportedIdentityProviders: ["COGNITO", "Google"] → ["COGNITO"]
 └─ [-] DependsOn: ["GoogleProvider"]
```

Google で登録した人がサインインできなくなります。

```bash
AWS_REGION=ap-northeast-1 AWS_ACCOUNT_ID=417589270669 DEPLOY_ENV=dev \
  npx cdk deploy --all --require-approval never --context googleOAuth=true
```

⚠️ **必ず `cdk diff` で Cognito に差分が出ないことを確かめてから流すこと。**
2026-08-10 に実際にこの差分が出て、デプロイ直前に気づきました。

### 2. 契約テーブルは shared-infra を先に入れる

core / assessments は契約（プランと上限）とカウンタのテーブル名を
SSM から引きます。shared-infra が先に入っていないと、パラメータが
無くてデプロイに失敗します。

```
shared-infra → core / assessments（この2つは順不同）
```

### 3. API Gateway のステージ再デプロイが必須、かつ結果整合性がある

共有 API にリソースを追加しただけでは、そのリソースはステージに反映されず
**HTTP 403（Missing Authentication Token）** になります。

さらに CDK デプロイ直後は結果整合性のため、`create-deployment` を
一度実行しただけでは反映が間に合わないことがあります（実際に再現しました）。

対策として、各サービスのワークフローでは
**認証必須メソッドが 401 を返すまで最大5回リトライ**し、
403 のままなら明示的に失敗させています。
開発規則どおり `continue-on-error` は付けていません。

### 4. Next.js 15 は `_not-found/index.html` を生成しない

開発規則の例では `/_not-found/index.html` を挙げていますが、
Next.js 15 の静的エクスポートが実際に出力するのは **`404.html`**
（および同内容の `404/index.html`）です。

存在しないパスを指定すると CloudFront が 404 を返せずエラーになるため、
`NOT_FOUND_PAGE_PATH = '/404.html'` としています。
規則の本質（ランディングページを 404 に流用しない）は満たしています。

CI では `out/404.html` の存在を検証し、無ければビルドを失敗させます。

### 5. `next build` は `NODE_ENV=production` で実行する

`NODE_ENV` を上書きすると 404 ページの生成に失敗します
（`<Html> should not be imported outside of pages/_document`）。

### 6. API Gateway のアカウントレベル設定はシングルトンにする

CloudWatch Logs ロールは**アカウント × リージョンに1つ**しか設定できません。
dev/stg/prod が同一アカウントに同居する構成で各環境が個別に設定を持つと
相互に上書き・削除し合うため、環境非依存のスタック
（`any-learn-ai-apigateway-account`）として分離しています。

### 7. API Gateway (REST) の 29 秒制限は引き上げられない

**これは設計時に見落とすと後から作り直しになる、最も重い制約です。**

API Gateway REST API の統合タイムアウトは **29 秒が上限**で、
引き上げる手段がありません（`timeoutInMillis: 29000`）。
Lambda 側のタイムアウトをいくら伸ばしても、クライアントは 29 秒で
`{"message": "Endpoint request timed out"}` を受け取ります。

厄介なのは **Lambda は完走している**点です。DynamoDB には結果が
書き込まれているのに、クライアントは ID すら受け取れず、
生成物に二度とたどり着けません。実際にアセスメント生成で発生しました。

AI を使う重い処理はほぼ確実にこの制限を超えます。

| 処理 | 実測/推定 | 方式 |
|------|----------|------|
| プログラム生成 | 数分 | 非同期 |
| アセスメント設問生成 | 29秒超 | 非同期 |
| 診断レポート | 29秒超 | 非同期 |
| 解説生成・再解説 | 30〜90秒 | 非同期 |
| 目標分析 (`POST /goals`) | 約16秒 | 非同期 |
| 学習計画の算出 (`POST /goals/{id}/plan`) | 約11秒 | 非同期 |
| Haiku を使う処理全般 | 数秒 | 同期 |

目標分析と学習計画の算出は 29 秒に収まってはいましたが余裕が乏しく、
モデルの応答が伸びれば同じ症状に陥るため予防的に非同期化しました。
**これで AI を呼ぶ処理はすべて非同期です。**

#### 採用した方式: 非同期ジョブ + ポーリング

```
starter (API Gateway)          worker (非同期 Lambda)      client
  ├ 入力を検証                                              
  ├ ID を採番して即座に記録                                  
  ├ status = generating                                     
  ├ worker を Event 呼び出し ──▶ AI 実行（最大10分）        
  └ 202 を即返す ───────────────────────────────────▶ ID を受け取る
                                 ├ 成功 → status = ready    │
                                 └ 失敗 → status = failed   │ GET でポーリング
                                           + エラー内容      ◀┘
```

重要なのは **失敗も必ず記録する**ことです。worker が黙って落ちると
クライアントは永久にポーリングし続けます。

worker は API Gateway に接続せず、`InvocationType: Event` でのみ
起動します。starter には対象 worker への `lambda:InvokeFunction` だけを
与えます。

### 8. OIDC の subject claim は immutable 形式

GitHub の OIDC トークンの `sub` クレームは、組織名・リポジトリ名だけでなく
**数値 ID を含む immutable subject claim** 形式です。

```
repo:{org}@{orgId}/{repo}@{repoId}:environment:{env}
```

旧形式 `repo:{org}/{repo}:environment:{env}` で信頼ポリシーを書くと
`sts:AssumeRoleWithWebIdentity` が **AccessDenied** になります。

実際の値は次で確認できます。

```bash
gh api repos/{org}/{repo}/actions/oidc/customization/sub --jq .sub_claim_prefix
```

ID は組織名・リポジトリ名を変更しても不変なので、リネームによる
乗っ取り（旧名を第三者が取得する攻撃）への耐性もあります。

---

### 9. Structured Outputs は配列の要素数を強制できない

`output_config.format` の JSON Schema では **`minItems` / `maxItems` が
サポートされていません**。「必ず20個の要素を返す」といった件数の制約を
スキーマに書いても効きません。

アセスメントの出題数を可変にしたとき、この制約が効いてきました。
件数の制御は次の2段構えで行っています。

1. **システムプロンプトで明示的に指示する**（何問にすべきかの判断基準を含めて）
2. **受け取った後にサーバー側で検証する**（範囲外なら失敗として記録）

同じ理由で、文字列長（`minLength` / `maxLength`）や数値範囲
（`minimum` / `maximum`）もスキーマでは強制できません。
「80文字以内」のような制約はプロンプトで指示するしかありません。

## アセスメントの出題数（設計書からの変更）

設計書 v1.0 は「20問（固定）」でしたが、実装では
**10〜30問の範囲で AI がテーマの広さに応じて決める**方式に変更しました。

固定20問には次の問題がありました。

- 「二次方程式の解の公式」のような限定的なテーマに20問は冗長で、
  同じ論点を言い換えただけの設問が混ざる
- 「統計学全般」「資格試験の全範囲」のような広いテーマでは20問では
  単元を網羅できず、診断の根拠が薄くなる

出題数が変わる以上、難易度と形式の配分も絶対数では持てないため、
比率で定義しています（easy 30% / medium 50% / hard 20%、
multipleChoice 約75% / shortAnswer 約25%）。

### freeText をやめた

当初は「理解の深さを測る」ために自由記述を1〜2問、末尾の hard に
置いていました。実際に出たのが

> 英語の12時制（現在・過去・未来×単純・進行・完了・完了進行）について、
> それぞれの基本的な使い分けの考え方を説明してください。
> 特に完了形と完了進行形の違いに触れてください。

で、問いが開きすぎて**何をどこまで書けばよいのか学習者に判断できません**
でした。診断の最後（24問目）に置かれるため、ここで手が止まると
それまでの23問が結果に結びつきません。

深さは hard の shortAnswer で測ります。ただし「〜について説明してください」
のような問い方を禁じ、答えの形が決まる聞き方（「〜と〜の違いを一言で」）に
するようプロンプトへ明記しました。

⚠️ 型と描画の既定分岐は残してあります。回答途中のアセスメントが
DynamoDB にあり、それが読めなくなってはいけないためです。

利用者が「なぜこの問題数なのか」を判断できるよう、
AI に出題数の根拠を書かせて画面に表示しています。

## 学習計画の確定とプログラム生成をひとつの流れにした

計画を確定すると画面には学習期間・週あたり時間・マイルストーンが出て
**完了したように見えます**。しかし実際にはもう1段階あり、ダッシュボードから
「学習プログラムを作る」→ 確認画面でもう一度押す必要がありました。

実ユーザーのログを調べたところ、`confirm-plan` と `calculate-plan` は
各1回実行されているのに `create-program` は **0回**。本人は
「プログラムは作ったはず」と認識したまま、そこで止まっていました。

しかもその中間画面は、goals 統合の結果 `createProgram({ goalId })` を
呼ぶだけになり、**新しい入力を何ひとつ求めない関門**になっていました。

そこで計画算出のワーカーが、計画を書き込んだあとそのまま生成を開始します。
中間画面は廃止しました。

### 設計上、意識的に決めた3点

**1. 生成の失敗で学習計画を巻き込まない**

`planStatus` は `ready` のままにします。計画は正しく算出できているのに
後続の失敗で計画ごと failed にすると、利用者は理解度診断からやり直す
ことになります。失敗はログに残し、ダッシュボードの作成ボタンから復旧します。

**2. `POST /programs` は二重生成しない**

自動生成が入ると、このエンドポイントが何らかの経路でもう一度叩かれたとき
**システム中で最も高コストな処理が二重に走ります**。進行中・完了済みの
プログラムがあれば作り直さず既存を返し、失敗しているものだけを
作り直しの対象にすることで、復旧の入口として安全に残せます。

**3. 作成ボタンは残す**

自動生成が入る前に作られた既存データと、生成失敗時の復旧経路になります。

### 画面を削除するときの注意

`/programs/new/` を消したとき、**CloudFront Function の `staticRoutes`
からも外す**必要がありました。残すと存在しないファイルへリライトして
404 応答自体が壊れます。ルーティングのテストは CloudFront Function の JS を
実際に実行して検証しているので、そちらも合わせて更新します。

## programs を goals に統合した理由

当初は `goals` と `programs` を別のマイクロサービスに分けていましたが、
**統合しました**。分けたことによる実害が出ていたためです。

きっかけは `programs` の入力定義でした。

```ts
interface CreateProgramRequest {
  readonly goalId?: string;
  /** 以下は呼び出し元（BFF / フロント）が渡す目標のコンテキスト */
  readonly subject?: string;
  readonly targetLevel?: string;
  readonly durationWeeks?: number;
  readonly weeklyStudyHours?: number;
  ...
}
```

ここに並ぶ項目は**すべて goal レコードに既にある値**です。
programs は goals のテーブルを読めないため、
**ブラウザが目標を取得してバラし、詰め直して programs へ渡していました**。
フロントエンドが2サービスの結合層をやらされていた状態です。

そこから出た実害:

| 症状 | 原因 |
|------|------|
| ダッシュボードの「学習プログラムを作る」ボタンが消えない | programs が goal を更新できず、フロントが `POST /goals/{id}/program` を別途呼ぶ必要があった。しかも失敗が握り潰されていた |
| 入力がすべて optional で検証できない | 正となる目標を参照できず、クライアントの申告を信じるしかない |
| 削除がブラウザからの多サービス連鎖 | サーバー側でカスケードできない |
| 「学習計画」と「学習プログラム」を利用者が区別できない | 期間・週あたり時間・マイルストーンは goal 側、フェーズ・ユニットは programs 側。**同じ概念がサービス境界で割れていた** |

最後の行が本質です。用語が紛らわしいのではなく、
**サービス境界がそのまま UI に漏れていました**。

分ける利点も実現していませんでした（同一パイプライン・同一 Lambda 構成・
同一リリース周期）。

### 統合後

- `POST /programs` の入力は **`{ goalId }` のみ**。他はサーバー側で目標から読む
- プログラム生成と同時に `goal.programId` を書く（紐づけ漏れが構造的に起きない）
- `DELETE /goals/{goalId}` がプログラムと進捗もカスケード削除する
- `POST /goals/{goalId}/program`（紐づけ）は廃止

API パスとテーブル名は据え置いたため、`learning` サービスとフロントの
URL は無改修です。リポジトリ名も当時は `any-learn-ai-goals` のままにしました。
OIDC の subject claim にリポジトリ名が含まれるため、改名すると cicd 側の
再デプロイを伴い、機能的な利得がありません。

> **その後の変更**: `learning` も同じ理由（同一パイプライン・同一リリース周期・
> 境界が UI に漏れる）で統合し、新リポジトリ `any-learn-ai-core` へ移した。
> このときは新規リポジトリを作ったので、名前の据え置き判断は解消している。

`assessments` は分けたままです。理解度チェックは一度限りの独立した成果物で、
ライフサイクルも goals とは別に動くためです。

### 移行手順（dev で実施）

`/programs` のパスとテーブル名を goals 側で再作成するため、
**先に programs スタックを破棄する**必要があります。逆順だと
「同名のリソースが既に存在する」で失敗します。

⚠️ この単純な手順が使えたのは dev だけです。dev は `removalPolicy` が
`DESTROY` かつ programs / progress とも 0 件だったためテーブルごと
消せました。stg / prod は `RETAIN` なのでテーブルが残り、goals 側の
再作成が失敗します。その場合は CloudFormation のリソースインポートで
goals スタックへ引き取ってください。

## フロントとサーバーのフィールド名の食い違い（最も繰り返した不具合）

**この種の不具合を4回踏みました。** 実ユーザーが遭遇したのは
「学習する」を押すと即座に「今回のセッションはここまでです」と出る症状です。

```
サーバー  : { nextMicroStep: {...}, isSessionComplete: false }
クライアント: next.microStep を参照
```

存在しないキーなので常に `undefined` になり、「次のステップが無い＝
セッション完了」と判定して完了 API を呼んでいました。実データでも
3回の試行がいずれも**開始から1〜3秒で completed** になっていました。

### 3つの防御をすべてすり抜ける

| 防御 | すり抜ける理由 |
|------|---------------|
| 型チェック | `optional` / `null` 許容だと、欠けていても TypeScript は何も言わない |
| ユニットテスト | フロントとサーバーが別リポジトリなので、突き合わせがどちらのテストにも入らない |
| E2E（curl） | サーバーの項目名で書くため、**クライアントの型を一度も通らない** |

curl ベースの E2E は「サーバーが正しいこと」しか見ておらず、
**フロントがそれを正しく読めるか**は誰も検証していませんでした。

### 対策

1. **サーバーが必ず返す項目から `optional` を外す。** 必須にしておけば、
   次に取り違えたときコンパイルエラーで気づけます。今回のバグは
   `null` 許容だったために黙って通りました。
2. **契約検証スクリプト**（`scripts/e2e-learning-contract.sh`）を追加。
   `lib-web/api.ts` の interface から**必須項目を自動抽出**し、実 API の
   レスポンスに存在するかを照合します。項目名をハードコードしないので、
   サーバー・フロントのどちらが変わっても食い違いを検出できます。

### 根本的には型の共有が要る

マルチリポジトリ構成である以上、コンパイル時に契約を強制するには
型定義を共有パッケージとして 公開する必要があります。
現状は上記2つの運用でカバーしています。

## 設定が必要な GitHub Secrets

開発規則に従い、環境ごとに異なる値はすべて GitHub Secret に置きます。

### リポジトリシークレット（全リポジトリ）

| 名前 | 値 |
|------|-----|
| `AWS_ACCOUNT_ID` | AWS アカウント ID |
| `AWS_REGION` | `ap-northeast-1` |

### environment シークレット（dev / stg / prod ごと）

| リポジトリ | 名前 | 内容 |
|-----------|------|------|
| 全リポジトリ | `AWS_DEPLOY_ROLE_ARN` | 当該環境のデプロイロール ARN（設定済み） |
| **shared-infra** | `ANTHROPIC_API_KEY` | Claude API キー（dev は設定済み。stg / prod は要設定） |

### Anthropic API キーの設定

API キーは環境ごとに異なる値なので、**GitHub Secret を正**とします。
Lambda はランタイムに GitHub Secrets を読めないため、デプロイ時に
shared-infra のワークフローが Secrets Manager へ注入します。
CDK は「箱」だけを作り、値をテンプレートに残しません。

```bash
gh secret set ANTHROPIC_API_KEY --repo any-learn-ai/any-learn-ai-shared-infra --env dev
gh secret set ANTHROPIC_API_KEY --repo any-learn-ai/any-learn-ai-shared-infra --env stg
gh secret set ANTHROPIC_API_KEY --repo any-learn-ai/any-learn-ai-shared-infra --env prod
```

未設定のままデプロイすると、ワークフローが**明示的に失敗**します
（実行時に AI 機能が黙って壊れるのを防ぐため）。

> 以前は手動で `aws secretsmanager put-secret-value` を実行する手順でしたが、
> これは「3 環境が完全に同一のコードからデプロイされる」原則に反するため廃止しました。
