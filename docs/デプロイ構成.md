## 使用モデル

設計書 v1.0 では重量級処理に Opus を指定していましたが、
実装では **`claude-sonnet-5`** を使っています。

| 用途 | モデル |
|------|-------|
| 目標分析・学習計画算出・アセスメント生成・診断レポート・プログラム生成・解説生成 | `claude-sonnet-5` |
| 対話・回答評価・Q&A・脱線検知・確認問題生成 | `claude-haiku-4-5` |

Opus ではなく Sonnet を選んだ理由:

- 単価が約 6 割（$3/$15 対 $5/$25 per Mtok）
- 生成が速く、非同期ジョブの待ち時間が短くなる
- この用途（構造化された学習コンテンツの生成）では品質差が小さい

⚠️ Sonnet 5 は `temperature` / `top_p` / `top_k` を受け付けません（400 になる）。
本実装では元々設定していないため影響はありませんが、
将来これらを足すときは注意してください。

### コスト最適化

- **Prompt Caching**: システムプロンプトに `cache_control: ephemeral` を付与。
  日時・ユーザー ID 等の可変値をシステムプロンプトに含めないことで
  キャッシュヒット率を最大化しています。
- **Structured Outputs**: `output_config.format` の JSON Schema で出力を制約し、
  パース失敗によるリトライを排除。
- **ローカル採点**: アセスメントの4択問題（全体の約75%）は API を呼ばず
  ローカルで判定します。

## 実装で判明した重要な落とし穴

### 1. API Gateway のステージ再デプロイが必須、かつ結果整合性がある

共有 API にリソースを追加しただけでは、そのリソースはステージに反映されず
**HTTP 403（Missing Authentication Token）** になります。

さらに CDK デプロイ直後は結果整合性のため、`create-deployment` を
一度実行しただけでは反映が間に合わないことがあります（実際に再現しました）。

対策として、各サービスのワークフローでは
**認証必須メソッドが 401 を返すまで最大5回リトライ**し、
403 のままなら明示的に失敗させています。
開発規則どおり `continue-on-error` は付けていません。

### 2. Next.js 15 は `_not-found/index.html` を生成しない

開発規則の例では `/_not-found/index.html` を挙げていますが、
Next.js 15 の静的エクスポートが実際に出力するのは **`404.html`**
（および同内容の `404/index.html`）です。

存在しないパスを指定すると CloudFront が 404 を返せずエラーになるため、
`NOT_FOUND_PAGE_PATH = '/404.html'` としています。
規則の本質（ランディングページを 404 に流用しない）は満たしています。

CI では `out/404.html` の存在を検証し、無ければビルドを失敗させます。

### 3. `next build` は `NODE_ENV=production` で実行する

`NODE_ENV` を上書きすると 404 ページの生成に失敗します
（`<Html> should not be imported outside of pages/_document`）。

### 4. API Gateway のアカウントレベル設定はシングルトンにする

CloudWatch Logs ロールは**アカウント × リージョンに1つ**しか設定できません。
dev/stg/prod が同一アカウントに同居する構成で各環境が個別に設定を持つと
相互に上書き・削除し合うため、環境非依存のスタック
（`any-learn-ai-apigateway-account`）として分離しています。

---

### 5. API Gateway (REST) の 29 秒制限は引き上げられない

**これは設計時に見落とすと後から作り直しになる、最も重い制約です。**

API Gateway REST API の統合タイムアウトは **29 秒が上限**で、
引き上げる手段がありません（`timeoutInMillis: 29000`）。
Lambda 側のタイムアウトをいくら伸ばしても、クライアントは 29 秒で
`{"message": "Endpoint request timed out"}` を受け取ります。

厄介なのは **Lambda は完走している**点です。DynamoDB には結果が
書き込まれているのに、クライアントは ID すら受け取れず、
生成物に二度とたどり着けません。実際にアセスメント生成で発生しました。

AI を使う重い処理はほぼ確実にこの制限を超えます。

| 処理 | 実測/推定 | 方式 |
|------|----------|------|
| プログラム生成 | 数分 | 非同期 |
| アセスメント設問生成 | 29秒超 | 非同期 |
| 診断レポート | 29秒超 | 非同期 |
| 解説生成・再解説 | 30〜90秒 | 非同期 |
| 目標分析 (`POST /goals`) | 約16秒 | 非同期 |
| 学習計画の算出 (`POST /goals/{id}/plan`) | 約11秒 | 非同期 |
| Haiku を使う処理全般 | 数秒 | 同期 |

目標分析と学習計画の算出は 29 秒に収まってはいましたが余裕が乏しく、
モデルの応答が伸びれば同じ症状に陥るため予防的に非同期化しました。
**これで AI を呼ぶ処理はすべて非同期です。**

#### 採用した方式: 非同期ジョブ + ポーリング

```
starter (API Gateway)          worker (非同期 Lambda)      client
  ├ 入力を検証                                              
  ├ ID を採番して即座に記録                                  
  ├ status = generating                                     
  ├ worker を Event 呼び出し ──▶ AI 実行（最大10分）        
  └ 202 を即返す ───────────────────────────────────▶ ID を受け取る
                                 ├ 成功 → status = ready    │
                                 └ 失敗 → status = failed   │ GET でポーリング
                                           + エラー内容      ◀┘
```

重要なのは **失敗も必ず記録する**ことです。worker が黙って落ちると
クライアントは永久にポーリングし続けます。

worker は API Gateway に接続せず、`InvocationType: Event` でのみ
起動します。starter には対象 worker への `lambda:InvokeFunction` だけを
与えます。

### 6. OIDC の subject claim は immutable 形式

GitHub の OIDC トークンの `sub` クレームは、組織名・リポジトリ名だけでなく
**数値 ID を含む immutable subject claim** 形式です。

```
repo:{org}@{orgId}/{repo}@{repoId}:environment:{env}
```

旧形式 `repo:{org}/{repo}:environment:{env}` で信頼ポリシーを書くと
`sts:AssumeRoleWithWebIdentity` が **AccessDenied** になります。

実際の値は次で確認できます。

```bash
gh api repos/{org}/{repo}/actions/oidc/customization/sub --jq .sub_claim_prefix
```

ID は組織名・リポジトリ名を変更しても不変なので、リネームによる
乗っ取り（旧名を第三者が取得する攻撃）への耐性もあります。

---

### 7. Structured Outputs は配列の要素数を強制できない

`output_config.format` の JSON Schema では **`minItems` / `maxItems` が
サポートされていません**。「必ず20個の要素を返す」といった件数の制約を
スキーマに書いても効きません。

アセスメントの出題数を可変にしたとき、この制約が効いてきました。
件数の制御は次の2段構えで行っています。

1. **システムプロンプトで明示的に指示する**（何問にすべきかの判断基準を含めて）
2. **受け取った後にサーバー側で検証する**（範囲外なら失敗として記録）

同じ理由で、文字列長（`minLength` / `maxLength`）や数値範囲
（`minimum` / `maximum`）もスキーマでは強制できません。
「80文字以内」のような制約はプロンプトで指示するしかありません。

## アセスメントの出題数（設計書からの変更）

設計書 v1.0 は「20問（固定）」でしたが、実装では
**10〜30問の範囲で AI がテーマの広さに応じて決める**方式に変更しました。

固定20問には次の問題がありました。

- 「二次方程式の解の公式」のような限定的なテーマに20問は冗長で、
  同じ論点を言い換えただけの設問が混ざる
- 「統計学全般」「資格試験の全範囲」のような広いテーマでは20問では
  単元を網羅できず、診断の根拠が薄くなる

出題数が変わる以上、難易度と形式の配分も絶対数では持てないため、
比率で定義しています（easy 30% / medium 50% / hard 20%、
multipleChoice 約75% / shortAnswer 約20% / freeText 1〜2問）。

利用者が「なぜこの問題数なのか」を判断できるよう、
AI に出題数の根拠を書かせて画面に表示しています。

## 設定が必要な GitHub Secrets

開発規則に従い、環境ごとに異なる値はすべて GitHub Secret に置きます。

### リポジトリシークレット（全リポジトリ）

| 名前 | 値 |
|------|-----|
| `AWS_ACCOUNT_ID` | AWS アカウント ID |
| `AWS_REGION` | `ap-northeast-1` |

### environment シークレット（dev / stg / prod ごと）

| リポジトリ | 名前 | 内容 |
|-----------|------|------|
| 全リポジトリ | `AWS_DEPLOY_ROLE_ARN` | 当該環境のデプロイロール ARN（設定済み） |
| **shared-infra** | `ANTHROPIC_API_KEY` | Claude API キー（dev は設定済み。stg / prod は要設定） |

### Anthropic API キーの設定

API キーは環境ごとに異なる値なので、**GitHub Secret を正**とします。
Lambda はランタイムに GitHub Secrets を読めないため、デプロイ時に
shared-infra のワークフローが Secrets Manager へ注入します。
CDK は「箱」だけを作り、値をテンプレートに残しません。

```bash
gh secret set ANTHROPIC_API_KEY --repo any-learn-ai/any-learn-ai-shared-infra --env dev
gh secret set ANTHROPIC_API_KEY --repo any-learn-ai/any-learn-ai-shared-infra --env stg
gh secret set ANTHROPIC_API_KEY --repo any-learn-ai/any-learn-ai-shared-infra --env prod
```

未設定のままデプロイすると、ワークフローが**明示的に失敗**します
（実行時に AI 機能が黙って壊れるのを防ぐため）。

> 以前は手動で `aws secretsmanager put-secret-value` を実行する手順でしたが、
> これは「3 環境が完全に同一のコードからデプロイされる」原則に反するため廃止しました。
