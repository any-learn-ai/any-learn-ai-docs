# 利用量と所要時間の所有権整理

作成: 2026-08-17

## 何をしたか

共有テーブル2つを廃止し、各マイクロサービスが自分のデータを自分で持つ形に改めた。

| 旧（shared-infra が所有） | 誰が読み書きしていたか | 新 |
| --- | --- | --- |
| `usage-counters` | core / assessments / llm の**3サービス** | core と assessments が**それぞれ**自分のものを持つ |
| `ai-usage` | llm が書き、core / assessments が読む | llm だけが持つ（読む人は居なくなった） |

## なぜやったか

AWS の指針が、この形を名指しで否定している。

> individual data stores cannot be directly accessed by other
> microservices, and persistent data is accessed only by APIs
>
> — AWS Prescriptive Guidance / Database-per-service pattern

`usage-counters` は**所有者が居ないテーブル**だった。3つのサービスが同じレコードを
更新しており、「どのサービスの都合でこの列があるのか」が誰にも言えない状態だった。

### 共有していた本当の理由は、原価だった

数えていたものを分解すると、共有が要るものは1つも無かった。

| 数えていたもの | 発生する場所 | 共有が要るか |
| --- | --- | --- |
| `coursesCreated` | core | 要らない |
| `sessionsStarted` | core | 要らない |
| `assessmentsCreated` | assessments | 要らない |
| `costMicroUsd`（原価の走る合計） | **llm**（呼び出しごと） | ⚠️ ここだけ跨いでいた |

つまり「原価の月次上限」という機能ひとつのために、3サービスが1つのテーブルを
共有していた。⚠️ **機能を1つ廃止したら、構造の問題ごと消えた。**

## 原価の月次上限を廃止した

`monthlyCostYen` / `monthlyCostMicroUsd` をプラン表・型・判定から外した。

代わりに**全プランがコース数の上限を持つ**ようにした。原価はコース数でほぼ決まり、
重い使い方でも 1 コース 90 円である。

| プラン | 月額 | コース数 | 重い使い方の上限額 | 比率 |
| --- | --- | --- | --- | --- |
| Free | 0 円 | 3 | 270 円 | 集客費 |
| Starter | 480 円 | 3 | 270 円 | 56% |
| Standard | 980 円 | 5 | 450 円 | 46% |
| Professional | 2,980 円 | 20 | 1,800 円 | 60% |

Professional の 20 コースは 500 セッションに相当し、1 日 16 セッション以上を
1 か月続けないと届かない。普通の使い方では当たらない。

⚠️ **原価が要らなくなったのではない。**どのモデルに何トークン払ったかは llm が
`ai-usage` に記録し続ける。後から数えたくなればそこから数えられる（今は画面に出さない）。

⚠️ **学習者に見せる意味も無かった。**「今月の原価の上限に達しました」は、こちらの
都合を学習者の言葉として出しているだけだった。

## 所要時間の見積もりは「結果イベントで受け取り、自分で貯める」

待ち画面の「あと何秒」は実測から出している。その実績の置き場所が問題だった。

**旧**: llm が `ai-usage` に `#duration-estimates` という番兵キーで書き、
core / assessments がそれを直接読む。⚠️ 自分で測ってもいない数字を、
他サービスのテーブルから読んでいた。

**新**: 所要時間とモデル名は**結果イベントに既に乗っている**（`LlmResult` の
`durationMs` / `model`）。結果を受け取るのは core / assessments なので、
そこで自分のテーブルへ書く。

```
llm ──(結果イベント: durationMs, model)──> core の結果ハンドラ
                                              └─> core-duration-estimates（自前）
                                                    ↑
                                          GET 系が読む（書く権限は無い）
```

⚠️ **契約（LlmResult）の変更は要らなかった。**必要な値は最初から流れていた。
読んでいた場所が間違っていただけである。

### 個数（units）の扱い

実績は「秒 / 個」で貯める。所要時間は作る個数でほぼ決まるため。

| 用途 | 個数 | どこから取るか |
| --- | --- | --- |
| `explanation` | 1 | 固定 |
| `goal-analysis` | 1 | 固定 |
| `program-generation` | セッション数 | 依頼の context |
| `assessment-generation` | 設問数 | ⚠️ **保存した実数**（依頼時の希望数ではない） |
| `report` | 設問数 | ⚠️ 依頼側（start-report）が context に載せる |

## ⚠️ この整理で見つかった既存の不具合

### 1. 待ち画面2つが、ずっと固定値だった

`get-explanation.ts` と `get-program.ts` は `estimateSeconds()` を呼んでいたが、
**CDK がテーブル名の環境変数を渡していなかった。**

読めないときは既定値へ倒す作りなので**落ちない。**そのため「実測から出している
つもりで、ずっと固定値だった」状態が誰にも気づかれず残っていた。
`get-explanation` は1人あたり75回通る、いちばん多い待ち画面である。

⚠️ **静かに劣化する配線は、落ちる配線より悪い。**

対策として、CDK のテストが**ソースを読んで**「`estimateSeconds` を呼ぶハンドラ」を
割り出し、そこに環境変数が渡っているかを突き合わせる。手で並べた一覧では、
また並べ忘れる。

### 2. assessments は逆に、全関数へ渡していた

読むのは2つ（`get-assessment` / `get-report`）だけなのに、**全9関数**に
他サービスのテーブルへの読み取り権限が付いていた。

## ⚠️ キー設計で踏みかけた罠

相乗りしていた頃、`purpose` と `model` は**普通の属性**だった。自前のテーブルでは
**キー属性**にしたので、更新式で `SET purpose = :purpose` と書くと DynamoDB が
`This attribute is part of the key` で拒否する。

⚠️ この関数は例外を投げない作りなので、**落ちずに黙って記録されなくなる。**
不具合1と同じ壊れ方に戻る。テストで固定した。

## ⚠️ 「数で縛るテスト」を7件やめた

この作業で落ちたテストのほとんどが、数を突き合わせるものだった。

```
expect(functions.length).toBe(41);
expect(methods.length).toBe(28);
expect(optionsMethods.length).toBe(23);
expect(businessResourceIds.size).toBe(23);
expect(tables.length).toBe(5);          （2 か所）
expect(tableNames.sort()).toEqual([...5 件ちょうど...]);
```

⚠️ **落ちたときに直す先が数字なので、数字を書き換えて通してしまう。**
それでは何も守っていない。守りたいことを直接書く形に改めた。

| 旧 | 新 |
| --- | --- |
| Lambda が 41 個 | ⚠️ synth の関数は業務関数より**必ず1つ多い**（logRetention のカスタムリソース） |
| メソッドが 28 本 | 素通し（認証なし）が**1本も無い** |
| テーブルが 5 つ | 実データが入っている5つが**この名前で在り続ける**（arrayContaining） |

## 残っている手順

1. ✅ core が自前のカウンタと実績テーブルを持つ
2. ✅ assessments を同じ形にする
3. ✅ 画面から原価表示と `monthly_cost` を撤去
4. llm が `ai-usage` を自分で持ち、`usage-counters` へ書くのをやめる
5. ⚠️ shared-infra から `usage-counters` と `ai-usage` を削除（**必ず最後**）

⚠️ **dev の `ai-usage` 412 件は捨てる。**原価の実測に使った検証データで、
数字は既に設計書へ書き出してある。stg / prod は両テーブルとも 0 件。

⚠️ **デプロイの順番**: 画面 → 各サービス → shared-infra。逆にすると、
まだ読んでいるサービスがある状態でテーブルが消える。
